# План фаз

Прочитай раздел PRD: $ARGUMENTS

Допиши фазы в `docs/roadmap/plan.md` (раздел «Фазы реализации») и обнови «Покрытие
критериев PRD» в конце плана — по номерам критериев (раздел «Покрытие по критерию»).

## Структура фазы

```markdown
### Фаза {N}: {название} (S{этап})

**Цель:** что даёт эта фаза
**Затрагивает:** core / adapters / runtime / shared / provision / docs
**Задачи:**

- [ ] Задача 1
- [ ] Задача 2

**Когда готова:** конкретный проверяемый критерий
```

## Размер фазы: одна фаза — один PR, который можно отревьюить

Фазу петля сдаёт одним PR: ревью → правки → ревью правок → гейт. Ревью — тоже сессия с
бюджетом ходов и контекста, и PR, который в неё не влезает, не ревьюится вовсе.

- **Не больше 5 задач в фазе.** Лимит итераций раннера (`maxIterations`) — потолок на всю
  фазу, а не на карточку: повтор после `maxTurns` съедает итерацию, и фаза на 11
  карточек при лимите 10 встаёт на брейкере посреди ночи.
- **Дифф фазы — до 3–4 тыс. строк.** Ориентир, а не механизм: больше — дели фазу.

Поймано живьём на каноне (28.10.2026): фаза 16c — 11 карточек и +12 тыс. строк одним PR.
Первое ревью работало 25 минут и вышло без вердикта — ни сводки, ни блока; петля встала
«ревью без вердикта». Фаза 16b перед ней сдавалась 4,5 часа кругами правок. План
16c–16e писался мимо этого скилла, фазы по 8–12 карточек.

## Размер задачи: одна карточка — одна сессия

У сессии кодера бюджет ходов (`maxTurns`). Превышение — не «чуть дольше», а обрыв посреди
работы: раннер коммитит остаток и запускает сессию заново, но повторов немного
(`coderTurnRetries`), и каждый съедает итерацию фазы. Исчерпал — петля встаёт до человека.

- **Не больше двух компонентов на карточку.** Три в сессию раннера не влезают — проверено
  на каноне ещё в фазе 2. Компонент — модуль со своими тестами (`core/x.ts` +
  `core/x.test.ts`), а не файл.
- **Больше ~8–10 файлов правок** — почти наверняка две задачи.
- **Переезд или переименование модуля вместе с новым поведением** — всегда отдельная
  карточка: перенос трогает импорты по всему дереву и съедает бюджет до начала работы.
- **Живая проба настоящим CLI** — своя карточка или явный критерий, который сессия может
  выполнить: ключа CLI у сессии петли нет, guard не даёт его читать. Критерий, который
  требует ключа, ставит карточку в `blocked` и останавливает фазу.

Проверка от противного: больше пяти критериев готовности или формулировка «и заодно вот
это» — карточка слишком крупная. Разбей.

Поймано живьём на потребителе (11.08.2026): карточка «оверлей поверх экрана» потянула новый
виджет, перенос хука в общий слой, новый форматтер, правки четырёх соседних компонентов и
e2e — 25 файлов. Сессия исчерпала 200 ходов и упала. Поднимать `maxTurns` бессмысленно:
следующая такая карточка упрётся позже и дороже. Лечится только размером карточки.

## Глубина резки зависит от исполнителя

Декомпозицию делает сильная модель ОДИН раз — здесь, при планировании. Сессия петли план
исполняет, а не сочиняет; раннер дерево подзадач не строит. Кто исполнитель — видно по
`modelRouting` конфига петли: метка `complexity:*` ведёт карточку на конкретную модель.

- **Сильный исполнитель** — карточка как выше: симптом, причина, что сделать, критерии.
- **Слабый исполнитель** — одно изменение поведения и **3–6 последовательных шагов**. Каждый
  шаг называет участок кода (символ, `describe`), ожидаемый результат и команду проверки.
  Ориентир — один модуль с тестами и небольшой участок подключения, обычно 3–6 файлов.
- **Резка кончается там, где следующий шаг — локальная правка по известному контракту.**
  Остался выбор архитектуры, неизвестный протокол или согласование нескольких контрактов —
  вопрос снимает планировщик (решение вписывается в тело), либо это отдельная карточка для
  сильного исполнителя. «Найди подходящее место» в шаге возвращает проектирование слабой
  модели — так писать нельзя.
- **Шаги не становятся отдельными карточками.** Карточка — одна сессия, фаза — не больше
  пяти карточек; дробление шагов в трекер ломает и то и другое.
- **Метку не понижают ради дешёвого маршрута.** Маленькая правка границы доверия остаётся
  `high`; если карточка всё равно должна уйти слабой модели — сначала решение в тело, потом
  метка по остаточному риску.

Поймано живьём на каноне (29.10.2026, #200): карточка `expert` смешала профиль песочницы,
подключение к запуску, живую пробу и миграцию действующей петли. Слабая модель написала
годный код (5 коммитов, тесты и типы зелёные), а модель посильнее на переписывании съела
контекст чтением файлов на 13 и 18 тыс. строк целиком и не сделала ни одного коммита.

## Покрытие по критерию

Строка «раздел PRD → фаза» покрытием не является: она «покрывает» и критерий, который план
забыл. Покрытие — по номеру критерия (`[S{этап}.{n}]`, скилл `prd`):

| Критерий | Фаза | Задача | Чем проверяется |
| -------- | ---- | ------ | --------------- |

- Каждый номер раздела — ровно в одной строке; критерий без задачи — план не готов.
- **Сверь решение плана с каждым критерием**, а не только наличие строки: выбранный
  механизм обязан его выполнять. На Фазе 18 строка покрытия была, а решение «`what` —
  сообщение без префикса» критерий «PID и время не меняют идентичность» не выполняло.
- Номера критериев задачи переходят в тело карточки дословно (скилл `issues`, «Приёмка»).
- У раздела PRD без номеров — сначала номера (скилл `prd`), потом план.

## Решение закрывает класс, а не случай

Решение в плане — то, что исполнитель не будет пересматривать. Поэтому выбирай вариант,
который закрывает класс входов, и записывай, что отвергнуто:

```markdown
**Решение:** идентичность отказа — поля типизированной ошибки (`code`, `params`).
**Отвергнуто:** разбор текста сообщения — текст пишется для человека и меняется вместе с
ним; каждый новый символ в подставленном значении ломает нормализацию.
```

- **Контракт строится из структур кода, а не разбором своего же текста.** Сообщение
  ошибки, строка лога, текст уведомления — представление для человека. Если решению нужно
  значение из ошибки, ошибка его несёт полем; вытаскивать его регуляркой из текста нельзя.
- **Развилку «A либо B» не оставляй исполнителю.** Слабая модель выбирает дешёвый вариант
  и чинит потом названный ревью случай, а не класс.

Поймано на каноне (02.11.2026, Фаза 18): план задал идентичность разбором текста ошибки.
Ревью трижды находило следующий край одной регулярки (`»` внутри заголовка, перевод
строки, порядок редакции) — три круга правок и две попытки `blocked` на правке, которую
типизированный отказ закрыл бы сразу. Ревью предлагало тип ещё в первом круге; исполнитель
выбрал регулярку.

## Задетые барьеры

Задетые барьеры — объединение двух наборов, оба целиком, без отбора «какие относятся»:

1. **Читающие исходник как текст** — окна «вызов A стоит выше B», сканы чистоты. Для
   каждого правимого файла ядра найди тесты, которые называют его строковым литералом
   пути (импорт `from './x.ts'` под шаблон не попадает):

   ```
   grep -rlE "['\"]<файл>\.ts['\"]" tests core --include='*.test.ts'
   ```

2. **Исполняющие модуль через импорты** — `npx vitest related --run <правимые файлы ядра>`.
   Vitest строит граф импортов и берёт каждый тест, транзитивно зависящий от правимого
   файла. Греп литерала пути такие зависимости не находит.

Оба набора — в команду последнего шага карточки:

```
npx vitest run <список из греп-литерала> && npx vitest related --run <правимые файлы ядра>
```

Отбор — снова решение исполнителю, а прогон дешевле круга правок. Те, что сторожат
правимый участок, — ещё и в «Карту чтения». На Фазе 18 вставка 22 строк в
`orchestrator.ts` уронила два окна (`core/phase-branch.test.ts`,
`tests/intent-crash-windows.test.ts`); узнали о них из CI и ревью, а не в сессии.

На Фазе 19 все пять карточек сдались зелёными, а полный гейт PR фазы упал на 60 тестах
в шести сценарных сьютах: новая обязательная сессия планировщика правок ждала план,
подставные сессии его не отдавали, и сценарии останавливались на `fix-plan`. Грепнутый
список их пропустил: обвязки зовут оркестратор транзитивно. Поэтому одного грепа мало.
Перечислять сценарные сьюты руками нельзя — список устаревает с первым новым сценарием,
а граф импортов Vitest считает сам. Полный `npm test` на каждой карточке гонял бы весь
сьют (178 файлов на 02.11) рядом с работающими процессами петли; `related` берёт только
зависящие — для `orchestrator.ts` на 02.11 это 40 файлов, все шесть упавших сьютов среди них.

## Исполнимость критериев

Каждый критерий готовности проверь вопросом: **может ли сессия выполнить его, если новый
код существует только в её ветке?** Раннер исполняется из установки на зафиксированной
ревизии (`ralph.project.md`, первый абзац): то, что ветка добавляет в каталог проб, схему
намерений или правила раннера, раннеру неизвестно до **мерджа → установки ревизии →
рестарта петли**. Одного мерджа мало.

Для карточек с живой пробой, правкой средств проверки или миграцией действующей петли
выпиши критерии таблицей прямо в план:

| Критерий | Кто проверяет | Проверяемая ревизия | Средство проверки / откуда исполняется | Предпосылка |
| -------- | ------------- | ------------------- | -------------------------------------- | ----------- |

В «Предпосылке» назови и возможности установленного раннера (пара пробы, схема
намерений), и нужные права.

Если критерий требует, чтобы результат этой же фазы был **установлен в исполняемый
раннер**, перенеси его после мерджа → установки → рестарта: в следующую фазу или в карточку
`human`. Обычные зависимости внутри фазы допустимы — модуль из первой карточки виден второй
в общей ветке фазы. Порядок для нового средства проверки: средство (новый сценарий пробы) —
своей фазой, мердж и установка, затем реализация, проверяемая уже установленным средством. Ветка не выбирает себе проверяющего — каталог проб принадлежит
установленному ядру, и ослаблять это ради удобства нельзя.

На #200 критерий «живая проба `sandbox`» стоял в той же карточке, что и добавление пробы в
каталог. Раннер трижды отверг намерение — проба была только в ветке, — и фаза сожгла три
итерации на том, что ни одна сессия исправить не могла.

## Перерезка упавшей карточки

Карточка уже заведена и упала (брейкер, `blocked`, повтор одного отказа, сессия без
коммитов). Сначала диагноз; перерезай, если причина — размер карточки, неснятые решения или
неисполнимый критерий. Транзиент, ручная предпосылка или неисправность раннера лечатся
устранением своей причины, а не новыми карточками. Перезапуск той же карточки на другой
модели без диагноза — не лечение.

- **Вход:** тело карточки, исход попыток (что закоммичено, какие проверки зелёные), причины
  отказов из лога раннера дословно.
- **Сначала диагноз**, по трём источникам: модель (не нашла участок, повторяла ошибку),
  карточка (несколько поведений, решение не принято, критерий неисполним), раннер (отказ без
  обратной связи). Лечится то, что сломалось, а не всё сразу.
- **Сохраняй сделанное.** Годные коммиты становятся первой частью, а не выбрасываются ради
  чистого переписывания: проверь их целевыми тестами и типами.
- **Выход:** новые тела карточек по шаблону `issues`, разрез и порядок зависимостей,
  включая мердж → установку → рестарт. Больше пяти карточек — новые фазы.
- Перенос в трекер — скилл `issues`; старую карточку закрыть комментарием со ссылками на
  новые.

## Правила

- Каждая фаза даёт РАБОЧИЙ результат: можно остановиться после любой.
- Первая фаза — минимальный сквозной путь: тонкий срез через все слои.
- В каждой фазе запланированы тесты, покрывающие её поведение, включая проверку барьера
  «от противного» (корень канона: скан, который никогда не краснел, может не работать).
- План покрывает ВСЕ критерии готовности раздела PRD — по номеру, а не разделом; задач,
  которых в PRD нет, не добавляй.
- Проверки в плане — детерминированные: целевые тесты на шагах, полный гейт на фазе.
  Дополнительного LLM-проверяющего на шаг или карточку не планируй — время решения растёт
  кратно, а гейт и ревью фазы уже есть.
- PRD неполный — вопрос до плана.
- Порядок задач внутри фазы — это порядок карточек: петля берёт их по номеру, а не по
  тексту плана. Задавать можно только порядок фаз.
