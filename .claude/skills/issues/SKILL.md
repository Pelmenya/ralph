# Вехи и карточки

Прочитай фазы плана: $ARGUMENTS

Для каждой новой фазы заведи веху и карточки в репозитории канона на его площадке
(`origin` этого дерева).

**Инструмент — MCP площадки, если он подключён; иначе её CLI.** Поведение площадки сверяй
с её документацией и OpenAPI, а не с интуицией от GitHub: она там систематически врёт
(статусов шесть, связь PR с карточкой — своя, slug меток — свой).

## Порядок действий

1. Прочитай фазы плана.
2. Проверь существующие вехи и открытые карточки — идемпотентность: дубль вехи или карточки
   хуже, чем лишний вопрос. Ищи полным списком, а не префиксом названия: поиск по началу
   строки молча пропускает карточку с другим первым словом.
3. Веха на фазу: название `Ralph · Ф{N}: {название}`, где номер и название — из заголовка
   фазы в плане (`### Фаза {N}: {название} (S…)`), без этапа в скобках. Одна форма имени на
   все вехи: по ней ищется существующая веха, и другая форма завела бы дубль.
4. Карточка на задачу: title, body, веха, **ровно одна метка сложности и ровно одна метка
   зоны** (разделы ниже).
5. **Фаза — в локальный конфиг петли.** Петля идёт по списку `common.phases` в
   `.claude/ralph/ralph.config.json` (файл локальный, в репозиторий не коммитится):
   `{ "milestone": "<название вехи>", "branch": "feature/f<N>-<slug>" }` на своё место в
   порядке. Веха без строки в конфиге петлёй не берётся никогда.
6. **Рестарт ради новой фазы не нужен** (#221). Раннер перечитывает `phases` на границе
   фаз — после мерджа текущей и до выбора следующей, — и в логе это строка `🗂 Список фаз
   перечитан`. Ставь фазу ПОСЛЕ текущей: вставка перед ней — стоп `config-reload`. Ядро,
   запущенное с ревизии старше #221, конфиг перечитывать не умеет — ему по-прежнему нужен
   рестарт на границе фазы.

## Статусы карточки (их шесть)

`open` → `inProgress` → `closed`; плюс `paused`, `declined`, `duplicate`. Дубль закрывается
статусом `duplicate` с комментарием-ссылкой на оригинал, а не `closed`.

В выводе CLI статус — объект (`{id, slug, name, status_type}`): сравнивай `status.slug`,
а не строку. Ожидатель, сравнивавший строку `closed`, молчал бы вечно.

## Метки

Slug меток — с дефисом (`complexity-low`): площадка вырезает двоеточие из slug, а фильтры
идут по slug.

**Сложность (ровно одна — кроме карточек `human`)** — по ней раннер выбирает модель:

| Метка               | Когда ставить                                                          |
| ------------------- | ---------------------------------------------------------------------- |
| `complexity:low`    | Механика: перенос, конфиг, текст — без решений                         |
| `complexity:medium` | Типовая правка по образцу: модуль с тестами, адаптер по готовому шву   |
| `complexity:high`   | Инженерные решения: граница доверия, протокол, барьер                  |
| `complexity:expert` | Критично для корректности: мердж, откат, разбор ответа площадки        |

Сомневаешься между двумя — бери более высокий уровень.

Метка — про **риск и решения**, а не про размер: маленькая правка границы доверия — `high`.
Понижать метку, чтобы карточка ушла дешёвой модели, нельзя: снимай остаточные решения в
тело (скилл `plan-phase`, «Глубина резки зависит от исполнителя»).

**У карточки `human` метки `complexity:*` нет.** Раннер отвергает такое сочетание
fail-closed («конфликт замысла»: кто исполнитель?), причём по ВСЕМ карточкам вехи, а не по
той, что собрался брать. Одна карточка с обеими метками останавливает всю фазу при исправном
коде.

**Зона (ровно одна):** `area:core`, `area:adapters`, `area:docs`, `area:devops` — по
каталогу, который правит карточка; правила каталогов — в их `CLAUDE.md`.

## Тело карточки

- **Симптом → Причина → Что сделать → Критерии готовности.** Критерии — поведение, а не
  «написать тест»; у барьера — тест «от противного».
- **Решения человека — в тело карточки, а не в комментарий.** Сессия петли получает тело
  карточки, а ветку обсуждения не видит: сессия, которой решение не вписали, сделает работу
  по отвергнутому варианту.
- **Зависимости — номерами** («зависит от #N», «закрыть до …»). Номер — только реальной
  карточки этой площадки: площадка связывает PR и карточку по любому `#N` в тексте.
- **Никаких проектных следов**: ни имени потребителя, ни пути машины, ни адреса хоста —
  карточки публичные.

### Карточка для слабого исполнителя

Если `modelRouting` конфига ведёт карточку на слабую модель, после «Симптом → Причина»
тело обязано нести разделы ниже — заголовками markdown, каждый непустой:

```markdown
## Решение
Интерфейс, инварианты, поведение отказа — уже выбранные. Не «реши, как лучше».
Отвергнуто: <вариант> — <почему>. (Из плана; без этой строки исполнитель и ревью
открывают развилку заново.)

## Границы
Что входит. Какие соседние изменения требуют нового плана, а не правки по ходу.

## Карта чтения
- `core/x.ts` → `buildFoo` — точка подключения
- `core/x.test.ts` → describe «foo отказ» — образец теста
- Образец реализации: `adapters/y.ts` → `parseY`

## Шаги
1. Тест: отказ preflight → запуск не вызван, причина сохранена.
   Проверка: `npx vitest run core/x.test.ts` — ожидается RED именно из-за отсутствующего
   поведения; это успех шага, переходи к шагу 2. Ошибка загрузки или другая причина —
   неожиданный отказ.
2. Подключить готовый профиль в `buildFoo` до запуска.
   Проверка: `npx vitest run core/x.test.ts && npm run typecheck` — ожидается GREEN.
3. …
N. Задетые барьеры: `npx vitest run <список из греп-литерала> && npx vitest related --run <правимые файлы ядра>` — GREEN.
   Красный барьер-окно чинится правкой кода (вынести блок), а не окна.

## Приёмка
Критерии PRD, которые закрывает карточка, — номером и дословно:
- [S{этап}.{n}] <текст критерия из PRD>
Поведенческие примеры, включая отрицательные. Живая проба — отдельной строкой, с парой
`cli`/`case` из каталога УСТАНОВЛЕННОГО раннера.

## Предпосылки
Что должно быть смерджено и установлено до старта. Нет — так и написать: «нет».
```

Существующие символы и пути планировщик проверяет **после чтения кода** по исходной
ревизии (`rg -n` должен их находить). Новые пути и символы помечает «создать» и задаёт их
контракт; якорь из предыдущей карточки фазы — с зависимостью на её номер. Якорь — имя
функции или `describe`, не номер строки: номера уплывают с первым же коммитом. Шагов 3–6,
у каждого — команда проверки и ожидаемый исход (RED или GREEN). Шаг без команды или с
формулировкой «найди подходящее место» — карточка не дорезана.

Номер критерия PRD, назначенный плану этой задаче, обязан стоять в «Приёмке» её карточки,
а текст — совпадать с PRD дословно: пересказ при переносе — то место, где на Фазе 18
потерялся «PID и время не входят в идентичность». Последний шаг правки файла ядра — прогон
задетых барьеров (скилл `plan-phase`, «Задетые барьеры»): оба набора из плана целиком,
без отбора — читающие исходник по литералу пути и исполняющие модуль через граф импортов.
Команда: `npx vitest run <список из греп-литерала> && npx vitest related --run <правимые файлы ядра>`.
На Фазе 19 один греп пропустил шесть сценарных сьютов: карточки сдались зелёными, а
60 тестов упали уже на полном гейте PR фазы. Поэтому `related` обязателен в последнем шаге
каждой карточки, правящей код, даже если план назвал только греп-список.

## Правила

- Порядок карточек = порядок задач в плане: петля берёт их по номеру. Заводи в том порядке,
  в каком их надо делать.
- Не выдумывай задач, которых нет в плане.
- **Карточка обязана помещаться в одну сессию**; в фазе не больше 5 задач (карточек),
  6–7 — только по решению человека, записанному в фазе плана строкой `**Размер:**`;
  больше 7 — никогда, дели фазу. Держит `tests/phase-size.test.ts` (скилл `plan-phase`).
  Увидел в плане крупную — не заводи как есть, вернись к `plan-phase`.
- Закрывает карточку описание PR строкой, НАЧИНАЮЩЕЙСЯ со слова «Закрывает» (корень канона,
  раздел Git), а не связь PR с карточкой.
- В конце — компактная сводка: веха → карточки по номерам → строка в конфиге.
