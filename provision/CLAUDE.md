# `provision/` — запуск на машине

Продуктовая часть провижна: как раннер стартует и как ему обновляют токен. Контурное —
адреса машин, ключи, туннель — живёт у потребителя и сюда не попадает никогда. Общие
правила репозитория — в [корне канона](../CLAUDE.md).

| Файл                        | Что это                                                               |
| --------------------------- | --------------------------------------------------------------------- |
| `ralph.service.example`     | ШАБЛОН юнита systemd с плейсхолдерами, ставится руками                |
| `start-tmux.sh`             | запуск петли в tmux-сессии                                            |
| `update-token.sh`           | ротация токена форжа                                                  |
| `resolve-worktree-path.mts` | печатает путь дерева раннера для профиля — тем же резолвом, что ядро  |
| `install-stand.sh`          | стенд внешней установки: держит ли CLI внешний хук; отчёт — в `docs/` |
| `stand/stand.mts`           | стенд живых проб в изоляции ОС: `check` доказывает изоляцию, `exec`   |
| `stand/isolate.sh`          | сборка корня стенда в своих namespace: запись только в каталог стенда |
| `stand/egress.mts`          | сеть стенда: прокси к адресу провайдера (цепочкой через прокси хоста) |
| `stand/fake-mcp.mts`        | фиктивный MCP (stdio): чтение и мутация только пишут журнал стенда    |

## Местные правила

**Только плейсхолдеры.** `__REPO_DIR__` и его соседи — не заглушка «пока так»: юнит с
незаполненным плейсхолдером стартует и честно падает с «нет каталога», а не делает вид,
что работает. Конкретное значение здесь — это след машины в публичном репозитории.

**Один резолв пути, а не два.** `resolve-worktree-path.mts` существует затем, чтобы шелл и
ядро отвечали на вопрос «где дерево раннера» одинаково. Второй ответ, посчитанный в
скрипте, расходится с первым ровно в тот день, когда меняется схема имён.

**Эта папка вне скана чистоты ядра.** Не потому, что «не код»: обвязка запуска при
переносе заменяется под своё окружение, а не копируется как есть. Барьер следов на неё
распространяется в полной мере — публичность репозитория от папки не зависит.

**Стенд живых проб изолирует ОС, а не каталог** (задача 182, принцип 8
`docs/harness-contract.md`). Отрицательная проба просит CLI сделать запрещённое, и при
дефектном барьере это исполняется — поэтому граница стоит в ядре ОС: корень стенда собран
белым списком (`isolate.sh`), дома человека в нём нет, запись вне каталога стенда — EROFS.
Белый список, а не «весь `/` на чтение»: первый вариант оставил записываемыми `/dev/shm` и
`/run`, и файлы изнутри появились на хосте. Проверка изоляции (`stand.mts check`) идёт при
выключенном барьере и краснеет на любом выходе за пределы, даже при совпавших хешах
конфигов человека — хеши только дополнительная проверка. Где namespace недоступны (без root
при запрете user namespace), живые тесты стенда пропускаются, называя причину, а `check`
краснеет: стенд без изоляции — не стенд. С `STAND_ISOLATE=1` `install-stand.sh` не
исполняет бинарь CLI на хосте ни разу, включая `--version`.

**Улики судьи — вне досягаемости проверяемого.** Каталог стенда пишется изнутри, поэтому
судья `install-stand.sh` не берёт из него ничего на веру: ожидаемое — переменной хоста, логи
сессий — в соседнем каталоге вне стенда, логи хуков — копией только обычного файла без
следования симлинку, а хуки и копии guard внутри только для чтения. Так же прокси выхода,
работающий снаружи с правами человека, пишет журнал в стенде по дескриптору, открытому до
старта, а не по имени: имя изнутри подменяется симлинком на файл человека.
