# `adapters/` — швы

Всё, что зависит от площадки: источник задач, форж, рантайм кодер-сессии, нотификатор,
проверка деплоя. Ядро знает **интерфейс** шва, а какая реализация подключена — решает
`ralph.config.json` → `adapters.*`. Общие правила репозитория — в [корне канона](../AGENTS.md).

## Что где

| Модуль                       | Что это                                                                   |
| ---------------------------- | ------------------------------------------------------------------------- |
| `adapters.ts`                | ИНТЕРФЕЙСЫ швов — контракты точек расширения, без единой реализации       |
| `adapters-impl.ts`           | сборка: `buildAdapters` выбирает реализацию каждого шва по ключу конфига  |
| `github-forge-commands.ts`   | примитивы мердж-пути GitHub: мердж PR, «фаза смерджена», метка blocked    |
| `github-issue-commands.ts`   | карточки GitHub: очередь фазы, тело задачи, намерения сессии, веха, доска |
| `github-pr-commands.ts`      | pull request'ы GitHub: лента ревью, голова PR, заведение и поиск PR       |
| `github-deploy-commands.ts`  | два чтения пост-мердж проверки: коммит мерджа и прогоны deploy-workflow   |
| `sourcecraft-task-source.ts` | источник задач поверх SourceCraft                                         |
| `sourcecraft-api.ts`         | синхронный HTTP-транспорт к её API                                        |
| `sourcecraft-ci-checks.ts`   | чек PR у SourceCraft: вердикт прогона CI и лог упавшего куба              |
| `session-end.ts`             | исход сессии рантайма (`SessionEndReason`) по признакам его CLI           |
| `runtime-profile.ts`         | профиль рантайма (харнесс, провайдер) и разбор ответа `--version` его CLI |

## Местные правила

**Это единственное место, где команды форжа законны.** Всё остальное дерево сканируется на
`gh`/`glab` — здесь скан не идёт, потому что здесь им и место.

**Интерфейс отдельно от реализации.** `adapters.ts` не импортирует ни одной реализации:
иначе подключение одного шва тянуло бы за собой транспорт всех остальных, и «выключить
деплой-проверку» перестало бы означать «не грузить её код».

**Различие площадок — не в переименовании методов.** У одного форжа доска — отдельная
сущность, у другого — проекция статуса задачи; у одного связь issue↔PR даёт ключевое слово
в сообщении коммита, у другого её проставляют явно. Шов обязан выражать НАМЕРЕНИЕ («задача
закрыта», «фаза смерджена»), иначе реализация для второй площадки получается подгонкой под
механику первой.

**Fail-closed на границе.** Не смогли прочитать голову PR — бросай, а не отдавай пустую
строку. Пустая строка проедет дальше и остановит петлю в месте, где причину уже не видно.
То же у `null`, если он — штатный ответ: `findOpenPullRequest` отдаёт null на «PR нет», и
сбой, отданный им же, петля читала как «PR нет» и заводила второй PR (#127). Сбой — бросок.

**Реализация одного форжа — несколько файлов, и это не дробление ради дробления.**
GitHub-половина разложена по темам (мердж-путь, карточки, pull request'ы, деплой), потому
что у групп разные потребители и разные режимы отказа: очередь fail-closed, веха и доска
fail-open. Один файл на всё дал бы модуль, который читают только грепом. Второй форж
волен собраться иначе — швы описаны методами, а не файлами.

**Мердж-путь `taskSource` развязан, `gate` — нет.** Барьер
`MERGE_PATH_BOUND_SEAMS` перечисляет теперь один только шов гейта: состав и прогон чеков
`tryMergePhase` берёт напрямую из `core/gate.ts`, и принять `gate: 'cargo'` значило бы
соврать. Снятие — провести прогон через `adapters.gate.runChecks`.

**Секрет площадки называет сам шов** (`secretEnvNames`, #56). Ядро вырезает значения этих
переменных из вывода упавшей сессии, лога и пуша, но списка площадок не ведёт: токен
SourceCraft однажды уже прошёл мимо такого списка, а он даёт мердж в `main`. Метод
обязательный, пустой ответ отвергает контрактный сьют — новый шов без секрета не соберётся.
Имя переменной, которое шов называет, обязано совпадать с тем, откуда токен берёт его
транспорт: у SourceCraft это общая константа `SOURCECRAFT_TOKEN_ENV`.

**Готовность рантайма спрашивается у шва** (`checkAvailable`, #44). Сломанный рантайм раньше
всплывал первой кодер-сессией — после worktree и установки зависимостей. Теперь `main()` до
них зовёт `checkAvailable` у каждого достижимого рантайма (статический плюс провайдеры
`modelRouting`), и отказ звучит «кодер-рантайм недоступен», а не как отказ форжа: ремонт у
них разный. Метод обязательный; проба не пишет ничего и идёт в `--dry-run` тоже. Ключи
kimi/openai проверяет не она, а резолв рантаймов в preflight.

**Исход сессии называет рантайм, а не ядро** (`session-end.ts`, Фаза 16). Формулировки
CLI — лимит, вход, бюджет ходов, обрыв — меняются с версией и разные у харнессов, поэтому
их регулярки живут здесь, у классификатора своего CLI, а ядро получает одно из семи слов.
У каждого ключа реестра `coderRuntime` обязан быть классификатор и набор фикстур:
contract suite (`session-end.test.ts`) требует, чтобы каждый исход был подтверждён
фикстурой или назван неподдерживаемым с причиной (у Codex нет бюджета ходов), и проверяет
исход через боевой spawn-путь. Фикстуры — обрезанный вывод CLI с источником каждой строки
(`__fixtures__/README.md`). Узкие формулировки проверяются раньше широких: «not your usage
limit» у Claude — перегрузка, а не лимит.

**Версию CLI разбирает рантайм, а читает раннер перед каждой сессией** (`runtime-profile.ts`,
#113, R13). CLI обновляются сами и меняют поведение между итерациями; без версии в записи
попытки дефект ядра неотличим от смены инструмента. Версия — фактическая (`--version`
бинаря), а не ожидаемая из конфига. Разбор строгий, по форме ответа своего CLI: чужая строка,
пустой ответ, отказ запуска — `unknown` с причиной, а не номер из баннера обёртки и не пропуск
поля. Харнесс и провайдер названы порознь: Kimi — харнесс Claude Code с провайдером Moonshot,
и смена версии `claude` касается обоих. У каждого ключа реестра `coderRuntime` обязана быть
запись — сьют `runtime-profile.test.ts` сверяет это и проверяет запись попытки через боевой
spawn-путь каждого рантайма.
