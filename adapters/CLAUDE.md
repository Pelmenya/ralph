# `adapters/` — швы

Всё, что зависит от площадки: источник задач, форж, рантайм кодер-сессии, нотификатор,
проверка деплоя. Ядро знает **интерфейс** шва, а какая реализация подключена — решает
`ralph.config.json` → `adapters.*`. Общие правила репозитория — в [корне канона](../CLAUDE.md).

## Местные правила

**Это единственное место, где команды форжа законны.** Всё остальное дерево сканируется на
`gh`/`glab` — здесь скан не идёт, потому что здесь им и место.

**Интерфейс отдельно от реализации.** `adapters.ts` не импортирует ни одной реализации:
иначе подключение одного шва тянуло бы за собой транспорт всех остальных, и «выключить
деплой-проверку» перестало бы означать «не грузить её код».

**Различие площадок — не в переименовании методов.** У одного форжа доска — отдельная
сущность, у другого — проекция статуса задачи; у одного связь issue↔PR даёт ключевое слово
в сообщении коммита, у другого её проставляют явно. Шов обязан выражать НАМЕРЕНИЕ («задача
закрыта», «фаза смерджена»), иначе реализация для второй площадки получается подгонкой под
механику первой.

**Fail-closed на границе.** Не смогли прочитать голову PR — бросай, а не отдавай пустую
строку. Пустая строка проедет дальше и остановит петлю в месте, где причину уже не видно.
То же у `null`, если он — штатный ответ: `findOpenPullRequest` отдаёт null на «PR нет», и
сбой, отданный им же, петля читала как «PR нет» и заводила второй PR (#127). Сбой — бросок.

**Реализация одного форжа — несколько файлов, и это не дробление ради дробления.**
GitHub-половина разложена по темам (мердж-путь, карточки, pull request'ы, деплой), потому
что у групп разные потребители и разные режимы отказа: очередь fail-closed, веха и доска
fail-open. Один файл на всё дал бы модуль, который читают только грепом. Второй форж
волен собраться иначе — швы описаны методами, а не файлами.

**Мердж-путь `taskSource` развязан, `gate` — нет.** Барьер
`MERGE_PATH_BOUND_SEAMS` перечисляет теперь один только шов гейта: состав и прогон чеков
`tryMergePhase` берёт напрямую из `core/gate.ts`, и принять `gate: 'cargo'` значило бы
соврать. Снятие — провести прогон через `adapters.gate.runChecks`.

**Секрет площадки называет сам шов** (`secretEnvNames`, #56). Ядро вырезает значения этих
переменных из вывода упавшей сессии, лога и пуша, но списка площадок не ведёт: токен
SourceCraft однажды уже прошёл мимо такого списка, а он даёт мердж в `main`. Метод
обязательный, пустой ответ отвергает контрактный сьют — новый шов без секрета не соберётся.
Имя переменной, которое шов называет, обязано совпадать с тем, откуда токен берёт его
транспорт: у SourceCraft это общая константа `SOURCECRAFT_TOKEN_ENV`.

**Готовность рантайма спрашивается у шва** (`checkAvailable`, #44). Сломанный рантайм раньше
всплывал первой кодер-сессией — после worktree и установки зависимостей. Теперь `main()` до
них зовёт `checkAvailable` у каждого достижимого рантайма (статический плюс провайдеры
`modelRouting`), и отказ звучит «кодер-рантайм недоступен», а не как отказ форжа: ремонт у
них разный. Метод обязательный; проба не пишет ничего и идёт в `--dry-run` тоже. Ключи
kimi/openai проверяет не она, а резолв рантаймов в preflight.

**Исход сессии называет рантайм, а не ядро** (`session-end.ts`, Фаза 16). Формулировки
CLI — лимит, вход, бюджет ходов, обрыв — меняются с версией и разные у харнессов, поэтому
их регулярки живут здесь, у классификатора своего CLI, а ядро получает одно из семи слов.
У каждого ключа реестра `coderRuntime` обязан быть классификатор и набор фикстур:
contract suite (`session-end.test.ts`) требует, чтобы каждый исход был подтверждён
фикстурой или назван неподдерживаемым с причиной (у Codex нет бюджета ходов), и проверяет
исход через боевой spawn-путь. Фикстуры — обрезанный вывод CLI с источником каждой строки
(`__fixtures__/README.md`). Узкие формулировки проверяются раньше широких: «not your usage
limit» у Claude — перегрузка, а не лимит.

**Версию CLI разбирает рантайм, а читает раннер перед каждой сессией** (`runtime-profile.ts`,
#113, R13). CLI обновляются сами и меняют поведение между итерациями; без версии в записи
попытки дефект ядра неотличим от смены инструмента. Версия — фактическая (`--version`
бинаря), а не ожидаемая из конфига. Разбор строгий, по форме ответа своего CLI: чужая строка,
пустой ответ, отказ запуска — `unknown` с причиной, а не номер из баннера обёртки и не пропуск
поля. Харнесс и провайдер названы порознь: Kimi — харнесс Claude Code с провайдером Moonshot,
и смена версии `claude` касается обоих. У каждого ключа реестра `coderRuntime` обязана быть
запись — сьют `runtime-profile.test.ts` сверяет это и проверяет запись попытки через боевой
spawn-путь каждого рантайма.

**Возможности рантайм объявляет сам** (`runtime-capabilities.ts`, Фаза 16b, #118). Ядро
передаёт `RunOptions` всем рантаймам одинаково, и до карточки неподдержанный параметр молча
игнорировался: `maxTurns` у Codex выглядел гарантией, которой у харнесса нет. Поле
`capabilities` у шва обязательное — `turnLimit` (`required`, если CLI сам обрывает сессию на
потолке, иначе `best-effort`) и `fallbackModel`. `buildAdapters` проверяет форму у КАЖДОГО
ключа реестра, а не только у выбранного: фолбэк и маршруты `modelRouting` берут рантайм мимо
выбора. Объявляется то, что CLI исполняет, а не то, что хотелось бы: Claude Code и Kimi (тот
же харнесс) — `required`, `codex exec` флага потолка не знает — `best-effort`. Сверку с
конфигом делает ядро (`core/runtime-requirements.ts`): обе возможности, и общий `fallbackModel`
у рантайма без фолбэк-модели — строка `⚠` на старте, а не молчание. Третье поле — необязательный
`toolless` (#217): CLI умеет сессию без единого инструмента флагом запуска. Молчание —
«не умеет», и объявлен он только у харнесса Claude Code (`claude`, `kimi`); прочие рантаймы
запуск с `toolless` отменяют до spawn, а не выдают сессии полный набор.

**Guard регистрирует харнесс своим форматом, а исполняемое у барьера одно**
(`harness-guard.ts`, Фаза 16b, #119). Проба барьера до карточки знала только JSON settings
Claude Code и отвергала Codex целиком. Стенд Фазы 11 (`docs/install-stand.md`) показал, что
внешний блокирующий хук держат все четыре CLI, но регистрируют по-разному: Codex — `-c
hooks.PreToolUse=[…]` в argv с `--dangerously-bypass-hook-trust` и `--enable hooks` (без
первого хук молча не зовётся; второй — защита в глубину: `[features] hooks = false` в
`.codex/config.toml` снимает и хуки из `-c`, а `--ignore-user-config` раннера такой файл не
грузит, пока дерево не доверено иным путём), Kimi
Code — `[[hooks]]` в `config.toml` своего дома, OpenCode — плагин на `tool.execute.before`.
Здесь — построение этих регистраций, их обратное чтение (проба читает ТО, что уйдёт в CLI) и
форма события: вход Codex и Kimi — форма Claude Code (`tool_name: "Bash"`), но у Kimi путь
файла — `path`, а matcher без якорей; OpenCode зовёт плагин, и плагин сам переводит `bash`/
`filePath` в форму Claude Code. Свою ошибку плагин бросает — упавший при загрузке плагин CLI
пропускает. Хук он пропускает только кодом 0: упал, завис, не запустился — блок (ревью Фазы
16b: прежняя семантика «блокирует только 2» пропускала `rm -rf` при сломанном хуке — класс
#120), и с #192 блок несёт код неисправности последней строкой: `hook-failed` у хука,
`plugin-fault` у самого плагина — проба правила такой блок не засчитывает. MCP-инструмент
OpenCode называет `<сервер>_<инструмент>` без `mcp__`, и matcher канона его не видел; плагин
отдаёт его именем `mcp__…` без второго разделителя, которое правило MCP блокирует всегда
(`opencodeClaudeToolName`): границу сервера и инструмента по имени не восстановить. Патч судится
по каждому пути из `patchText`, и разбор повторяет CLI: строки только по `\n`, заголовок —
`startsWith`, путь — `.trim()`. Табуляция у края, оставленная в пути барьера, и `\r` после
двоеточия, на котором регекс с флагом `m` терял строку, уводили env-файл мимо правил защищённых
путей. Всё это — перевод в форму Claude Code для хуков потребителя, которые читают её со stdin;
вердикт канона с #192 даёт guard регистрации раннера по сырому событию (ниже), и для него
`multiedit` и `batch` — `unknown-tool`: первого CLI 1.19.4 в режиме `run` модели не отдаёт,
вложенные вызовы второго стенд не сверял. Перевод остаётся: путь элемента `edits[]`
(`multiedit`) уходит хукам дерева `file_path` и судится отдельным вызовом, `batch` вне таблицы
встроенных уходит им MCP-именем, которое правило MCP блокирует целиком. По сроку хука плагин
гасит всю его группу процессов, а не один `sh`. Код 0 с JSON-отказом в форме Claude Code
(`permissionDecision: "deny"`, `decision: "block"`, `continue: false`) плагин тоже считает
блоком: хуки потребителя переезжают в регистрацию вместе с каноническими, и прежде такой хук в
OpenCode молча переставал блокировать. Понимают ли JSON-решение Codex и Kimi Code, стенд не
сверял; хуки канона блокируют кодом 2 и от этого не зависят. Патч без `patchText` — блок:
MCP-имя `apply_patch` (сервер `apply`) совпало бы со встроенным и ушло бы `Edit` без пути. Проба
у всех четырёх харнессов включает MCP-мутацию. Стенд Фазы 11 видел PreToolUse Codex только на
оболочке, а стенд #188 — и на MCP, и на `apply_patch`, и на вложенных вызовах code mode
(`harnesses/__fixtures__/codex-0.163.0-stand.json`). Нормализатор Codex отображает имя
`mcp__…` в операцию `mcp` раньше сверки с `toolMap`, и вердикт даёт политика контура —
`mcp-not-allowed`, как у остальных, а не `unknown-tool`. Всё же у Codex барьер держит меньше,
чем у остальных, и старт говорит это строкой `⚠` рядом с «проба пройдена»
(`CODEX_GUARD_LIMIT`). Патч `apply_patch` с #232 судится событием нормализатора Codex
(`guardInput: 'event'` пакета), и проба старта подаёт патч данных контура с контекстом петли —
блок кодом `contour-data` — и разрешённый патч парой; `apply_patch` в команде оболочки без
литерального тела (`cat p | apply_patch`) — отказ, путей в тексте нет. Ввод в процесс
`write_stdin` хук не зовёт вовсе, и канал не судится, а выключен (ниже). Серверы MCP закрыты
не хуком, а своим домом сессии без серверов (#195) и `--ignore-user-config` — с флагом Codex не читает доверие проекту из конфига дома
(записывает его и под флагом), и `.codex/config.toml` недоверенного дерева Codex 0.163 не грузит
(стенд: сервер, дописанный в проектный конфиг, без флага стартует, с флагом нет). Флаг сторожит тест `buildCodexArgs`.

**Канал мимо хука у Codex выключается, а не объявляется пределом** (#190). Каналов исполнения у
Codex три, и описание пакета называет каждый в `eventCoverage`: прямой вызов и вложенный из code
mode хук получает до эффекта (сам `exec` code mode — нет, но у его JavaScript нет ни `require`,
ни `process`, ни `fetch`, импорт отвергнут), а продолжение процесса (`write_stdin`) — нет вовсе.
Строка в REPL Python или Node — код, которого guard не видел, поэтому перехвата нет, а есть
отключение: `--disable unified_exec_tty` (`CODEX_DISABLE_TTY`) едет в регистрации барьера, и без
TTY stdin процесса CLI закрывает сам. Стенд под argv петли (`loopChannels` фикстуры): `tty: true`
отвергнут у оболочки, `python3 -i` и `node -i`, запрещённый ввод в живой процесс без эффекта,
разрешённый — командой `exec_command` под хуком. Обратное чтение argv (`codexGuardFromArgs`)
считает отказом и отсутствие флага, и TTY, включённый снова, — проба старта не пустит сессию с
открытым каналом. Песочницу отключением канала не считаем: кодер-сессии Codex идут с
`danger-full-access`.

**Конфиг сессии Codex собирает раннер, а не берёт у человека** (`codex-home.ts`, #195). С домом
человека сессия писала в его `config.toml` доверие к деревьям петли (и под `--ignore-user-config`)
и везла его файл хуков (стенд #188, `L-proj`, `L-home`). Теперь дом у сессии свой — каталог в
состоянии раннера (`prepareCodexSession` ядра): `config.toml` из комментария и вход человека
ссылкой; проект недоверен `-c projects=…` ключами дерева и главного репозитория worktree;
`CODEX_*` и `OPENAI_BASE_URL` раннера сессии не достаются. Перед спавном argv и env сверяет
`codexIsolationProblems` — сборщик, забытый новым путём спавна, остановил бы сессию, а не пустил
её с конфигом человека. Слои `.codex/` дерева у недоверенного проекта CLI не исполняет, и всё же
их наличие в дереве и предках — отказ (`config-layers.ts`): слой в дереве петли кто-то положил, а
следующая версия CLI могла бы его исполнить. Какие поверхности отвергать, говорит
`configSurfaces` описания, а включает отказ поле пакета `projectLayers` (дома CLI человека —
`CODEX_HOME` и `~/.codex` в предке — из отказа исключены оба); у пакетов без сборщика конфига
поле `null`, и старт называет это строкой `⚠`. Зависимости, вывод сборки и вложенные
репозитории скан не обходит: иначе крупное дерево перерастало предел и отменяло старт без
единого слоя; цена скана перед каждой сессией и предел симлинков — в докблоке модуля. Факты — раздел `sessionHome` фикстуры стенда.

**Проектный MCP Kimi Code держит недоверие каталогу, а не отказ старта** (`kimi-home.ts`, #196).
Доверенному каталогу Kimi Code 2.3.2 поднимает серверы `.mcp.json` корня git и
`.kimi-code/mcp.json`, а доверие — запись в `workspace-trust/` дома или
`KIMI_CODE_TRUST_WORKSPACE`. Поэтому окружение сессии собирает `kimiSessionEnv`: `KIMI_CODE_*`,
`KIMI_CLI_*` и `KIMI_OAUTH_HOST` раннера сняты, `KIMI_CODE_NO_AUTO_UPDATE=1` — без него CLI на
старте проверяет релиз и подменяет себя под петлёй. `mcp.json` дома — MCP раннера, пустой и
пересобранный перед каждой сессией. Перед спавном `kimiIsolationProblems` сверяет то env, что
уйдёт в CLI, и каталог доверия дома: запись там — стоп `guard-probe` с адресом, раннер её не
удаляет (её кто-то положил). Поверхностей отказа у пакета нет намеренно: `.mcp.json` — файл MCP
Claude Code, у потребителя он законен, а недоверенный каталог его не исполняет. Стенд
(`sessionHome` фикстуры Kimi Code): со сборщиком серверы не стартуют и `updates/` не появляется,
контрольный прогон с доверием переменной поднимает оба сервера, без выключателя — проверяет
релиз. Сервер, дописанный в `mcp.json` дома ПОСРЕДИ сессии, CLI поднимает на лету — это Фаза 16d3.

**Подменённый MCP-сервер ловит сверка итога, а не имя** (`mcp-trust.ts`, #198). Модуль
разбирает MCP в формате каждого CLI — `mcpServers` у Claude Code и Kimi Code, `mcp` у OpenCode
(`local` — команда массивом, `environment`; выключенный пропускается), таблицы `mcp_servers` и
`-c` у Codex — в одну форму и считает её отпечаток: команда, адрес и sha256 записи с ключами по
порядку. Разбор понимает подмножество и всё прочее бросает: непонятый сервер не становится
«серверов нет». Сервер доверенного, которого нет в итоге, — не расхождение: раннер вправе отдать
меньше. Какие файлы читать, решает ядро по сборщику; слои OpenCode называет
`opencodeSessionConfigLayers`.

Формы событий — фикстуры `__fixtures__/hook-events.json`, у каждой источник.
Kimi Code проведён адаптером `kimi-native` (#120), OpenCode — адаптером `opencode` (#121), оба
ниже; харнесс без принятого пакета реестра не стартует (`core/guard-probe.ts`).

Каталог дерева сессии хук получает строкой `export CLAUDE_PROJECT_DIR=…;` в своей команде, а
не префиксом `X=… cmd`: префикс не действует на раскрытие `${X}` в той же строке. Живая
сессия Kimi Code с префиксом исполнила `rm -rf` — путь хука раскрылся пустым, упавший хук
CLI пропустил вызов, — а проба была зелёной, потому что сама клала переменную в окружение
хука. Теперь проба не-Claude харнессов идёт без неё: её ставит только Claude Code.

**`kimi-native` — Kimi Code родным харнессом, рядом с `kimi`, а не вместо** (`kimi-native.ts`,
Фаза 16b, #120). `kimi` — Claude Code на endpoint Moonshot, и родное поведение Kimi Code через
него не проверить. Каждое решение снято с CLI 2.3.2 живьём:

- **промпт — файлом, в `-p` указатель.** Со stdin `kimi -p` промпт не читает, а в argv он не
  влезает (урок #8). Файл 580 КБ модель прочла частями до последней строки; каталог файла
  отдаётся `--add-dir`, дом CLI — нет: там ссылки на вход человека;
- **ядру отдаётся только текст ассистента** из stream-json: результаты инструментов несут
  прочитанные файлы, и `ralph.md` с образцом блока намерений дал бы второй блок;
- **`--skills-dir` повторяется на весь набор**: он ЗАМЕНЯЕТ автообнаружение, а `.claude/skills`
  CLI не ищет вовсе. Набор — `.claude/skills` дерева, каталоги дерева и `HOME`, которые CLI нашёл
  бы сам, и `skills` дома ЧЕЛОВЕКА явно: сессия идёт с домом, собранным раннером, и сам CLI искал
  бы скиллы там, где ссылки на них нет. Дерева нет (вне `main()`) — каталогов дерева нет, CWD не
  угадывается; файл промпта снимается после сессии;
- **бюджет ходов исполняет CLI** (`KIMI_LOOP_MAX_STEPS_PER_TURN` → `loop.max_steps_exceeded`),
  поэтому `turnLimit: 'required'`; фолбэк-модели у `kimi` нет;
- **дом CLI собирает раннер** (`prepareKimiNativeHome` в `core/session-settings.ts`): конфиг
  человека плюс `[[hooks]]` барьера, вход ссылками; проба — на том тексте `config.toml`, что
  ляжет в дом, перед каждой сессией. Флага файла настроек у Kimi нет, и дом человека как есть
  сессии не достаётся никогда;
- **готовность до выбора задачи включает вход и алиасы моделей**: `kimi --version`, ключи и
  таблица `[models."<алиас>"]` для `kimiNativeRuntime.model`, каждого маршрута `kimi-native` и
  `default_model`, если явной модели нет (`kimiNativeAuthProblems`, без сети). Сравнение идёт
  точной строкой после обрезки пробелов, без дублей; опечатка — отказ старта с именем алиаса.
  Протухший токен узнаёт сессия исходом `auth`;
- **исход — по строке отказа CLI в stderr** (`error: failed to run prompt: <код>: …`), коды
  закрытого списка CLI. Срок раннера Kimi ловит сам и выходит кодом 143 без сигнала —
  граница spawn приводит такой исход к сигналу, классификатор читает 129/130/143 как `timeout`;
- **срок сброса — из API лимитов, а не из строки отказа** (`kimi-usage.ts`). CLI срока не печатает,
  а запасные ожидания ядра короче 5-часового окна: упор кончался упавшей сессией. На исходе
  `api-limit` раннер читает `GET <база>/usages` — тот же источник, что у `getManagedUsage` CLI, — и
  берёт самый поздний сброс исчерпанных окон. Тем же запросом сверяется неопознанный
  `provider.api_error`: квоту CLI узнаёт и по коду ошибки, а печатает только текст, и упор с
  незнакомой формулировкой стал бы `unknown`. Упором он становится только при окне, исчерпанном
  полностью: 1 % остатка постороннего отказа не объясняет. Сброс дальше 6 часов сроком не
  считается: недели сна без проверки мягкой остановки хуже запасного пути. Адрес — константа:
  `KIMI_CODE_BASE_URL` раннер снимает с окружения сессии, и токен по нему ушёл бы на чужой адрес.
  Токен идёт в curl через stdin и только читается: refresh общий с сессиями. Любой сбой — прежний
  исход и строка `⚠` с причиной.

Песочницы, которой `docs/harness-adapters.md` требует от `kimi-native`, ещё нет: сессия идёт на
хосте. Поэтому `kimi-native` — эксперимент оператора, как OpenCode (ревью Фазы 16b): конфиг
заявляет `kimiNativeRuntime.status: "experimental"`, смена рантайма маршрутом `modelRouting` —
отказ старта (`checkExperimentalRuntimes`). Маршрут в уже статический `kimi-native` разрешён:
он меняет только модель, которую `runKimiNativeOnce` действительно передаёт флагом `-m`. У
OpenCode такого послабления нет — его запуск модель маршрута игнорирует.

Барьера скиллов у не-Claude харнессов нет, и это сказано строкой `⚠` старта
(`SKILL_BARRIER_LIMIT`). Он ищет вызов `Skill` в транскрипте, а в сессии петли без транскрипта
блокирует fail-closed. Kimi Code и плагин OpenCode транскрипта хуку не отдают, у Codex он в
формате rollout: перенесённый в их регистрацию, барьер закрывал бы правку тестов навсегда, и
кодер жёг бы итерации до брейкера. Поэтому `guardHooksOf` его не переносит, а тест на событиях
Kimi и OpenCode держит обе половины: сам хук блокирует, регистрация пропускает.

Секции `kimiNativeRuntime` и `opencodeRuntime` разбирает резолв конфига
(`runtimeSectionProblems`): незнакомый ключ и не-строка — стоп. Прежде `home: 123` молча уводил
Kimi в дом по умолчанию.

**`opencode` — экспериментальный третий харнесс, только экспериментом оператора** (`opencode.ts`,
Фаза 16b, #121). Допуск в резерв или роль — canary профиля (Фаза 17), не регистрация бинаря.
Поэтому конфиг заявляет эксперимент дословно (`opencodeRuntime.status: "experimental"`,
модель `provider/model`, один провайдер), маршрут `modelRouting` в OpenCode — отказ старта
(`checkExperimentalRuntimes`), а статус назван строкой старта и строкой каждой сессии. Решения
сняты с CLI 1.19.4 живьём:

- **промпт — на stdin**: `opencode run` без позиционного сообщения читает его оттуда (#8);
- **ядру — только события `text`**; ошибка CLI идёт событием `error` в stdout, и её строка
  добавляется к тексту, иначе диагноз падения пропал бы;
- **исход — по имени ошибки и HTTP-коду провайдера**, а не по тексту: формулировки у провайдеров
  свои и на любом языке. Срок раннера CLI сам не ловит — сигнал, `timeout`. Бюджета ходов,
  обрывающего сессию, нет — `turnLimit: 'best-effort'`, `turn-limit` не поддержан;
- **неизвестные провайдер или модель — отказ до выбора задачи** по списку `opencode models`:
  в сессии они дают «Unexpected server error» без причины;
- **ключ провайдера — у самого CLI** (вход `auth.json` или `provider.<id>.options.apiKey`):
  сессия идёт без ключей раннера в env, а список моделей отдаётся и без ключа; готовность
  зовёт CLI тем же env, что сессия (`opencodeAuthProblems`);
- **код 0 — `completed`**, даже если по пути было событие `error`: 503 и 429 CLI переживает
  повтором сам, и последняя ошибка сделала бы сделанную работу ожиданием окна;
- **барьер — плагин в `OPENCODE_CONFIG_DIR`**, настройки сессии — `OPENCODE_CONFIG`; с конфигом
  человека и дерева они больше не сливаются (#197, ниже). Собирает и пробует их раннер перед
  каждой сессией (`prepareOpencodeSession`), `--pure` в argv не ставится никогда;
- **полнота скиллов сверяется**: `.claude/skills` CLI ищет сам, но «нашёл» не значит «нашёл
  все» — `opencode debug skill` обязан назвать каждый `SKILL.md` дерева, иначе сессия не стартует.

Барьера скиллов в сессии OpenCode нет, как и у Kimi: транскрипта хуку нет (`SKILL_BARRIER_LIMIT`).

**Конфиг сессии OpenCode собирает раннер, а не сливает CLI** (`opencode-home.ts`, #197). В 16b
CLI сливал с настройками сессии глобальный конфиг человека (`<XDG_CONFIG_HOME>/opencode`),
`opencode.json(c)` и `.opencode/` дерева — плагины, инструменты, MCP, провайдеров, — а
`OPENCODE_PURE` раннера снимал плагин барьера. Теперь окружение сессии собирает
`opencodeSessionEnv`: всё `OPENCODE_*` раннера снято префиксом, `OPENCODE_DISABLE_PROJECT_CONFIG=1`
и `OPENCODE_DISABLE_AUTOUPDATE=1`, `XDG_CONFIG_HOME` — свой каталог `xdg-config` рядом с каталогом
сессии (вход `auth.json` живёт в `XDG_DATA_HOME` и остаётся тем же). Выключенный проект снимает и
корневой `AGENTS.md`, поэтому правила дерева едут `instructions` абсолютным путём — первый
найденный из `rules` описания (`AGENTS.md`, затем `CLAUDE.md`, как искал бы сам CLI); не нашлось
ни одного — строка `⚠` перед сессией, непринятый пакет — отказ. MCP раннера — `mcp: {}`.
Цена: провайдер с ключом в глобальном конфиге человека до сессии не доходит, ключ — только
входом CLI, и готовность спрашивает CLI с тем же каталогом. Перед
спавном `opencodeIsolationProblems` сверяет то env, что уйдёт в CLI: `forbiddenEnv` описания
(`OPENCODE_PURE`, `OPENCODE_CONFIG_CONTENT`, `OPENCODE_PERMISSION`) по имени, прочее окружение CLI,
выключатели и `~/.opencode` — его CLI читает без флага, и исполняемый слой там — стоп с адресом,
дом человека раннер не правит. Слои дерева CLI под выключателем не исполняет, и всё же их
наличие — отказ (`config-layers.ts`). Каталоги `.opencode/plugin(s)` и `tool(s)` — слой самим
наличием. Любой `opencode.json(c)` — и в `.opencode/`, и в корне и подкаталогах — слой только с
ключами, которые грузят или исполняют код (`jsonKeys` пакета, сняты со схемы `Config` бинаря
1.19.4: `plugin`, `mcp`, `formatter`, `lsp`, `shell`, `command`, `npm` провайдера и модели;
`experimental` исполняемого в 1.19.4 не несёт): без них это законная настройка CLI человека в
дереве потребителя. JSONC, который не разобрался, — отказ с причиной, а не «ключа нет». Каталог
сессии CLI берёт из `PWD`, а не из рабочего каталога процесса, и `chdir` раннера `PWD` не
меняет — без явного `PWD` сессия и её оболочка шли бы в каталоге запуска раннера; поэтому
сборщик ставит `PWD` дереву сессии, спавн — `cwd`, а сверка ловит расхождение. Стенд
(`sessionHome` фикстуры OpenCode): со сборщиком при `OPENCODE_PURE=1` у раннера плагин барьера
загружен и отменил вызов, слои дерева и человека не грузятся, правила дерева дошли до модели;
контроли — `OPENCODE_PURE` после сборщика (барьера нет), снятый выключатель с XDG человека
(грузятся все три слоя), `PWD` каталога запуска (сессия там) — каждый назван сверкой.

**Пакет харнесса — каталог `harnesses/<имя>/` с описанием по схеме** (`harnesses/descriptor.ts`,
Фаза 16c, #179). Описание — данные, по которым реестр принимает пакет, а генератор строит
матрицу проб (`docs/harness-contract.md`). Валидатор fail-closed: незнакомая версия схемы —
отказ без разбора остального, отсутствующее или незнакомое поле — отказ (опечатка в имени
перечня полей иначе оставила бы его пустым, то есть «незнакомых полей нет»), а `argMap` и
`allowedFields` обязаны называть только инструменты `toolMap` и только поля из перечня.
Операций две, которых в сессии петли нет совсем (#225): `agent` (порождает субагента) и
`defer` (откладывает ход — `ScheduleWakeup`, `CronCreate`). По ним `loopDeniedTools` реестра
отдаёт ядру имена для флага запуска `--disallowedTools`; пакет не принят — бросок, а не пустой
запрет. Флаг выразим у харнесса Claude Code (`claude`, `kimi`). У Codex, `kimi-native` и
OpenCode флага в argv нет: флаг, не сверенный со стендом, мог бы уронить запуск. Держит там
guard: у Kimi Code — событием нормализатора (`Agent`, `AgentSwarm` — `agent`, `CronCreate` —
`defer`, #191), у OpenCode — тоже событием нормализатора (`task` — `agent`, #192).
Пакет — часть барьера: `toolMap` решает, что guard не судит вовсе (`inert`), поэтому
`harnesses/**` правится только с ship человека (`.sourcecraft/review.yaml`,
`core/protected-paths.ts`). Предстартовая проба поймала бы перенос в `inert` лишь у
инструментов своего состава, а новый инструмент, заведённый сразу `inert`, — нет.

**Поверхности конфига объявляет описание, а защищает guard** (`protectedSurfaces`, #199).
`configSurfaces` — слои, которые preflight отвергает в дереве; `protectedSurfaces` — шире: всё, что
сессия петли не вправе писать, включая дома CLI (`CLAUDE_CONFIG_DIR`/`~/.claude`, `CODEX_HOME`,
`KIMI_CODE_HOME`, `<XDG_CONFIG_HOME>/opencode`, `OPENCODE_CONFIG_DIR`, `~/.opencode`), дом-файл
`~/.claude.json` и системные пути managed-настроек (`absolute`: `/etc/claude-code`, `/etc/codex`).
Дом из переменной не отменяет дом по умолчанию: защищены оба (раннер сам ставит `XDG_CONFIG_HOME`
сессии OpenCode, а `~/.config/opencode` человека остаётся конфигом его CLI). Слой,
который отвергает preflight, обязан быть и в защищаемых — сверяет тест реестра. Дом защищён
целиком, кроме `exempt` — истории, сессий и кэша: перечень исключений, а не защищаемых, чтобы
новый каталог конфига следующей версии CLI оказался закрыт. `protectedSurfacesOf` объединяет
перечни всех принятых пакетов: сессия одного CLI, правящая `.codex/`, меняет барьер следующей
сессии другого. Отказ механизма перехвата (упавший хук — пропуск) у Claude Code, Codex и Kimi Code
пакет называет в `guardLimit` (`HOOK_CRASH_PASSES`).

**Нормализатор пакета — исполняемая команда, а не модуль для хука** (`harnesses/protocol.ts`).
Общий хук пакет не импортирует: он отдаёт сырой вход на stdin и ждёт `{"protocol": N, "event":
ToolEvent}` (сторона хука — `.claude/hooks/adapter-event.cjs`). Сбой нормализатора — код 1 и
причина в stderr: хук читает это блоком с причиной. Версия протокола объявлена у сторон порознь,
равенство держит тест. `core/` и `.claude/hooks/` от `harnesses/` не зависят — сторожит
`tests/harness-package-deps.test.ts`. Образец пакета для проб протокола —
`tests/__fixtures__/harness-sample/`: код под `__fixtures__` каталога ядра выпал бы из скана
`core-purity`.

**Харнесс выбирает реестр, а не ветвление в ядре** (`harness-registry.ts`, Фаза 16c, #180).
До карточки выбор жил `switch` по харнессу и списком `GUARD_WIRED_HARNESSES` в
`core/guard-probe.ts`, и каждый новый CLI правил ядро. Теперь реестр сам находит
`harnesses/<имя>/` и принимает пакет только целиком: описание по схеме, `harness` описания и
кода равен имени каталога (переименованный каталог иначе подменял бы чужой пакет), команда
нормализатора лежит в пакете (иначе блок всего в сессии, а не отказ на старте), версия
интерфейса кода (`harness-package.ts`) — та, что знает реестр, и сверяется раньше формы. Пакет
объявляет версию литералом: импортированная константа совпадала бы с реестром всегда.
Отказ одного пакета остальные не роняет; пакет, в который конфиг может отправить сессию,
обязан быть принят — иначе старт отменён с причинами реестра, а отвергнутый пакет вне
маршрутов назван строкой `⚠`. Нечитаемый каталог — отказ всех, а не «пакетов нет».

Пакеты грузятся `await import()` на верхнем уровне модуля реестра: ядро синхронно. Поэтому
пакет не импортирует реестр — цикл на незавершённом `await` повесил бы загрузку, — только
`harness-package.ts`. Ядро знает пакет по интерфейсу: регистрацию барьера, прочитанную
обратно, состав пробы, matcher, форму входа, `CLAUDE_PROJECT_DIR` от CLI и исполнимость
барьера скиллов. Харнесс, в чьём формате раннер собирает настройки сессии, называет
`SESSION_SETTINGS_HARNESS` здесь же: из этих настроек строятся регистрации остальных пакетов.

Пакет Claude Code — первый. Нормализатор — в тождественной форме: имена инструментов и
полей Claude Code — те, на которых написан барьер, и перевод — раскладка по `toolMap` и
`argMap` описания; незнакомые инструмент, поле входа или конверта — `unknown` с причиной и видом
(`kind: tool | field`), по которому guard выбирает код (#186). Перечень полей — полный, иначе
строгость остановила бы петлю на первом `description`: конверт снят со схемы входа хука в
бинаре CLI 2.1.312, поля инструментов — со схем, которые CLI отдаёт модели, и с вызовов
сессий петли (`harnesses/__fixtures__/claude-code-loop.json`, помечена собранной). `Skill`
описан явно. Путь команды нормализатора guard получает от регистрации раннера, а тот — у
реестра (`normalizerPathIn`, перенесённый в каталог исполняемого ядра).
Codex и Kimi Code — пакетами с той же регистрацией, что была у моста 16b (#181): настроек
сессии эти CLI не читают, поэтому `guardRegistration` получает вторым аргументом хуки барьера в
общей форме (`guardHooksOf` ядра) и читает обратно то, что из них строится, — argv `codex exec`
и `[[hooks]]` дома Kimi Code. Предел, которого проба не видит (у Codex — `write_stdin` мимо
хука), пакет называет полем `guardLimit`, и строку `⚠` старт берёт оттуда, а не по имени. Чем
guard судит регистрацию, пакет объявляет полем `guardInput`: `event` — событием своего
нормализатора (Codex с #232, Kimi Code с #191, OpenCode с #192), `compat-16b` — совместимым
входом; у реестра сейчас его не объявляет ни один пакет.
Доказательство скилла у обоих — объявленная заглушка до Фазы 16e, в описании названа словом.
Заглушка нормализатора (так было у Kimi Code до #191) на любой вход отказывает кодом 1 с
причиной (блок неисправностью `adapter-failed`). Не `unknown`: его guard читает кодом правила
(`unknown-field`), и заглушка, подключённая без совместимого входа, засчиталась бы пробой как
держащий барьер.

**Нормализатор Kimi Code снят со стенда, а не с формы Claude Code** (#191,
`harnesses/kimi-code/event.ts`). Сырые события Kimi Code 2.3.2 сняты на стенде живых проб с
фиктивным провайдером Chat Completions (`harnesses/__fixtures__/kimi-code-2.3.2-stand.json`):
настоящий бинарь зовёт хук до эффекта на `Write`/`Edit` (путь — `path`, у `Write` ещё
`mode: append`), `Read`, `Grep` с `glob`, `Glob`, `Bash` с `cwd`, `FetchURL`, `Agent` и MCP.
Перечень инструментов и полей описания — тот, что CLI отдал модели (раздел `inventory`
фикстуры). `Bash` исполняется в своём `cwd` — и вне дерева тоже (`bash-cwd-allowed`), — поэтому
база оболочки — этот `cwd`, разрешённый от `cwd` события; совместимый вход его не видел, и
`mv ralph bak` из `.claude` судился от корня дерева. MCP-имя длиннее 64 знаков CLI обрезает с
хешем (`kimiMcpToolName` повторяет это побайтно), и граница сервера теряется: имя в 64 знака без
перевода в `mcpNames` — отказ разбора. Проба старта подаёт с контекстом петли запись данных
контура `Write`, перенос из `cwd` оболочки и разрешённую запись парой.

**Параметры MCP-вызова — операции `derived`, одним разбором у всех пакетов** (#193,
`mcpDerived` в `harnesses/event-roles.ts`). Имя инструмента об эффекте не говорит: разрешённое
чтение с путём env-файла в аргументе — то же чтение секрета. Поля путей и адресов называет
описание (`mcpArgs`): под полем пути — `write`, под полем адреса и адрес целиком — `fetch`
(до политики сети — блок), прочая строка без пробелов и ключ объекта — `read`, потому что сервер
волен назвать путь любым полем. Сквозной тест `harnesses/mcp-derived.test.ts` гоняет сырое
событие каждого CLI через его нормализатор и `decideEvent`; живые пробы `mcp-*` стенда — пока
только у Claude Code: маршрут ключа остальных CLI не проверен (#219).

**Нормализатор OpenCode судит сырое событие плагина** (#192, `harnesses/opencode/event.ts`).
Хук-команд у OpenCode нет, поэтому сырое событие — аргументы `tool.execute.before`: `input`
(`tool`, `sessionID`, `callID`) и `output.args`. Плагин барьера кладёт хуку на stdin прежнюю
форму Claude Code — её читают хуки потребителя — и рядом сырое событие полем `opencode`;
нормализатор судит только его. Перевод плагина терял `workdir` оболочки и `include` поиска, а
у GPT-моделей (`gpt-` в имени, кроме `oss` и `gpt-4`) CLI отдаёт `apply_patch{patchText}`
ВМЕСТО `write` и `edit` — единственную правку файла. События сняты на стенде живых проб с
фиктивным провайдером (`harnesses/__fixtures__/opencode-1.19.4-stand.json`): плагин зовётся до
эффекта на `apply_patch`, `write`, `edit`, `read`, `bash` с `workdir` (и вне дерева —
`bash-workdir-allowed`), `grep` с `include`, `glob`, `task`, `skill`, `webfetch` и MCP. Перечень
инструментов описания — тот, что CLI в режиме `run` отдал модели (раздел `inventory`, по
модели); `list`, `question`, `multiedit` и прочие встроенные вне него — `unknown-tool`. Патч —
общим разбором (`patch.ts`); `workdir` — база оболочки от `cwd` события; `include` и `glob` —
шаблон путей; `task` — `agent` (в петле блок до наследования барьеров); `skill` — событие
доставки инструкций (`inert`), не доказательство. MCP-имя `<сервер>_<инструмент>` границу
сервера не несёт: без перевода в `mcpNames` — `unknown-tool`, а не догадка. Проба старта подаёт
с контекстом петли патч и запись данных контура, перенос из `workdir`, субагента и разрешённые
пары; плагин в пробе получает контекст тем же окружением (`runPluginFn`, четвёртый аргумент).

OpenCode — пакетом с той же регистрацией (#213), и с ним из ядра ушли временный мост 16b и
`GUARD_WIRED_HARNESSES`: проведён харнесс, у которого есть принятый пакет, и только он. Хук-команд
у OpenCode нет — барьер плагин, и проба обязана исполнить сам плагин: он и есть разбор события,
и проба хуков в обход него увидела бы барьер, которого у сессии нет. Поэтому способ пробы пакет
объявляет полем интерфейса `plugin` (исходник из хуков барьера, обратное чтение, событие CLI), а
не ядро ветвлением по имени; `null` — хуки командой. Накрытие инструмента пакет считает по
переводу имени OpenCode в имя Claude Code — тем же, что делает плагин. Ключ рантайма `opencode`
совпадает с именем пакета, и ядро берёт его константой адаптера (`OPENCODE_RUNTIME`).

Сборщики готовой регистрации (`prepareCodexGuardArgs`, `prepareKimiNativeHome`,
`prepareOpencodeSession`) пока в ядре и пробуют её пакетом реестра; в пакеты они переезжают в
Фазе 16d. Что в `core/` нет ветвления по харнессу принятого пакета, сторожит
`tests/harness-identity.test.ts`: имя бинаря `codex` в ядре поэтому берётся из профиля
рантайма, а не литералом. Что сценарии петли канона проходят хуки пакета —
`core/guard-probe-registry.test.ts`.

**Проба доказывает правило, а не двойку** (`barrier-reason.ts`, `probe-kinds.ts`, #183). До
карточки зелёной пробой был любой код 2 любого хука, а барьер fail-closed: guard без правил
блокирует всё той же двойкой, и запрещённые пробы проходили ровно потому, что он сломан. Теперь
блок несёт последней строкой stderr код причины из закрытого перечня контракта
(`docs/harness-contract.md`, «Коды причины»): у запрещённой пробы харнесса (`HarnessProbe`) — код,
которым её обязан назвать барьер, и стартовая проба засчитывает только его; код неисправности,
строка без кода и незнакомый код — «не правилом». Хуки — CommonJS без зависимостей: формат строки
и коды у них литералами, равенство с перечнем держит `barrier-reason.test.ts`. Коды `reserved`
судья матрицы уже ждёт, а выпускать их начнёт guard на событии (#186).

Живая проба — свой судья с пятью видами (правило, регистрация, отключённый канал, preflight,
песочница) и своим набором свидетельств у каждого; проба правила без попытки вызова настоящим CLI
— «не доказано», и стартовая проба этим судьёй не доказывается по построению: она исполняет хуки
на синтетическом входе, без CLI и без эффекта (`core/guard-probe-boundary.test.ts`). Матрицу живых
проб строит генератор из описания (`harnesses/probe-matrix.ts`): поля — из `argMap`, у каждой
отрицательной пара, нехватка роли в описании — проблема матрицы, а не поле по догадке.
