# Живые canary матрицы защиты lock

**Задача 106**, Фаза 14 плана (`docs/roadmap/plan.md`). Статический тест политики
(`tests/protection-policy.test.ts`, задача 49) сверяет файл политики с нашим представлением о
площадке. Canary сверяет саму площадку: маска, которую площадка разворачивает не так, как мы
думали, или сброс одобрения, которого на ней нет, проходят статический тест зелёными. Ровно на
таком расхождении барьер и испаряется молча.

## Почему матрицу гоняет человек, а не петля

Каждый исход — живой PR на площадке, а исход 2 ещё и одобрение человека. Сессии петли не
создают PR и не ходят в форж (`ralph.md`), а одобрить PR им нечем намеренно: аккаунт один, и
одобрение агентом сняло бы требование ship человека (`.claude/ralph/hooks.json`, заметка о
`SetDecision`). Поэтому петля готовит процедуру и место под результат, а прогон — за человеком.

## Матрица

Три исхода на каждой площадке. Третий весит не меньше первых двух: перетянутая политика
остановит петлю на каждом PR, и это та же поломка, только громкая.

| #   | Исход                                      | Что в canary-PR                                     | Ожидание                                     |
| --- | ------------------------------------------ | --------------------------------------------------- | -------------------------------------------- |
| 1   | правка lock без одобрения не мерджится     | одна строка в `.ralph/core.lock`                    | мердж отказан, требуется ревьюер из политики |
| 2   | одобрение не переживает следующий push     | PR из исхода 1, одобрен человеком, затем ещё коммит | одобрение сброшено, мердж снова отказан      |
| 3   | обычный доменный PR мерджится без человека | правка вне защищаемых путей (например, `README.md`) | мердж проходит без одобрения                 |

Где проверяется — на демо-потребителе обеих площадок, а не на продовом (решение человека на
прогоне 27.10.2026: canary-PR в продовом потребителе оставил бы след в его истории):

Имена и ссылки полигонов, номера canary-PR и их состояние — в карточке #106, а не здесь:
канон публичный и называет потребителей только абстрактно (`your-org/ralph-demo`, как в
`docs/demo.md`), а состояние чужого репозитория в дереве канона быстро стало бы неправдой.

- **SourceCraft** — демо-потребитель `your-org/ralph-demo`, правило ревью `.sourcecraft/review.yaml`: `need_ships: 0` глобально, `need_ships: 1` на
  `.ralph/**`, `ralph`, `.sourcecraft/**`.
- **GitHub** — публичное зеркало того же демо (на бесплатном плане ruleset в приватном репозитории не действует). CODEOWNERS на
  `/.ralph/`, `/ralph`, `/.github/`, `/.sourcecraft/`; ruleset `lock-protection` на основной
  ветке — `pull_request` с `require_code_owner_review` и `dismiss_stale_reviews_on_push`, без
  bypass actors. Для исхода 2 сброс устаревших одобрений обязателен: без него GitHub одобрение
  сохраняет.

## Как прогнать

1. Ветка `canary/lock-<площадка>-<исход>` от свежей основной ветки потребителя.
2. Для исходов 1–2 — правка `.ralph/core.lock` (значение не важно: canary не мерджится).
   Для исхода 3 — безобидная правка вне защищаемых путей.
3. PR. Попытка мерджа тем же путём, которым мерджит раннер, — отказ или успех и есть
   результат; текст отказа площадки записать дословно.
4. Исход 2: человек одобряет PR из исхода 1, в ветку уходит ещё один коммит, попытка мерджа
   повторяется.
5. PR исходов 1–2 закрыть без мерджа; PR исхода 3 смерджить или откатить по вкусу полигона.
6. Ссылки и наблюдения — в таблицу ниже.

## Расхождения площадок

**Одобрение по путям есть только на SourceCraft.** Там правило ревью задаёт число ship на
маску путей: lock защищён, доменный PR идёт без человека — исходы 1 и 3 держатся одной
политикой. GitHub ruleset так не умеет: `require_code_owner_review` работает только вместе с
порогом одобрений ≥ 1, а порог действует на ВСЕ PR ветки. Выбор на GitHub — между двумя
поломками: порог 0 — lock не защищён (исход 1 красный, canary-PR смерджен), порог 1 — каждый
доменный PR ждёт человека (исход 3 красный, доменный PR стоит) и петля встаёт на каждом PR.
Совместить исходы 1 и 3 одним ruleset на GitHub нельзя.

**Решение человека 27.10.2026: на GitHub защита — в раннере, площадка не страхует.** Один
аккаунт, порог ruleset 0, без отдельного чека по путям. Перед мерджем PR фазы гейт раннера
сверяет его файлы с защищаемыми путями (`core/protected-paths.ts`, тот же список, что у
статического теста политики) и на пересечении встаёт с причиной «правка защищаемого пути —
мердж за человеком» и списком файлов; не получил список файлов — тоже стоп (задача 139).
Площадку раннер узнаёт по шву форжа (`reviewProtectsPaths`): SourceCraft пути держит сам, и
там сверки нет.

**Оговорка — прямо.** Это защита мердж-пути раннера, а не репозитория. PR, смердженный мимо
раннера — руками в интерфейсе, `gh pr merge`, другим агентом с тем же токеном, — площадка на
GitHub пропустит при пороге 0, как пропустила canary-PR исхода 1. Исход 1 на GitHub держится
только для мерджа раннером; для всего остального площадка не страхует.

**Bypass на GitHub закрыт.** `GET rulesets/{id}` при пустом `bypass_actors` отдаёт
`current_user_can_bypass: never`: токен владельца репозитория — им же ходит раннер — ruleset
не обходит. Подсказка `gh pr merge` про `--admin` общая и признаком обхода не является.

**Исход 2 на GitHub не доказан.** `dismiss_stale_reviews_on_push` в ruleset стоит, но живой
сброс одобрения не наблюдался: одобрить нечем, пока аккаунт один (задача 50). Статический тест
политики видит настройку, площадка её не подтвердила — ровно то расхождение, ради которого
canary существует.

**Побочка прогона.** Canary-PR исхода 1 при пороге 0 смерджен, и правка lock осталась в
основной ветке GitHub-полигона. Вернуть её можно только PR с одобрением второго аккаунта (при
пороге 1 своё одобрение автору недоступно); значение и состояние — в карточке #106.

## Итог фазы 14 на GitHub

**Критерий готовности фазы на GitHub не выполнен**, и сдавать фазу таким итогом нельзя. План
требует: canary-PR с lock без одобрения не мерджится ни на одной площадке. На GitHub исходы 1
и 3 одним ruleset несовместимы, исход 2 не прогнан. SourceCraft держит все три исхода.

**Конфигурация, в которой полигон оставлен, прогоном не записана.** Таблица показывает обе
пробы порога, но не то, какое значение `required_approving_review_count` стоит на полигоне
после прогона. Снять его (`GET rulesets/{id}`) и записать сюда — часть карточки решения ниже;
до записи считать полигон в неизвестной конфигурации, а не в защищённой.

Обе карточки заведены из ревью PR фазы 14; номера — в трекере по заголовкам.

- **«GitHub: защита lock при пороге 0»** — механизм решён человеком 27.10: защита в гейте
  раннера (задача 139, выше). Остаётся запись итогового состояния ruleset полигона.
- **«Статический сверщик GitHub-пары политики защиты»** — закрыт без сверщика решением
  человека 27.10. На GitHub защищаемые пути держит гейт мерджа раннера (задача 139, выше), а
  не ruleset: ruleset по путям защищать не умеет, и статическая сверка файлов, которые ничего
  не защищают, барьером не была бы. `tests/protection-policy.ts` сверяет только SourceCraft —
  намеренно; файлы GitHub-пары по-прежнему защищены политикой SourceCraft.
