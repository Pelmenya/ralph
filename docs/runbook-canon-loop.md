# RUNBOOK: петля на каноне

Порядок оператора для петли, которая работает над самим каноном. Общий порядок разбора
стопов живёт отдельно (он ещё не вынесен из копии потребителя, см. `docs/convergence.md`,
строка `RUNBOOK.md`); здесь — только то, что отличает канон от обычного потребителя.

Пути ниже — форма, а не адреса: `<канон>` — дерево человека с клоном канона,
`<канон>-ralph` — дерево-сосед, где идут сессии, `<установки>` — каталог установленных
ревизий ядра, `<состояние>` — каталог состояния экземпляра.

## Раскладка

Канон здесь в двух ролях сразу, и роли разведены по разным каталогам:

| Корень          | Каталог                 | Роль                                                              |
| --------------- | ----------------------- | ----------------------------------------------------------------- |
| `consumerRoot`  | `<канон>`               | потребитель: дерево человека, его локальный конфиг                |
| `executionRoot` | `<канон>-ralph`         | дерево работы: ветки фаз, сессии, гейт                            |
| `productRoot`   | `<установки>/<ревизия>` | ядро, которое ИСПОЛНЯЕТСЯ: клон канона на зафиксированной ревизии |
| `runtimeDir`    | `<состояние>`           | state, лок, лог, сессии — вне всех деревьев                       |

Почему продукт — отдельный клон. `core/roots.ts` запрещает совпадение `productRoot` с
`consumerRoot` и с `executionRoot`: иначе петля исполняла бы ровно тот код, который сама
правит, и незаконченная правка ветки фазы меняла бы поведение раннера посреди прогона.
Отдельная установка — та же раскладка, что у внешней установки Фаз 12–13, только руками.

Файлы потребителя:

- `<канон>/.claude/ralph/ralph.config.json` — локальный, под `.gitignore`: в нём
  абсолютные корни этой машины. Раннер читает его из дерева человека при старте.
- `.claude/ralph/ralph.project.md` — в git: сессии идут в дереве работы, куда
  игнорируемый файл не попал бы. Описывает канон, следа потребителя в нём нет.
- Промпт конфига обязан называть `ralph.md`: по этому упоминанию в первом сообщении
  барьер скиллов (`.claude/hooks/skill-barrier.cjs`) узнаёт сессию петли.

## Установка ревизии

```bash
rev=$(git -C <канон> rev-parse --short origin/main)
git clone --no-checkout <канон> <установки>/$rev
git -C <установки>/$rev checkout --detach $rev
```

Затем `roots.productRoot` в конфиге — на `<установки>/$rev`. Зависимостей у ядра в
рантайме нет, `npm ci` в установке не нужен. Установку не правят: правка ядра идёт PR
в канон и приезжает следующей ревизией.

**Смена ревизии — рестарт на границе итерации.** Дождаться закрытия карточки, погасить
петлю, поставить новую ревизию, перевести `productRoot`, поднять. Прежнюю установку
не удалять, пока новая не прошла хотя бы одну итерацию: откат — вернуть `productRoot`
и рестартовать.

## Запуск

Из дерева человека, с секретами форжа и модели в окружении (через свою обёртку —
guard сессии вахты режет команды с именем env-файла):

```bash
cd <канон>
node <установки>/<ревизия>/ralph.js --dry-run        # read-only, лок не берёт
node <установки>/<ревизия>/ralph.js --profile prod   # боевой прогон
```

Зелёный dry-run — это строка `Проба барьера пройдена` и план первой итерации без
отказов конфига. Проба (`core/guard-probe.ts`) подаёт хукам дерева работы запрещённые
вызовы; не заблокировано — петля не стартует.

`RALPH_TRACE_DENY` в окружении раннера обязателен: без словаря скан следов в гейте идёт
только по структурным классам, а петля пишет коммиты в публичный репозиторий.

## Переключение очереди между репозиториями

На машине одна петля за раз: и ради нагрузки (гейт каждой гонит полный сьют), и ради
недельного лимита модели. Второй writer на ТОТ ЖЕ репозиторий раннер отвергает сам
(реестр владения по каноническому origin, `core/repo-owner.ts`); две петли на РАЗНЫХ
репозиториях он не запрещает — это правило оператора.

1. Петля A: дождаться закрытия текущей карточки, погасить на границе итерации — тогда
   работа закоммичена, и state переживает рестарт.
2. Убедиться, что владение снято: в реестре владения нет записи A (или её pid мёртв).
3. Если очередь A ещё нужна — ничего не сбрасывать: state A останется в её `runtimeDir`
   и продолжит фазу при следующем старте.
4. Поднять петлю B: сначала `--dry-run`, затем боевой прогон.
5. Возврат на A — тот же порядок в обратную сторону.

Очередь фаз каждой петли — `phases` её конфига; смена порядка фаз — правка конфига и
рестарт, мерджа для этого мало: конфиг читается один раз при старте.
