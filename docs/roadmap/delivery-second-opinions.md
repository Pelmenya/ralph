## Codex, gpt-6-astra, усилие high

**Рекомендую (а): внешнее хранилище неизменяемых ревизий, закреплённых lock-файлом потребителя.** Единица обновления — ядро вместе с контрактом запуска и подключением защитных хуков.

Уточнение по коду: четыре корня обнаружены в каноне. В копии SourceCraft-монорепо остаются относительные константы путей, а конфиг читается до `chdir` в `main()`. Поэтому готовность копии к внешней установке пока не подтверждена. Ниже — предлагаемая схема, а не описание уже реализованного launcher.

**1. Почему (а) подходит фактам 1–7**

Внешний `productRoot` не переключается вместе с linked worktree потребителя. Процесс и дочерние инструменты используют одну ревизию до остановки; обновление начинает действовать после рестарта. `runtimeDir` существует независимо от устанавливаемых версий.

Коммит потребителя закрепляет SHA канона, digest и версии контрактов. Источником установки служит Git, обязательного npm-publish нет. Пути машины вычисляются launcher локально; проектные правила остаются у потребителя.

Гейт ядра переезжает в канон, потребитель проверяет подключение. Это соответствует [ограничениям PRD], но требует отдельной миграции нынешнего гейта.

Важная оговорка к аргументу PRD: внешний каталог тоже можно исправить руками. От расхождения защищают проверка содержимого и запрет записи, а не расположение каталога.

**2. Работа, хуки, гейты и переключение**

Launcher читает закоммиченный lock и относительный путь конфига из `consumerRoot` один раз. Фиксирует для запуска:

- коммит потребителя и SHA ядра;
- абсолютные четыре корня;
- digest конфигурации и защитной политики.

После этого `executionRoot` может переключаться между `origin/main` и PR. Lock из PR **не переключает работающий раннер**. Монитор, промпты и хуки разрешаются через закреплённый `productRoot`, без общего изменяемого симлинка `current`.

В потребителе остаются `.claude/settings.json`, тонкие адаптеры хуков и проектные правила. Общий механизм защиты поставляется с ядром. Manifest ядра задаёт допустимые адаптеры и схему правил; идентичность связки определяется SHA ядра и коммитом потребителя.

Перед каждой агентной сессией, включая сессию после checkout, нужны проверка эффективных настроек, соответствия manifest и отрицательная проба: заведомо запрещённое безопасное действие действительно блокируется. Настройки и исполняемые компоненты защиты должны быть недоступны сессии для записи средствами изоляции ОС. Один `chmod` при том же владельце такой гарантии не даёт.

Сейчас есть конкретная ловушка: [skill-barrier] узнаёт петлю по `.claude/ralph/ralph.md`, а неопознанную сессию пропускает. Этот признак нужно заменить явным контрактом запуска. Проверка [guard-wiring] проверяет файлы тестом, но не доказывает фактическую активацию CLI-хуков. Падение самого хука также должно блокировать действие: актуальная документация Claude описывает `onFailure: "block"`, поддержку установленной версией надо проверить. [Документация хуков](https://code.claude.com/docs/en/hooks#block-the-action-when-a-hook-fails).

**Гейт канона:** тесты ядра, типизация, сценарии восстановления, совместимость контрактов, установка/откат, отсутствие потребительских имён и машинных путей. Результат привязан к точному SHA.

**Гейт потребителя:** происхождение SHA и digest, совместимость контракта, проводка хуков, короткие интеграционные сценарии плюс обычные проверки проекта. Проверяющий код берётся из доверенной базовой ревизии/образа, а lock PR читается как данные. Доверенной строки `npm run …` недостаточно, если реализацию команды подменяет PR.

Зону [храповика `.claude/ralph`], Vitest и typecheck меняют явной миграцией после появления заменяющих проверок.

**Update:** подготовить ревизию во временном каталоге → проверить → атомарно опубликовать каталог `<sha>` → подготовить отдельный коммит/PR потребителя с lock и изменениями контракта. Дерево человека остаётся чистым.

Активация после принятия коммита: остановиться на подтверждённой границе, дождаться завершения дочерних процессов, взять эксклюзивную блокировку экземпляра, проверить чистоту деревьев и совместимость state, запустить новую ревизию. Подготовка обновления не меняет работающую петлю.

**Rollback:** новый коммит возвращает прежнюю связку lock/контракт/адаптеры, затем тот же протокол активации. State сохраняется текущий. В v1 допускаются только обновления с проверенной обратной совместимостью state. Восстанавливать старый state после уже выполненных внешних действий нельзя: это создаёт повторные действия.

Git-коммит и рестарт процесса не образуют одной атомарной операции. Нужен журнал активации: после сбоя launcher однозначно продолжает переключение либо оставляет прежнюю версию, блокируя неоднозначный запуск.

**3. Отказы и механические барьеры**

| Отказ                                                | Чем ловится                                                                                     |
| ---------------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| Оборванная загрузка, неполная установка              | Временный каталог, проверка полного manifest, атомарное переименование                          |
| Каталог `<sha>` вручную изменён                      | Digest перед запуском; запрет записи для CLI и CI                                               |
| PR поменял одновременно SHA и checksum               | Проверка разрешённого канона и результата его гейта; checksum сам по себе не доказывает доверие |
| Checkout принёс несовместимые хуки                   | Проверка связки перед каждой сессией; запуск запрещён при несовпадении                          |
| Хук выключен настройками, падает или не узнаёт петлю | Проверка эффективных настроек, отрицательная проба, блокировка при ошибке                       |
| Два update/start одновременно                        | Общая блокировка экземпляра и журнал переключения                                               |
| Старая версия не понимает новый state                | Проверка версии до запуска; несовместимый downgrade отвергается                                 |
| Канон недоступен ночью                               | Проверенный локальный кеш; при отсутствии нужной ревизии — остановка, без fallback на `latest`  |
| Удаление старой версии ломает работающий монитор     | В v1 нет автоматической очистки установленных ревизий                                           |

**4. Почему не остальные**

- **Вендоринг:** обеспечивает автономный checkout, но возвращает редактируемую копию ядра в каждый проект. Самопроверка из PR обходится одновременной правкой ядра, digest и проверяющего скрипта; нужен тот же внешний источник доверия.
- **Subtree:** локальная правка и разрешение конфликта могут создать дерево, которого нет ни в одной ревизии канона. Для запрета расхождения всё равно понадобится manifest — фактически получится вендоринг с дополнительной Git-хореографией.
- **Worktree канона:** допустим как внутренний способ наполнить кеш варианта (а), но добавляет зависимость от общего Git-каталога и его обслуживания. Для исполнения достаточно проверенного экспортированного дерева.
- **npm из Git:** нативный запуск `.ts` внутри `node_modules` ограничен Node; потребуется дополнительный загрузчик, сборка или экспорт наружу. [Документация Node 24](https://nodejs.org/docs/latest-v24.x/api/typescript.html#type-stripping-in-dependencies).
- **Контейнер:** digest закрепляет поставку, но добавляет согласование путей worktree, CLI-авторизации и владельцев файлов. Сам по себе активацию потребительских хуков не решает.
- **Сабмодуль:** отвергнутый вами обход защиты через gitlink остаётся достаточной причиной отказа.

**5. Минимальный launcher v1**

`install`, `doctor`, `start`, `stop`, `update`, `rollback`: проверяемая установка точного SHA; разрешение корней; диагностика совместимости и хуков; блокировка экземпляра; закрепление ревизии запуска; подготовка коммита обновления; остановка и восстановление незавершённой активации. Без автообновлений, очистки кеша и произвольных миграций state.

**6. Что проверить до решения**

Не проверены экспериментом внешняя раскладка канона, все дочерние пути и эффективные настройки CLI. Нужен небольшой стенд: запуск из внешнего каталога; переключение worktree на PR с изменёнными settings; блокировка обоими хуками; падение установки и активации на каждой границе; откат после реальных внешних действий; запуск без сети. Отдельно — эквивалентность защиты в Codex/Kimi: наличие Claude-хуков её не гарантирует.

## Рекомендация: вариант (а), внешнее ядро по SHA

В репозитории потребителя остаются `.ralph/ralph.lock`, проектный конфиг/контракт и launcher; ядро устанавливается в `~/.local/share/ralph/<sha>/`. Это лучше всего разделяет уже существующие корни: `consumerRoot` и `executionRoot` принадлежат git-потребителю, `productRoot` — неизменяемой ревизии канона, `runtimeDir` переживает смену ядра.

Причины именно для этой эксплуатации:

- Linked worktree продолжает переключаться между `origin/main` и PR без какой-либо доставки ядра внутрь него.
- Lock фиксирует ревизию в обычном коммите, без gitlink и его обхода маски `.claude/ralph/**`.
- Исчезает рабочая копия ядра, которую кодер может незаметно поправить вместе с проектом.
- Тесты ядра уезжают из CI потребителя в канон; там же остаются их храповики.
- Не нужен npm publish.
- Канон содержит только переносимый код; проектные правила остаются контрактом потребителя.

Проверка показала уточнение к постановке: четыре корня действительно есть в каноне (`core/config-profile.ts:483`), но в копии SourceCraft-монорепо их поиск не находит; её `main()` ещё использует старые пути (`core/orchestrator.ts:164`, `:6630` той копии).

## Работа петли, хуки и гейты

Launcher запускается из дерева человека, читает lock и конфиг там, проверяет установленное дерево и передаёт ядру абсолютные корни. Далее ядро по-прежнему создаёт/обновляет соседний linked worktree и делает `chdir` туда. Путь к ядру от этого не меняется, а `runtimeDir` остаётся абсолютным и не переезжает при detach. В каноне именно так уже решаются state и lock до `chdir` (`core/orchestrator.ts:6890`, `:7025`).

**Хуки.** Нельзя просто оставить вызов `${CLAUDE_PROJECT_DIR}/.claude/hooks/...`: тогда PR способен заменить или отключить защиту, а её ревизия не обязана совпадать с ядром. Сейчас `settings.json` действительно вызывает guard и skill-barrier из дерева (`.claude/settings.json:81` потребителя).

Предлагаю:

- исполнение guard и обёртки хуков перенести в канон;
- проектные правила skill-barrier оставить данными контракта: текущий файл содержит специфичные пути и навыки (`skill-barrier.cjs:46`), поэтому целиком он непереносим;
- launcher формирует в `runtimeDir` итоговый settings из доверенного конфига дерева человека и абсолютных путей `<sha>/hooks/...`;
- ядро передаёт этот settings каждой агентной сессии явно, а не полагается на settings из PR;
- hook сверяет ожидаемый SHA из окружения с собственным canonical path; несовпадение, недоступность или ошибка загрузки — exit 2;
- preflight включает отрицательный canary: запрещённый вызов действительно блокируется. Без него отсутствие хука может остаться молчаливым.

**Гейт канона:** все тесты ядра и хуков, отсутствие следов потребителей, совместимость конфига/state/launcher, сценарии install/update/rollback, прерывание установки, linked-worktree и отрицательные hook-canary.

**Гейт потребителя:** только свои проверки плюс схема lock, существование SHA в разрешённой линии канона, контрольная сумма установленного дерева, совместимость версий и `doctor`. Тесты ядра и их храповик оттуда удаляются. Политика берётся из доверенного `main`, а не из PR.

## Update, rollback и работающая петля

Lock содержит как минимум `canonicalUrl`, полный `sha`, `treeHash`, версии формата и совместимости. Хэш считается по канонически отсортированному списку «путь, тип/mode, содержимое», а не по tar-архиву с метаданными.

`update <sha>`:

1. Проверяет отсутствие живой петли по lock в `runtimeDir` и чистоту дерева человека.
2. Скачивает точный SHA во временный каталог на той же ФС.
3. Проверяет HEAD и хэш дерева, совместимость и preflight.
4. Атомарно переименовывает каталог в `<sha>`; существующий не перезаписывает.
5. Меняет только `.ralph/ralph.lock` и создаёт отдельный lock-only коммит. При ошибке восстанавливает прежний lock; `runtimeDir` не трогается.

`rollback` выполняет тот же протокол к предыдущему зафиксированному SHA. Старые ревизии не удаляются автоматически. Откат при несовместимой уже мигрированной схеме state запрещается, а не «откатывает» данные вслепую.

Работающая петля не переключается на лету: update при живом lock отклоняется. Текущий процесс продолжает старую ревизию; новая вступает в силу только после остановки и повторного `start`. Это соответствует однократной загрузке кода и конфига.

## Режимы отказа и механические барьеры

1. **Обрыв скачивания/диск заполнен:** временный каталог и атомарный rename; старая ревизия остаётся выбранной.
2. **Локальная правка кеша:** полный tree-hash при `doctor` и каждом `start`; несовпадение — отказ. Прав «read-only» недостаточно.
3. **SHA отсутствует или подменён remote:** fetch только точного SHA, сверка дерева; никакого fallback на `main`/latest.
4. **Несовместимы launcher, ядро, конфиг, state или Node:** обязательные версии в manifest и fail-closed preflight до переключения.
5. **Update во время петли:** блокировка по живому процессу в `runtimeDir`; никаких подмен каталога под работающим Node.
6. **PR меняет lock/settings/hooks:** запуск использует lock и объединённый settings дерева человека, явную передачу settings и hook-canary; CI проверяет lock независимо.
7. **Откат после миграции state:** журнал и версии схемы; запрет запуска/отката при незавершённой или необратимой миграции.
8. **Повреждение или подмена через symlink:** проверка `realpath`, владельца и типов файлов до исполнения; хэш после установки.

## Почему не остальные

- **(б) Вендоринг:** сохраняет именно источник нынешних 132 расхождений — редактируемые файлы в PR. Контрольная сумма обнаружит правку позднее, а CI потребителя продолжит тащить тесты чужого ядра.
- **(в) Subtree:** 72 локальных коммита превращают update в merge-операцию с конфликтами; rollback тоже становится историей потребителя, а не выбором целой ревизии. Ручная правка по-прежнему физически доступна.
- **Submodule:** известный gitlink-барьер плюс отдельная инициализация/очистка в каждом linked worktree.
- **Worktree канона:** не даёт сам по себе транзакционности: checkout может быть грязным или переключённым, `git worktree prune` способен удалить нужную ревизию. Опять появляется вторая git-хореография.
- **npm из git-URL:** добавляет dependency/lifecycle-семантику там, где нужен точный read-only снимок; кроме того, текущий consumer settings прямо запрещает `npm install *git+*`.
- **Контейнер:** не решает регистрацию хуков в host CLI и усложняет пути к worktree/state; выигрыша над нативным Node 24 нет.

## Минимальный launcher v1

`install`, `update <sha>`, `rollback [sha]`, `doctor`, `start`, `stop`; чтение/запись lock, lock-only коммиты, атомарный кеш, проверки SHA/hash/версий, абсолютные четыре корня, генерация settings и canary, сохранение state и предыдущей ревизии. Без автообновления, npm publish, garbage collection и переключения живой петли.

## Что проверить экспериментом до решения

1. Поддерживают ли все три CLI явный внешний settings, каковы приоритеты и не отключает ли его `bypassPermissions`.
2. Реально ли exit 2 внешнего hook блокирует инструмент в linked worktree у Claude, Codex и Kimi; Codex может потребовать другого механизма — это пока не проверено.
3. Можно ли объединить consumer settings и канонические хуки без потери остальных lifecycle-хуков.
4. Прерывание на каждом шаге update/rollback: после fetch, rename, изменения lock и коммита.
5. Два последовательных запуска со сменой SHA: state продолжается, worktree остаётся чистым, старый процесс никогда не видит новое ядро.
6. Установка в CI без сети: нужен ли обязательный локальный кеш канона.

Если пункты 1–3 не подтвердятся, внешнее ядро останется предпочтительным, но схему активации хуков нельзя считать решённой.
