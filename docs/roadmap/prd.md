# PRD: Ralph после хакатона — надёжная петля и отдельный продукт

**Дата**: 2026-10-26
**Статус**: Draft

Источники: исследование `docs/research/architecture-2026-10.md` (риски R1–R15), целевой контракт
харнессов `docs/harness-adapters.md`, исходный PRD выноса раннера (ступени R0/R1/R2,
август 2026, лежит в дереве проекта-источника оснастки), 46 открытых карточек
`pelmenya/ralph`, раннерные карточки SourceCraft-монорепо,
эксплуатация петли 15.09–20.10 и открытые материалы Михаила Шогина, который держит
похожий агентный конвейер в проде на открытых корпоративных моделях (блог и GitHub —
раздел «Внешние источники» в конце).

## Цель

Две цели, в этом порядке:

1. **Петля, которой можно доверять ночью.** Ни один рестарт, обрыв API или падение сессии
   не превращается ни в мердж без доказательства, ни в молчаливый стоп. Сегодня эти
   окна есть, и одно уже стреляло в проде (инцидент 16.10: ревью упало, мердж прошёл).
2. **Ralph — отдельный продукт.** Один канонический репозиторий `pelmenya/ralph`, из которого
   любой проект подключает петлю без форка и ручных копий, обновляется и откатывается
   одной командой, и в котором дефект ядра чинится один раз.

Масштабирование (несколько петель, взаимозаменяемые харнессы) — третья цель, и она
опирается на первые две: без надёжной одиночной петли и единого канона его строить
не на чем.

## Почему сейчас

- **Канон отстал на два месяца.** Последний коммит `pelmenya/ralph` — 25.08. Копия ядра
  в SourceCraft-монорепо с тех пор получила 72 коммита и расходится с каноном в 132 файлах.
  Любая правка ядра сегодня делается в одной копии и теряется для другой.
- **Найденные дыры безопасности мерджа подтверждены кодом:**
    - на пути восстановления `blocked` выставляется без проверки после записи
      (`orchestrator.ts:5328–5341`);
    - state пишется неатомарно, а повреждённый файл читается как отсутствующий
      (`state-lock.ts:153–162`, `exec.ts:48–54`);
    - ревью, вышедшее с кодом 0 без вердикта, засчитывается чистым (инцидент 16.10).
- **Доставка сабмодулем не годится.** Сабмодуль был кандидатом (исходный PRD прямо
  допускал «отрицательный результат spike — законный повод сменить механизм»). По опыту
  практиков он плохо работает и не приветствуется. Плюс у нас уже есть доказанный
  отказ: gitlink не ловится маской `.claude/ralph/**` (карточка `ralph#49`), то есть
  барьер защиты исчезает молча. Механизм доставки выбирается заново.

## Пользовательские сценарии

### Оператор петли (один человек, ночные прогоны)

- Петлю убили посреди любого шага → после рестарта она продолжает с последней
  подтверждённой точки, а в Telegram приходит строка о том, что именно было прервано.
  Слепого повтора уже выполненного внешнего действия нет.
- Сессия ревью упала, вышла без вердикта или ответила ошибкой прокси моделей → мердж
  не происходит, в уведомлении названа причина, а сбой провайдера повторяется
  с паузой и не тратит итерацию брейкера.
- Запись `blocked` на PR не подтвердилась → мердж удерживается, а не проходит.
- Файл state повреждён → петля не стартует с нуля, а останавливается с диагнозом
  «state повреждён» и сохраняет испорченный файл для разбора.
- Внешний CI не завёлся (воркер занят, площадка молчит) → поведение задано политикой
  проекта (`required`/`optional`/`disabled`), а не двухминутным таймаутом.
- Лимит ключа подписки исчерпан → петля переходит на следующий ключ из списка
  и ждёт только тогда, когда упёрлись все.
- Оператор открывает сводку → видит долю задач, доведённых до мерджа в отведённое
  время, и разбивку потерь по причинам.

### Владелец проекта-потребителя

- Подключает Ralph к новому проекту одной командой → получает launcher, минимальный
  контракт проекта и зелёный preflight/dry-run без ручной работы с git, SHA
  и внутренними файлами ядра.
- Обновляет или откатывает Ralph командой launcher → проект переходит на точную
  проверенную ревизию, state петли не теряется, рабочее дерево остаётся чистым.
- Работает на GitHub или SourceCraft → один и тот же цикл, разница только в адаптере.

### Мейнтейнер Ralph

- Чинит дефект ядра в `pelmenya/ralph` один раз → оба референсных потребителя
  (SourceCraft-монорепо с продом и GitHub-полигон с деплоем) получают его обновлением,
  без ручного переноса.
- Добавляет новый кодер-рантайм → он допускается в роль только после canary на этой
  роли, включая отрицательный сценарий (запрещённое действие остановлено).

## В скоупе

Скоуп разложен на ступени. Ступень — ворота приёмки, внутри неё работа режется
на вехи по ≤ 5 карточек. Подробности и соответствие карточкам — `roadmap.md`.

### S0. Единый канон

- Сведение копии SourceCraft-монорепо и `pelmenya/ralph`: каждое из расхождений классифицировано
  (принять / отвергнуть / уже в другой форме), с исходными SHA обеих сторон.
- Ревизия 46 открытых карточек `pelmenya/ralph` против сведённого кода: что уже закрыто
  в копии SourceCraft-монорепо, что протухло, что живо. Живые раскладываются по ступеням S1–S4.
- С этого момента правки ядра идут только в `pelmenya/ralph`. Копия в SourceCraft-монорепо
  обновляется из канона по manifest «код канона / данные потребителя», обратного
  направления нет; у переключения есть отрепетированный откат.
- До первого автономного запуска на каноне — минимальный guard с отрицательной пробой;
  preflight отвергает второй writer на тот же репозиторий (R15).
- S0 делается на этой неделе (26.10–01.11) руками человека и вахты (решение 26.10).

### S1. Безопасность мерджа и восстановление (P0)

- Вердикт ревью — структурный контракт: ревью засчитывается только по валидному вердикту,
  отсутствие вердикта или нераспознанный ответ — BLOCKED.
- Все записи `blocked`, от которых зависит мердж (восстановление, арбитр), проверяются
  чтением после записи; неизвестный исход держит мердж (R1).
- State: проверка схемы и версии, явное состояние «повреждён» (R2; атомарная запись
  в каноне уже есть).
- Явная политика внешнего CI на проект: `required`/`optional`/`disabled`; для `required`
  блокирует и неизвестная свежесть прогона; у гейта три
  исхода — прошёл / регрессия / сбой инструмента, с заданным fail-open или fail-closed
  на сбой инфраструктуры (R6).
- Сессия разбора `blocked`, оставившая незапушенный коммит, не роняет фазу, а причина
  стопа приходит в уведомлении текстом, а не `unknown`.
- Матрица окон падения: на каждый внешний эффект — тест «убить до / после эффекта»;
  приёмка формулируется как «что придёт в чат, если сейчас убить процесс».
- **Метрика продукта** (решение 26.10 — вперёд из S2): доля задач, доведённых до мерджа
  в отведённое время, потери по причинам и счётчик пойманных отказов по каждому барьеру.

### После S1: демо и путь входа

- Демо-репозиторий, на котором Ralph проводит карточку от трекера до мерджа, README
  с объяснением каждого барьера и цифрами метрики; установка пока ручная (решение 26.10 —
  вперёд из S4). Preflight ловит ошибки установки с понятной причиной.

### S2. Журнал попыток и наблюдаемость (P1)

- Журнал состояния этапов попытки: у каждого этапа обязательное событие исхода; после
  рестарта состояние берётся из журнала, а не собирается заново (R4, R9).
- Повтор намерения сначала сверяется с форжем по метке намерения; дубль комментария,
  issue или закрытия не публикуется вслепую. Детерминированный отказ одного намерения
  не блокирует хвост батча (`ralph#41`, `ralph#42`, `ralph#67`).
- Структурный журнал событий отдельно от человекочитаемого лога; ротация логов, порог
  диска, heartbeat не зависит от одной записи (R11).
- Ротация ключей подписки по кругу.
- Диагностика: стоп по подряд идущим «неизвестно» при проверке прогресса (R10), причины
  отказов в логе; валидатор формата карточки; адрес накопителя ревью (`ralph#65`).

### S3. Нормализованные харнессы и роли (P1)

- Адаптер рантайма сам распознаёт исход сессии и отдаёт нейтральную причину завершения
  (`SessionEndReason`); ядро не ищет маркеры Claude в тексте вывода (R7).
- Харнесс подключается пакетом адаптера вне `core/` и общих барьеров
  (`docs/harness-contract.md`): описание (что CLI читает сам, как называет инструменты и
  где у них пути, какие слои конфига исполняет, чем доказывает загрузку скилла),
  нормализатор события, регистратор барьера, сборщик конфига и чтение истории. Общие
  барьеры судят только по нормализованному событию и доверенному контексту сессии;
  незнакомое — запрет. Исполняемый конфиг дерева не исполняется. Хук — барьер качества,
  граница доверия — песочница у каждого харнесса. Пятый харнесс — пакет, фикстуры и
  зелёный набор соответствия, сгенерированный из описания.
- Профиль запуска = харнесс + провайдер + модель + авторизация; допуск профиля в роль —
  по canary на этой роли с отрицательным сценарием барьера (R8, R13).
- Ревью — всегда отдельная свежая сессия с валидным вердиктом (принятое решение);
  выбор модели ревьюера — маршрут роли, и в доказательстве мерджа записано, каким
  профилем оно проведено (R5).
- Гейт проверяемого кода исполняется в изолированном свежем клоне, политика гейта
  берётся из доверенной базовой ревизии (R3B).

### S4. Отдельный продукт (бывший R0 «доставка» и R1)

- Внешняя установка (принятое решение): точная ревизия ядра
  закреплена в коммите потребителя, рабочее дерево ядра не грязнится от работы петли,
  обновление и откат транзакционны.
- Launcher `./ralph`: install / update / rollback / doctor / start / stop; механизм
  доставки скрыт за ним (`ralph#36`, `ralph#37`).
- Контракт потребителя: раскладка файлов (`ralph#35`), четыре корня (есть в каноне с августа, в копии SourceCraft-монорепо — нет: пути там относительные внутри `.claude/ralph`, сводится в S0), версия
  совместимости launcher / ядро / конфиг / state / адаптер (`ralph#37`).
- Приёмка на двух живых потребителях — SourceCraft-монорепо с продом и GitHub-полигон
  с деплоем — и «фикс один раз» на реальном дефекте (`ralph#54`, `ralph#55`).
- Демо из ступени «после S1» переходит на установку launcher'ом.
- Защита lock на обеих площадках: PR, меняющий `.ralph/**` и `./ralph`, без человека не
  мерджится — на SourceCraft держит правило ревью площадки, на GitHub — гейт раннера
  (см. «Принятые решения», задача 50).
- У каждой миграции потребителя — отрепетированный откат; встроенная копия удаляется
  только после доказанного возврата на неё.

## Не в скоупе

- Несколько петель на одном репозитории (M1/M2 исследования, R15). Остаётся отдельным
  PRD после S4; до тех пор вторая копия на общем `origin` запрещена preflight'ом.
- Переписывание на брокер событий или durable workflow engine (варианты B/C исследования).
- Основной кодер на неконкурентной модели. Профили Kimi/Codex/OpenCode допускаются
  ступенью S3 в роли по canary; объявлять их основными до замеров не будем.
- Эскалация задачи на модель посильнее по провалу гейта: в открытом коде
  (`mshogin/archlint`, `mshogin/promptlint`) это только схема в `ECOSYSTEM.md`,
  проверенного механизма нет.
- Публикация в npm, SaaS, графический интерфейс, Windows.
- Перенос `visual-stand` в продукт — отдельная работа после S4.
- Claude Code Projects — исследование по готовности локального запуска, не веха.

## Технические ограничения

- Linux, Node.js 24+, ядро исполняется без сборки (как сейчас).
- Петля работает всё время миграции: ни одна ступень не требует остановить ночную
  работу дольше окна рестарта «🚦 Гейт мерджа». Конфиг читается при старте из дерева
  человека, и это не меняется до S4.
- Канон публичный: в нём нет имён проектов-потребителей, путей машин и секретов
  (барьер `ralph#2` действует и на документы).
- Ядро правится в `pelmenya/ralph` под его собственным гейтом; гейт SourceCraft-монорепо проверяет
  только то, что ядро встало в потребителя.
- Шов `gate` остаётся внутренним контрактом: потребитель задаёт состав `gate.checks`,
  но не подменяет реализацию (барьер `MERGE_PATH_BOUND_SEAMS`).
- Ступени S1 и S2 не меняют формат конфига потребителя без миграции, проверенной тестом.

## S2a. Устойчивый диагноз отказа и стоп повтора (пилот слабого исполнителя)

**Дата**: 2026-11-02
**Статус**: Draft

### Цель

Петля не запускает третью кодер-сессию на отказе, который уже дважды подряд повторился по
существу, и не теряет этот счёт при рестарте. Отказ, который сессия исправить не может
(возможности нет в установленном раннере), останавливает петлю сразу и называет причину.
Работа одновременно — первый пилот исполнения слабой моделью по карточкам, нарезанным
сильной.

Сейчас раннер держит два брейкера, и оба этот случай пропускают. Серия по карточке
(`maxSameIssue`, по умолчанию 3) считает взятия карточки, а не причину, и живёт в памяти
процесса: рестарт её обнуляет. Брейкер «без прогресса» (`maxNoProgress`) обнуляется любым
коммитом, а сессия, которая коммитит и упирается в тот же отказ, коммитит каждый раз. Так
одна карточка дошла до восьмой итерации из десяти, и последние три сессии упёрлись в один и
тот же отказ закрытия: кейса живой пробы не было в установленном ядре, и ни одна сессия
добавить его туда не могла.

### Сценарии

- Две сессии подряд по одной карточке получают отказ с одной идентичностью → третья не
  стартует, петля стоит и называет карточку, код отказа и путь к доказательству.
- Между двумя такими отказами раннер перезапущен → стоп всё равно наступает до третьей
  сессии.
- Второй отказ по той же карточке другой по существу (другой код или значимый параметр)
  → серия начинается заново, петля идёт дальше.
- Сессия просит закрыть карточку с живой пробой, кейса которой нет в установленном раннере
  → стоп сразу, без второй сессии. В тексте стопа — кейс и ревизия установки.
- Оператор после стопа читает причину в одном сообщении, без разбора длинного лога.

### В скоупе

- Типизированный результат отказа: категория, стабильный код, значимые параметры, короткая
  безопасная причина, ссылка на локальное доказательство. Сырой текст после редакции
  секретов хранится отдельно от идентичности.
- Два первых класса отказа: батч намерений не разобрался; закрытие выбыло, потому что
  живой пробы нет в установке.
- Идентичность отказа: экземпляр, фаза, карточка, этап, код, значимые параметры. PID,
  время и оформление текста её не меняют. SHA попытки хранится свидетельством и серию сам
  по себе не обнуляет.
- Серия и последний отказ хранятся в state раннера штатной атомарной записью; форма поля
  проверяется при чтении, state без него читается как «серии нет».
- Подключение к циклу: стоп до спавна третьей сессии и немедленный стоп на недоступной
  возможности установки.
- Порог серии — ключ конфига с дефолтом 2 (решение человека 02.11), с той же
  fail-closed-проверкой, что у `maxSameIssue`: опечатка или недопустимое значение — стоп на
  старте с названной причиной.

### Не в скоупе

- Красный CI, замечания ревью, сбои ревью-сессии и правок — следующие классы, отдельно.
- Передача причины в промпт следующей попытки (поставка B) и панель состояния (поставка C).
- Стадия планировщика правок по ревью (поставка D, `reliability-development.md`): решено
  02.11 делать сразу после пилота, на его данных.
- Изменение порогов и поведения `maxSameIssue` и `maxNoProgress`: они остаются как есть.
- Транзиенты (сеть, лимит, 5xx): у них свой ограниченный механизм повтора, в серию они не
  входят.
- LLM-классификатор отказов: код отказа ставит код раннера, а не модель.

### Ограничения

- Fail-closed: неизвестный отказ не превращается в успех и серию не обнуляет; битое поле
  серии в state — стоп с причиной, а не «серии нет»; сбой записи state — стоп.
- Успешный код выхода сессии без подтверждённого применения намерений серию не прерывает.
- Недоступная возможность лечится только сменой установки. Раннер не читает кейс пробы из
  дерева сессии и не просит сессию добавить его в свою ветку.
- Правила корня канона: без проектных следов, значения — в конфиге, команды форжа — в
  адаптерах, чистый клон, храповик покрытия. Решение не зависит от харнесса: одинаково
  у всех четырёх CLI.

### Критерии готовности

- [ ] Тест: два одинаковых отказа подряд по одной карточке → третьего спавна нет, стоп
      называет код и карточку.
- [ ] Тест: рестарт между двумя одинаковыми отказами → третьего спавна всё равно нет.
- [ ] Тест: разный код или значимый параметр (cli/case) → серия = 1, стопа нет.
- [ ] Тест: разные PID, время и оформление текста при одном коде и параметрах → одна
      идентичность.
- [ ] Тест: кейса живой пробы нет в установке → стоп до следующего спавна; дерево сессии
      при этом не читается.
- [ ] Тест: код выхода 0 без подтверждённых намерений → серия не прервана.
- [ ] Тест: state без новых полей читается как «серии нет»; битое поле серии и сбой записи →
      стоп с названной причиной.
- [ ] Тест: недопустимое значение ключа порога серии → стоп на старте с причиной.
- [ ] Существующие тесты `maxSameIssue` и `maxNoProgress` зелёные без правки ожиданий.

### Пилот исполнения

Решения человека 31.10–02.11: декомпозицию делает сильная модель один раз, при резке;
исполняет слабая. Кодер петли — Kimi CLI родным харнессом (`kimi-native`), K3.1 Pro;
ревью-стадия петли — тоже K3.1 Pro. Сильная модель режет карточки, ведёт вахту, разбирает
каждый провал исполнителя и перерезает карточку по диагнозу, а не пишет код за неё.
Работа петли — полный AFK: ручной шаг оператора как часть процесса не допускается. Как
режутся правки по ревью без человека, пилот не решает, а меряет: пачка инженерных решений
в сессию правок раздула прошлую поставку до +4283 строк, и пилот покажет, повторится ли
это на карточке, нарезанной заранее.

Что меряем: итерации на карточку, сессии без коммита, повторы одного отказа, остановки
до человека, объём правок после ревью. Пилот засчитывается только реализацией нового
поведения по подготовленной карточке; закрытие карточки с уже готовым кодом не считается.
Вывод о пригодности слабого исполнителя делает человек.

## S2b. Планировщик правок по ревью

**Дата**: 2026-11-02
**Статус**: Draft

### Цель

Сессия правок получает не сырые находки ревью, а план: выбранное решение, отвергнутые
варианты и шаги с командами проверки. Решение принимает отдельная роль петли —
планировщик — со свежим контекстом и всеми открытыми находками; исполнитель правок план
исполняет и решение не пересматривает.

Пилот Фазы 18 (02.11) показал, где теряется качество. Код пяти карточек на слабой модели
сдан за час с первой итерации каждой, ревью нашло дефекты по существу с пробами. Круги
правок не сходились: ревью предложило две дороги («тип отказа либо нормализация текста»),
исполнитель взял дешёвую и трижды подряд чинил названный край одной регулярки, а ревью
трижды находило следующий. Независимый арбитр без истории проходов — та же модель —
сразу вышел на поток данных целиком и нашёл два настоящих дефекта. Класс увидел свежий
контекст с другой ролью, а не более сильная модель. Отдельно: находка третьего круга
(`major`) потерялась, потому что промпт разбора `blocked` велит чинить только `[blocker]`
и причину метки, а мердж держат и `blocker`, и `major`.

### Сценарии

- Ревью фазы оставило находки → до сессии правок отрабатывает планировщик; сессия правок
  получает план и комментарии ревью как данные.
- Круг ревью правок и разбор `blocked` — тот же порядок: план, затем правки.
- Планировщик упал, вышел без плана или с планом не той формы → стоп с причиной; сессия
  правок не стартует, молчаливого пропуска стадии нет.
- Планировщик изменил дерево или HEAD → стоп с причиной: роль только читает.
- Раннер перезапущен после плана, до правок → правки идут по сохранённому плану, второго
  планировщика нет.
- После предела кругов планирования блокер остался → стоп с причиной, а не новый круг.

### В скоупе

- Роль планировщика на модели петли (сейчас — Kimi K3.1 Pro, `kimi-native`): та же
  маршрутизация модели, что у ревью. Отдельная модель или канал для неё не вводится.
- Форма плана и её разбор fail-closed; план идёт в промпт правок и в журнал сдачи.
- Вход планировщика — все комментарии ревью доверенных авторов и дифф фазы; блокирующими
  считаются `blocker` и `major` — во всех промптах правок, включая разбор `blocked`.
- Предел числа планов на фазу ключом конфига, fail-closed.
- Барьер к резке: каждый номер критерия раздела PRD покрыт строкой плана фаз.

### Не в скоупе

- Сильная модель или другой провайдер внутри петли: управляющий в петлю не встраивается
  (решение человека 02.11).
- Смена потолков лестницы ревью правок и попыток `blocked`: они остаются, планировщик
  встаёт перед каждой сессией правок внутри них.
- Перерезка карточек кодера: планировщик режет только правки по ревью.

### Ограничения

Правила корня канона: без проектных следов, значения — в конфиге, команды форжа — в
адаптерах, барьер вместо абзаца, fail-closed, чистый клон, храповик покрытия. Стадия не
зависит от харнесса. Каждый этап сдачи пишет исход в журнал сдачи; этап без исхода после
рестарта — не завершён.

### Критерии готовности

- [ ] [S2b.1] Тест: выход планировщика с решением, списком отвергнутого и 1–8 шагами, у
      каждого действие, команда и ожидаемый исход RED или GREEN → план разобран.
- [ ] [S2b.2] Тест: нет блока плана, второй блок, пустое решение, шаг без команды, ноль или
      больше восьми шагов, незнакомое поле → отказ разбора с названной причиной.
- [ ] [S2b.3] Тест: промпт правок по ревью, круга ревью правок и разбора `blocked` с
      планом содержит решение и шаги плана и запрет пересматривать решение.
- [ ] [S2b.4] Тест: промпт разбора `blocked` требует чинить находки `blocker` и `major`, а не
      только `blocker`.
- [ ] [S2b.5] Тест: ревью фазы с находками → планировщик запущен до сессии правок, план —
      в её промпте.
- [ ] [S2b.6] Тест: планировщик упал или план не разобрался → сессия правок не запущена,
      стоп с причиной `fix-plan`.
- [ ] [S2b.7] Тест: после планировщика HEAD сдвинулся или дерево грязное → стоп с причиной
      `fix-plan`, сессия правок не запущена.
- [ ] [S2b.8] Тест: рестарт после этапа плана с исходом `ok` и до правок → планировщик не
      запускается повторно, правки получают сохранённый план.
- [ ] [S2b.9] Тест: перед кругом ревью правок и перед разбором `blocked` планировщик
      запускается так же, как перед первыми правками.
- [ ] [S2b.10] Тест: число планов фазы дошло до предела, а блокер остался → стоп с
      причиной, новый планировщик не запущен.
- [ ] [S2b.11] Тест: недопустимое значение ключа предела планов → стоп на старте с
      причиной.
- [ ] [S2b.12] Структурный тест: каждый вызов промпта сессии правок в оркестраторе
      получает план.
- [ ] [S2b.13] Тест: номер критерия раздела PRD без строки в покрытии плана фаз → красный;
      все номера покрыты → зелёный; раздел без номеров не проверяется.
- [ ] [S2b.14] Существующие тесты лестницы ревью правок, арбитра и разбора `blocked`
      зелёные без правки ожиданий о потолках.

## S2c. Сдача без холостых кругов и без молчаливого пропуска плана

**Дата**: 2026-11-02
**Статус**: Draft

### Цель

Пилот Фазы 19 (02.11) сдал фазу одним кругом правок, но потерял время и запас прочности
на двух местах, где раннер решает за модель, а не модель за раннер.

Первое — холостой разбор `blocked`. Метку `blocked` ставит первое ревью фазы. Круг правок
закрыл все находки, ревью правок вынесло «merge» без блокирующих, но метку никто не снял:
снимает её только повторное ревью внутри разбора `blocked`. Гейт увидел метку и отправил
фазу в разбор, где чинить нечего, — сессия разбора, повторное ревью (≈ 11 мин) и одна из
трёх попыток `blocked` впустую.

Второе — пропуск плана правок без стопа. Планировщик (S2b) обязан стоять перед каждой
сессией правок, а его отказ — стоп с причиной. В двух местах правки всё же начинаются без
плана с записью «план пропущен»: когда модель планировщика не определилась (перед кругом
лестницы и разбором `blocked` то же условие — стоп), и когда начало правок само
дописывает пропуск плана ради журнала прежней ревизии — правило без признака ревизии,
действующее для любого журнала.

Третье — круг правок ради косметики (вахта 03.11, Фаза 21). Ревью фазы оставило одну
находку `nit` и ни одной серьёзнее, а раннер всё равно запустил планировщика и сессию
правок: 8 минут и две сессии на строку документации. Шаг правок после ревью идёт
безусловно, серьёзность находок он не смотрит. Решение человека 03.11: правки запускаются,
только если среди находок ревью фазы есть хоть одна не ниже порога, заданного в конфиге
потребителя; у канона порог — `minor`. Находки ниже порога остаются комментариями на PR.

### Сценарии

- Ревью правок вынесло «merge» без блокирующих находок, на PR осталась метка `blocked`
  первого ревью → метка снята по вердикту ревью раннера, гейт идёт к чекам без разбора
  `blocked`, попытка `blocked` не тратится.
- Ревью правок вынесло «merge», но снять метку не удалось → гейт ведёт себя как сейчас
  (разбор `blocked`), причина названа в логе.
- Ревью фазы с находками, модель планировщика не определилась → стоп с причиной
  `fix-plan` до сессии правок, как перед кругом лестницы и разбором `blocked`.
- Ревью фазы без находок → план пропущен записью этапа плана, правки не запускаются.
- Ревью фазы оставило только находки ниже порога правок из конфига → правки не
  запускаются, фаза идёт к гейту, находки остаются комментариями на PR, а лог называет
  пропуск и порог.
- Порог правок в конфиге не задан → правки идут на любую находку, как до порога.
- Журнал сдачи прежней ревизии (правки после ревью без записи плана) после обновления
  ядра → читается и продолжается с правок, а не с плана.
- Новый оркестратор начинает правки без записи этапа плана → отказ с причиной, а не
  молчаливая запись «план пропущен».

### В скоупе

- Снятие метки `blocked` первого ревью по вердикту «merge» ревью правок.
- Единое правило: нет модели планировщика — стоп `fix-plan` во всех местах планирования.
- Запись «план пропущен» — только решением этапа плана; совместимость с журналом прежней
  ревизии — только при разборе журнала с диска.
- Порог серьёзности, ниже которого находки ревью фазы правок не запускают, — значение
  конфига потребителя.

### Не в скоупе

- Потолки лестницы ревью правок и попыток `blocked` — не меняются.
- Предел числа планов фазы — S2b (Фаза 20).
- Причина стопа при молчании площадки CI — отдельная карточка Фазы 20.
- Порог правок на лестнице ревью правок и в разборе `blocked`: там правки идут только по
  блокирующим находкам и сейчас.

### Ограничения

Правила корня канона: fail-closed (отказ — стоп с причиной, а не пропуск), снятие блока —
результат ревью раннера, а не решение кодер-сессии, без проектных следов, чистый клон.
Журнал сдачи прежней ревизии обязан продолжаться после обновления ядра посреди сдачи.

### Критерии готовности

- [ ] [S2c.1] Тест: ревью правок вынесло «merge» без блокирующих находок при метке
      `blocked` на PR → метка снята, разбор `blocked` не запущен, счётчик попыток
      `blocked` не увеличен.
- [ ] [S2c.2] Тест: при вердикте «merge» снять метку не удалось → разбор `blocked` идёт
      как прежде, а лог называет причину неснятой метки.
- [ ] [S2c.3] Тест: ревью правок оставило блокирующие находки → метка `blocked` не
      снимается.
- [ ] [S2c.4] Тест: ревью фазы с находками и неопределённая модель планировщика → стоп с
      причиной `fix-plan`, сессия правок не запущена, записи «план пропущен» нет.
- [ ] [S2c.5] Тест: ревью фазы без находок → этап плана записан с исходом «пропущен»,
      сессия правок не запущена.
- [ ] [S2c.6] Тест: начало этапа правок без записи этапа плана в журнале текущей сдачи →
      отказ с причиной, запись «план пропущен» не появляется.
- [ ] [S2c.7] Тест: журнал прежней ревизии с диска (правки после ревью без записи плана)
      → разбор принят, продолжение с правок.
- [ ] [S2c.8] Тест: ревью фазы оставило только находки ниже порога правок → сессия правок
      и планировщик не запущены, фаза идёт к гейту, лог называет пропуск и порог.
- [ ] [S2c.9] Тест: среди находок ревью фазы есть хоть одна не ниже порога → правки идут
      как прежде.
- [ ] [S2c.10] Тест: порог правок не задан → правки идут на любую находку, включая `nit`.
- [ ] [S2c.11] Тест: порог правок задан неизвестным уровнем → отказ старта с причиной.

## S3a. Контекст петли доходит до хука каждого CLI

**Дата**: 2026-11-02
**Статус**: Draft

### Цель

Доказать живым прогоном настоящего CLI, что контекст сессии петли, который раннер кладёт
в окружение сессии, доходит до хука барьера у каждого из четырёх харнессов. От этого
зависят правила, действующие только в петле: запрет писать данные контура и поверхности
конфига харнессов и запрет делегирования.

Сейчас стартовая проба исполняет хуки сама, с нужным окружением, и поэтому доказывает
разбор контекста, а не его доставку. Доставку она доказывает только у Claude Code; у
остальных старт говорит строкой `⚠`, что правила держатся на допущении. Kimi Code с 02.11 —
основной исполнитель петли, и допущение покрывает каждую его сессию.

### Сценарии

- Стенд гоняет сессию CLI с контекстом в окружении и хуком, который записывает, что
  получил → судья даёт PASS, если хук получил ровно то значение, что положено в окружение.
- Хук вызван, но контекста нет или он другой → FAIL: правила «только в петле» у этого CLI
  не действуют.
- Хук не вызван ни разу → INCONCLUSIVE: ни доставка, ни её отсутствие не доказаны.
- Судья сам не дал вердикта (упал, ответил пустым или незнакомым словом) → проба не
  зелёная, стенд выходит ненулевым кодом. Найдено вахтой 03.11 на диффе Фазы 21: пустой
  вердикт проходил мимо счёта красных проб, и стенд выходил нулём.
- Вахта после мерджа гоняет пробу на Kimi Code в изоляции ОС и записывает итог с версией
  CLI в отчёт стенда.

### В скоупе

- Проба стенда для всех четырёх CLI стенда: Claude Code, Codex, Kimi Code, OpenCode.
- Значение контекста в пробе — случайное на прогон, ожидаемое судья берёт с хоста, а не из
  каталога стенда; в промпт сессии значение не попадает.
- Живой прогон на Kimi Code — вахтой после мерджа, итог — в `docs/install-stand.md`.

### Не в скоупе

- Снятие строки `⚠` для доказанных харнессов и реакция на FAIL — отдельная фаза по
  результату живого прогона: решение зависит от итога, которого до мерджа нет.
- Каталог живых проб раннера: маршрут ключа Kimi Code, Codex и OpenCode в стенд раннером не
  проверен (#219), поэтому проба исполняется стендом напрямую, а не намерением сессии.

### Ограничения

Правила корня канона: без проектных следов, барьер вместо абзаца, fail-closed, чистый
клон. Правила стенда (`provision/`): изоляция ОС, улики судьи вне досягаемости
проверяемого, исполнитель стенда и проверяемое — из разных деревьев.

### Критерии готовности

## S3b. Свежий CLI без поломки барьера

**Дата**: 2026-11-03
**Статус**: Draft

### Цель

Петля работает на той версии CLI харнесса, с которой снято описание его пакета, и узнаёт о
свежей версии сама, не ослабляя барьер. CLI обновляются ежедневно, а описание пакета —
строгий снимок полей и инструментов конкретной версии: незнакомое поле — блок. Поэтому
свежесть даёт не ослабление проверки, а конвейер: закреплённая версия → ежедневная
канарейка в стенде → PR смены версии под ship человека.

Сейчас петля зовёт системный бинарь из PATH и о расхождении с описанием пишет только
строку `⚠`. Повод — первый пилот на Kimi Code: исполнялась 2.4.0 при описании, снятом с
2.3.2; петля шла, потому что расхождение задело лишь историю файлов CLI, но другое поле
входа заблокировало бы каждый вызов. Поставка E направления надёжности
(`reliability-development.md`); поглощает отложенную карточку допуска версии CLI.

### Решения человека (03.11)

- Закреплённая версия — `cliVersion` описания пакета, единственный источник. Смена версии —
  PR нового описания.
- Петля исполняет СВОЮ копию CLI закреплённой версии, а не системный бинарь: обновление CLI
  на машине петлю не задевает и не останавливает.
- PR смены версии всегда под ship человека: правка `adapters/harnesses/**` не ослабляется.
- Канарейка — стадия петли раз в сутки на границе итерации, а не таймер хоста.
- «Безопасный» дрейф — только совпавший инвентарь: инструменты, поля входа и конверт
  события новой версии те же, что в снимке текущей. Любое расхождение — карточка с диффом,
  описание правится резкой, а не автоматом.

### Сценарии

- Петля стартует: копии закреплённой версии нет → ставит её в свой каталог и идёт на ней;
  в PATH другая версия → сессия всё равно на закреплённой.
- Установка копии не удалась или копия изменена после установки → стоп старта с причиной;
  фолбэка на PATH нет.
- Раз в сутки между итерациями канарейка смотрит последнюю опубликованную версию каждого CLI;
  новая → ставит её в изоляции стенда и гоняет снятие инвентаря, отрицательные пробы guard,
  стенд установки и короткую сессию — всё на фиктивном провайдере, без живого ключа.
- Всё зелёное и инвентарь совпал → PR с новой `cliVersion` и снимком стенда; петля его не
  мерджит. Инвентарь разошёлся → карточка с диффом. Красное → карточка с диагнозом. Петля в
  любом случае остаётся на прежней версии и не останавливается.
- Переход на новую версию — новой ревизией ядра после мерджа PR, рестартом на границе:
  описание пакета едет с ядром.

### В скоупе

- Все четыре CLI: Claude Code, Codex, Kimi Code, OpenCode.
- Копия CLI петли по ключу «харнесс, версия» и её защита от записи из сессии петли.
- Сверка версии исполняемого бинаря перед сессией — стопом, а не строкой `⚠`.
- Канарейка как стадия петли: срок, бюджет времени, итоги, PR и карточки без дублей.
- Матрица отрицательных проб стенда с вердиктом у каждого CLI: регистрация guard с
  нормализатором пакета и фиктивный MCP на стенде у Codex, Kimi Code и OpenCode (сейчас
  пробы путей, поиска, `unknown-tool` и MCP у них дают SKIP).

### Не в скоупе

- Мердж PR версии петлёй и автоматическая правка описания при дрейфе инвентаря.
- Полная независимая сверка инвентаря CLI с описанием пакета (Фаза 16f): канарейка сверяет
  снимок новой версии со снимком текущей, а не описание с инвентарём.
- Допуск модели в роль по canary (Фаза 17).
- Маршрут живого ключа провайдера в стенд: канарейке он не нужен.
- Автоматический переход петли на новую ревизию ядра: рестарт на границе остаётся за
  оператором (решение человека 03.11 — сперва изучаем поведение слабых моделей).

### Ограничения

Правила корня канона: без проектных следов, значения — в конфиге, команды — в адаптерах
(как поставить CLI нужной версии — данные и код пакета харнесса, не ядра), барьер вместо
абзаца, fail-closed на старте, чистый клон. Правила стенда: изоляция ОС, улики судьи вне
досягаемости проверяемого. Сбой канарейки — не стоп: она не решает мердж, но называет
причину.

## S2d. Причина отказа в следующей попытке и фаза не больше лимита итераций

**Дата**: 2026-11-03
**Статус**: Draft

### Цель

Вторая кодер-сессия по карточке знает, почему отвергли первую: раннер кладёт в её промпт
сохранённый диагноз отказа, а не надеется, что модель сама найдёт причину в логе, которого
не видит. И петля не берёт фазу, которую лимит итераций заведомо не вместит: раньше это
выяснялось брейкером посреди ночи.

Сейчас серия отказов (S2a) хранит диагноз в state и останавливает петлю после второго
одинакового отказа, но вторая сессия стартует вслепую — с тем же промптом, что и первая.
Ошибка формы намерений повторяется, и серия честно доходит до стопа, хотя причину можно
было назвать. Бюджет фазы (#220) — только строка `⚠`: фаза с 11 карточками при лимите 10
(Ф16c) встала на брейкере, а повтор после `maxTurns` съедает итерацию, так что запаса нет и
при равенстве.

### Решения человека (03.11)

- Поставка B из `reliability-development.md` режется сейчас, за Фазой 24; поставка C — после неё.
- Карточка #267 входит в эту работу. Превышение бюджета фазы — стоп, а не предупреждение:
  размер фазы держит барьер раннера, а не абзац. Это отменяет решение #220 «предупреждение,
  а не стоп» для старта фазы.
- Раздел согласован вместе с решениями: без отказа промпт кодера не меняется; непрочитанные
  карточки вехи — стоп; дописывание в идущую фазу — прежняя строка `⚠`; контекст получает
  только кодер-сессия; ревизия установки хранится вместе с отказом, у старой записи она
  неизвестна.

### Сценарии

- Первая сессия по карточке получила отказ, серия ещё не дошла до порога → следующая
  кодер-сессия по той же карточке получает в промпте код отказа, причину, значимые параметры,
  путь к доказательству и ревизии, на которых он случился.
- Между отказом и следующей попыткой раннер перезапущен → причина всё равно в промпте.
- Отказ записан по одной карточке, петля берёт другую или переходит в другую фазу → чужая
  причина в промпт не попадает.
- Отказа нет или серию прервали применённые намерения → промпт кодера такой же, как без
  этой работы.
- Живой пробы нет в установке → петля стоит до следующей сессии (S2a); в промпт сессии эта
  причина не уходит, и сессию не просят добавить пробу в свою ветку.
- В вехе открытых карточек петли больше `maxIterations` → фаза не начинается, стоп называет
  веху, число и лимит; на старте и на границе фаз одинаково.
- Карточек ровно столько, сколько итераций → строка `⚠`, фаза идёт.

### В скоупе

- Сборка контекста прошлой попытки из сохранённого в state диагноза: этап, код, причина
  после редакции секретов, значимые параметры, путь к доказательству, ревизия дерева
  попытки и ревизия установки ядра на момент отказа.
- Ревизия установки хранится вместе с отказом. Для отказа, записанного без неё, контекст
  называет её неизвестной, а не подставляет текущую.
- Явная граница длины контекста; усечение помечено словами в самом тексте.
- Причина подаётся как данные в штатной обёртке промпта: текст причины писала модель, и
  приказом он не становится. Делимитеры данных внутри причины рамку не закрывают.
- Источник — только state раннера: комментарии трекера, журналы сессий и дерево сессии для
  этого не читаются.
- Бюджет фазы на старте и при выборе следующей фазы на границе: число открытых карточек
  петли в вехе (без `human` и `hold`) из данных площадки, лимит — из конфига. Больше лимита —
  стоп до первой итерации с причиной; равно — строка `⚠`.

### Не в скоупе

- Новые классы отказов (красный CI, ревью, сбои сессии правок) — их диагноз S2a ещё не
  записывает.
- Контекст для сессий правок, ревью и планировщика — только кодер-сессия.
- Панель состояния (поставка C).
- Изменение порога серии, `maxSameIssue` и `maxNoProgress`.
- Бюджет при дописывании карточек в уже начатую фазу (намерения, лестница ревью): там
  остаётся строка `⚠` из #220 — карточку из идущей фазы раннер сам не выбросит.
- Правка текста скиллов резки и теста размера плана — барьер плана уже есть.

### Ограничения

- Fail-closed: битое поле диагноза в state — стоп с причиной (как у S2a), а не промпт без
  него. Бюджет фазы, который не удалось сверить (площадка не ответила), — стоп с причиной:
  непроверенный барьер не равен пройденному.
- Секреты и сырые транскрипты в промпт не попадают; причина та же, что ушла в стоп S2a.
- Решение не зависит от харнесса: контекст — текст промпта, одинаковый у всех четырёх CLI.
- Правила корня канона: без проектных следов, значения — в конфиге, команды форжа — в
  адаптерах, чистый клон, храповик покрытия.

### Критерии готовности

- [ ] [S2d.1] Тест: после первого отказа по карточке следующий кодер-промпт по ней содержит
      код, причину, значимые параметры и путь к доказательству — до фактического вызова
      сессии.
- [ ] [S2d.2] Тест: в контексте — ревизия дерева попытки и ревизия установки ядра на момент

## S2e. Приёмка от исполняемой спецификации (петля на слабом исполнителе)

**Дата**: 2026-11-04
**Статус**: Draft

### Цель

Фазу принимают проверки, записанные до кода и закрытые от правки исполнителем, а не модель,
которая читает дифф после. Петля, где все роли играет одна модель ниже фронтира, закрывает
фазу за предсказуемое время и не ходит кругами правок.

Сейчас качество держит ревью моделью: ревью фазы → правки → ревью правок (до трёх проходов)
→ арбитр → разбор `blocked`, а потолок проходов и предел планов лишь ограничивают ущерб.
Фазы 18–23 на слабом исполнителе закрывались за 0,5–4 ч: тело карточки почти было
спецификацией. Фаза 24 (резка по контракту, 21 критерий, ветка +8,3 тыс. строк) встала
через 13 ч на пределе планов правок: карточки — 5,7 ч, приёмка — 7 ч. Ревью правок давали
4, 4 и 1 новых blocker/major; исполнитель чинил показанный пример, а не класс дефекта;
проектный blocker (код проверяемой ветки исполняется на хосте до изоляции) нашло только
шестое ревью — полное, запущенное заново после чини-сессии гейта. 38 предметных находок
легли в шесть классов, и для четырёх в каноне уже было решение — в прозе и в чужих модулях.
Повторные прогоны модели-ревьюера находят разные подмножества дефектов: это свойство
метода, а не случайность фазы.

### Решения человека (04.11)

- Все роли петли — одна слабая модель. Сильные модели в петлю не встраиваются: доступ к
  ним может пропасть в любой момент. Резку пока ведёт сильная модель, но её формат должен
  быть исполним слабой.
- Человек в контракт фазы не включается: все фазы — AFK. Класс угрозы, которого нет в
  каталоге, слабая модель не найдёт; это названный предел. Пропущенный класс ловится после
  мерджа и пополняет каталог.
- Прежняя приёмка сжимается до одного полного ревью фазы. Ревью правок, арбитр и разбор
  `blocked` работают только по диффу правок и по классам.
- Сначала пилот на хвосте Фазы 24; Фаза 25 — под `hold` до перерезки по новой схеме.
- Перед пилотом — мини-срез раннера: предохранители размера, ревью фазы-продолжения и ревью
  после чини-сессии гейта по диффу. Без него пилот на старом раннере снова получил бы полное
  ревью всего PR Фазы 24 и мерил бы прежнюю болезнь ревью, а не новую резку. Полная сдача
  после чини-сессии (решение 19.07) заменяется ревью её диффа: правка гейта по-прежнему не
  идёт мимо ревью.
- Барьеры размера фазы — часть этой работы, как предохранитель, а не решение.
- Сессии сдачи снова гоняют полный гейт (откат #269).
- Поправка 04.11 (разделы S2f, S2g): до пилота этого раздела идут ревью по карточке и атака
  дизайна до кода; ревью фазы остаётся полным, его сужение — по метрикам обеих фаз.

### Сценарии

- В плане фаза с 13 критериями PRD → барьер плана красный, фаза до бэклога не доходит.
- Ветка фазы на заведении PR больше предела изменённых строк → стоп до ревью: «перережь».
- Петля берёт фазу → первая карточка — контракт: приёмочные тесты по каждому критерию фазы,
  сквозной сценарий, ответ по каждому классу каталога опасностей. Тесты красные, кода
  реализации нет.
- Сессия реализации или правок меняет закреплённый тест контракта → блок. Контракт меняет
  только сессия контракта; вторая правка контракта в фазе — стоп.
- Карточка реализации просит закрытия, а её приёмочные тесты красные → карточка открыта.
- Ревью фазы прикладывает к находке тест, красный на HEAD → находка блокирует. Без теста или
  с тестом, зелёным на HEAD, — minor, сдачу не держит.
- Сессия правок чинит находку → раннер откатывает строки правки: тест находки и проверка
  класса обязаны покраснеть, иначе правка не принята.
- Повторное ревью → смотрит дифф правок и непроверенные строки карты покрытия; проверенное
  заново не сэмплирует.
- Чини-сессия гейта поправила CI → ревьюится её дифф, а не вся фаза.
- Ветку с открытым PR, по которому полное ревью уже было, берёт новая фаза — продолжение с
  объявленной базой ревью → её ревью видит дифф от базы и открытые находки PR, а не весь PR.
- Второй дефект того же класса в фазе, новая находка вне диффа правок на втором проходе или
  приёмка дольше реализации → стоп «перережь» с пакетом: открытые классы, красные тесты,
  ветка и коммиты целы.
- Фаза закрыта → строка метрик: время реализации и приёмки, сессии и шаги по ролям, находки
  по проходам, повторы классов.

### В скоупе

- Предохранители размера: в плане — не больше 12 критериев PRD на фазу по таблице покрытия и
  не больше 5 карточек (как сейчас), долг плана — поимённо числом; в раннере — предел
  изменённых строк ветки фазы на заведении PR.
- Карточка контракта — первая в каждой фазе: заглушки типов и сигнатур, таблица состояний
  там, где есть state, приёмочные тесты по каждому критерию PRD фазы и сквозной сценарий,
  реестр опасностей фазы (ответ по каждому классу каталога и тест, который его держит).
- Проверка контракта раннером по форме: тест на каждый критерий фазы, тесты красные на
  коммите контракта, типы и формат зелёные, ответ по каждому классу.
- Закрепление контракта на фазу: тесты и реестр опасностей — защищаемая поверхность для
  сессий реализации и правок у всех четырёх харнессов.
- Каталог опасностей v0 в ядре — шесть классов: окна обрыва и идемпотентность внешних
  эффектов; время жизни процессов и ресурсов; разбор входа без fail-open; граница доверия
  и секреты; стыки между карточками; семантика сравнения. У каждого — вопрос применимости
  и переиспользуемый набор проверок, который карточка подключает, а не пишет.
- Закрытие карточки реализации раннером — только при зелёных её приёмочных тестах на точном
  коммите.
- Одно полное ревью фазы с картой покрытия (файлы × классы реестра, SHA). Находка
  blocker/major — с тестом-воспроизведением; идентичность находки — тест, а не текст.
- Мутационная проверка правки: откат строк правки краснит тест находки и проверку класса.
- Ревью правок и ревью после чини-сессии гейта — по диффу правок и непокрытым строкам карты.
- Фаза-продолжение открытого PR: база ревью объявлена в конфиге фазы; первое ревью — дифф от
  базы и открытые находки PR.
- Стопы перерезки с пакетом. Бюджет фазы (сессии, планы) не обнуляется переходом в
  `blocked`, чини-сессией гейта, повторной сдачей и рестартом.
- Строка метрик фазы на закрытии.
- Пилот: хвост Фазы 24 — первая фаза по новой схеме. Что в пилоте держит текст, а не код,
  план называет поимённо. Итог — сравнение метрик с Фазами 18–24.

### Не в скоупе

- Человек в контракте фазы и вторая модель в любой роли (решение 04.11).
- Автоматическое пополнение каталога из пропущенных дефектов — пополняет резка, карточкой.
- Резка как стадия петли — отдельная работа после пилота.
- Интерфейс чтения (отказ на чтение больших файлов целиком, карта чтения) и разрезание
  крупных модулей ядра — отдельная работа.
- Учёт квоты в токенах: рантайм их не отдаёт, валюта расхода — сессии и шаги.

### Ограничения

- Fail-closed: контракт без теста на критерий, тест, зелёный до реализации, пустой ответ по
  классу, непрочитанная карта покрытия, мутационная проверка, которая не запустилась, —
  стоп с причиной, а не пропуск.
- Независимость от харнесса: закрепление контракта — правило guard на событии у всех четырёх
  CLI; ни одна проверка не читает транскрипт конкретного CLI.
- Пороги (строки ветки, отношение приёмки к реализации) — в конфиге потребителя; битое
  значение — стоп.
- Расход: новая схема не добавляет проходов ревью сверх нынешнего худшего случая — каждый
  проход ест месячную квоту.
- Правила корня канона: без проектных следов, команды форжа — в адаптерах, чистый клон,
  храповик покрытия.

## S2f. Ревью по карточке с допуском, привязанным к проверенному коду

**Дата**: 2026-11-04
**Статус**: Draft

### Цель

Дефект кода ловится на диффе одной карточки, пока он мал, а карточка закрывается только после
ревью ровно того кода, который в ней лежит. Ревью полного диффа фазы на 1–8 тыс. строк не
сходится: каждый проход находит новое подмножество дефектов (раздел S2e). На диффе карточки
(сотни строк) предмет ревью обозрим, а правку делает сессия, у которой этот код ещё свеж.

Основание — пилот 04.11 на тех же четырёх задачах Фазы 26 (слабый исполнитель во всех ролях):
ревьюер той же модели нашёл на готовом коде реальные дыры, которые исполнитель не предусмотрел, —
причём оба класса blocker первого ревью сидели внутри одной карточки. Это довод за место ревью
(ближе к коду), а не доказательство сходимости: лестницу пилота остановили до исхода.

### Решения человека (04.11)

- Работа режется на два раздела и две фазы: сначала этот (ревью по карточке), затем S2g (атака
  дизайна). Обе фазы идут до пилота раздела S2e.
- Ревью фазы остаётся полным: сужать его до стыков — только по метрикам обеих фаз, отдельной
  работой. Продолжение фазы мимо карточки `blocked` — тоже отдельной работой: на общей ветке
  следующая карточка строилась бы поверх непринятых коммитов.
- Предел — три круга «ревью → правки» на карточку. Исход предела AFK-безопасный: стоп с пакетом,
  а не ожидание человека посреди шага.
- Резку этих фаз атакует слабая модель вручную до старта петли; находки — в тела карточек.

### Сценарии

- Кодер просит закрыть карточку → раннер не закрывает её, а запускает ревью диффа карточки: от
  головы ветки до первой сессии карточки до текущей головы.
- Ревью вернуло находки и вердикт «есть blocker или major» → сессия правок получает находки из
  state и по каждой называет тест, воспроизводящий её сценарий → следующее ревью снова видит весь
  дифф карточки (он мал) с фокусом на правке и открытых находках → … до трёх кругов. Правка,
  локально верная, но сломавшая ранее проверенную часть карточки, так не проходит мимо.
- Вердикт «чисто» для головы X, голова ветки — X → карточка закрыта с комментарием кодера.
  Голова сдвинулась после ревью → ещё круг: закрывается только проверенное.
- Три круга или бюджет сессий карточки исчерпаны, blocker или major открыт → карточка `blocked`,
  стоп фазы с пакетом: открытые находки, SHA последнего ревью, ветка и коммиты целы.
- Раннер убит на любом шаге → рестарт продолжает с того же шага; карточка не закрывается мимо
  чистого вердикта, закрытие не дублируется.
- Сдача фазы → у каждой карточки, закрытой петлёй в фазе, есть чистый вердикт ревью карточки;
  полное ревью фазы получает итоги ревью карточек как контекст.

### В скоупе

- Отложенное закрытие карточки и стадия ревью карточки; промпт ревью карточки; структурированные
  находки и вердикт ревью карточки намерениями.
- Вердикт, привязанный к SHA; круг «ревью → правки»; сессия правок по находкам из state; тест
  на каждую закрываемую находку blocker/major. Закрытие держат blocker и major; minor — в журнал
  карточки.
- Счётчики кругов и сессий карточки в state (включая упавшие сессии), их неубывание.
- Стоп на пределе с пакетом.
- Окна обрыва всех новых переходов, включая потерю ответа форжа на закрытии.
- Проверка сдачи фазы по вердиктам карточек; итоги ревью карточек в контексте ревью фазы.
- Ключи конфига и строка метрик на каждом исходе карточки.

### Не в скоупе

- Атака дизайна — раздел S2g.
- Сужение ревью фазы до стыков, продолжение фазы мимо `blocked` (изоляция карточки) — после
  метрик S2f и S2g.
- Резка как стадия петли; вторая модель в любой роли (решение S2e).
- «Тот же инвариант сломан повторно» как отдельный стоп: без зарегистрированных предикатов он не
  определяется механически (S2g вводит обязательства с ID); здесь предел — круги и бюджет.

### Ограничения

- Fail-closed: ревью карточки без вердикта, нечитаемая голова ветки, непрочитанные находки state —
  повтор по правилу исхода сессии или стоп с причиной, а не закрытие карточки.
- Допуск — к SHA: ни одна карточка не закрывается петлёй при голове, которую не видело её чистое
  ревью, в том числе после рестарта в любой точке.
- Все тексты сессий — в `core/prompts.ts`; находки и вердикт — намерениями, закрытие — через
  адаптер форжа; работает у всех четырёх харнессов.
- Стадия включается ключом конфига; выключена — поведение петли прежнее без правки ожиданий
  тестов; битое значение или несовместимое сочетание ключей — стоп на старте.
- Расход назван: до трёх кругов на карточку плюс прежнее полное ревью фазы. Пороги отключения
  (экспериментальные, до старта): любой закрытый мимо ревью коммит — стадия выключается; две фазы
  подряд расход на принятую карточку вырос больше чем на 30 %, а поздних дефектов (ревью фазы и
  после мерджа) не стало меньше — стадия выключается.
- Правила корня канона: без проектных следов, команды форжа — в адаптерах, чистый клон,
  храповик покрытия.

### Критерии готовности

- [ ] [S2f.1] Тест: ключи стадии — битое значение или несовместимое сочетание → стоп на старте с
      именем ключа; стадия выключена → тесты прежней сдачи зелёные без правки ожиданий.
- [ ] [S2f.2] Тест: кодер-сессия просит закрыть карточку → карточка на форже открыта, запускается
      ревью диффа карточки от головы до её первой сессии.
- [ ] [S2f.3] Тест: ревью карточки без вердикта → повтор по правилу исхода, затем стоп; находка
      без серьёзности или места — отказ батча с причиной.
- [ ] [S2f.4] Тест: вердикт без открытых blocker и major для головы X, голова ветки X →
      карточка закрыта комментарием кодера; голова ветки не X → карточка открыта, следующий круг;
      открытые minor закрытие не держат и уходят в журнал карточки.
- [ ] [S2f.5] Тест: вердикт с blocker или major → сессия правок получает находки из state;
      каждое ревью карточки, включая последнее, видит весь дифф карточки и открытые находки;
      последняя правка всегда проходит ревью.
- [ ] [S2f.6] Тест: круги и сессии карточки (включая упавшие) — в state; после рестарта, перехода
      в `blocked` и повторной сдачи счётчики не убывают; новые поля state проходят проверку формы.
- [ ] [S2f.7] Тест: предел кругов или бюджет сессий карточки исчерпан, blocker или major открыт →
      карточка `blocked`, стоп фазы с пакетом (находки, SHA последнего ревью); следующая карточка
      не берётся.
- [ ] [S2f.8] Тест: раннер убит после каждого перехода (запрос закрытия, вердикт, коммит правок,
      пуш, закрытие на форже, ответ форжа потерян) → рестарт продолжает с того же шага; карточка не
      закрыта мимо чистого вердикта своей головы; закрытие и комментарий не дублируются.
- [ ] [S2f.9] Тест: сдача фазы при включённой стадии — карточка, закрытая петлёй в фазе без чистого
      вердикта, → стоп с номером карточки.
- [ ] [S2f.10] Тест: промпт полного ревью фазы при включённой стадии прикладывает итоги ревью
      карточек (вердикт, SHA, открытые и закрытые находки); предмет ревью фазы прежний — весь дифф.
- [ ] [S2f.11] Тест: на каждом исходе карточки (закрыта, `blocked`, стоп) — строка метрик: круги,
      сессии и упавшие сессии, находки по серьёзности, время от первой сессии.
- [ ] [S2f.12] Тест: ответ сессии правок называет тест по каждой закрываемой находке blocker или
      major; теста нет в диффе правок → находка остаётся открытой с причиной.

## S2g. Атака дизайна до кода

**Дата**: 2026-11-04
**Статус**: Draft

### Цель

Дыры дизайна ловятся до кода. Слабая модель хорошо атакует готовое решение и плохо
предусматривает дыры в своём: петля ставит её атаковать карточку и композицию фазы до
реализации, а находки, принятые правкой дизайна, становятся обязательствами в теле карточки.

Основание — пилот 04.11: сессия той же модели, получив только тело одной карточки и код до
правки, одним вызовом нашла один из двух blocker, которые позже нашло ревью готового кода, ещё
два blocker и противоречие двух инвариантов карточки. Это возможность, а не надёжность: один
прогон, второй blocker ревью атака целиком не построила.

### Решения человека (04.11)

- Фаза этого раздела — после фазы S2f; до неё атаку на карточках делает вручную резка.
- Находки разбирает сессия правки дизайна, по каждой — явный статус; правка задевает решение
  человека или обязательство — стоп.

### Сценарии

- Фаза стартует → атака композиции: тела всех карточек фазы и код по их картам чтения → таблица
  «кто пишет → кто читает → когда сохраняется → что делает рестарт → что разрешает гейт» не только
  для полей state, но и для состояния вне него: голова и удалённая ветка, PR, неизвестный исход
  пуша, ответ форжа, файлы намерений → контрпримеры на стыки. Патч любой карточки делает
  недействительными строки таблицы, где она участвует.
- Петля берёт карточку без итога атаки для текущей версии тела → атака карточки: шаги × «сессия
  упала / процесс убит / чтение не удалось / не первая попытка»; отдельный обязательный проход по
  домену значений каждого сохраняемого и производного поля (нет, `undefined`, `null`, верное,
  устаревшее, нечитаемое) × первая и повторная попытка × фактический оператор записи; сочетания
  обязательств; связи, не названные карточкой. Писать «остальные исходы безопасны» без трассы
  нельзя: такая комбинация помечается «не доказано» → структурированные находки или «дыр нет».
- Находки есть → правка дизайна: по каждой — «принята / отклонена с опровергнутым шагом
  последовательности / не подтверждена», патч к разделам тела; обязательство с ID не удаляется,
  а уточняется только с отображением «старый ID → новый ID» → одна повторная атака изменённых
  мест и замыкания затронутых связей (карточки, ссылающиеся на изменённые ID) → кодер.
- Повторная атака подтвердила противоречие → карточка `blocked`, стоп с пакетом.
- Тело карточки изменили снаружи → итог атаки недействителен, атака заново.

### В скоупе

- Атака композиции фазы и атака карточки; промпты; структура находки.
- Правка дизайна патчем: статусы находок, защищённые обязательства с ID (уточнение — только
  отображением «старый → новый»; семантическое «не ослаблено» кодом не проверить — это названный
  предел, его держит повторная атака) и раздел «Решения человека», одна повторная атака
  изменённого и замыкания связей.
- Итог атаки, привязанный к хешу тела и базе; бюджет атак и правок на карточку и фазу.
- Окна обрыва: новое тело — в state до записи на форж; потеря ответа форжа.
- Раздел обязательств с ID в шаблоне карточки (скилл `issues`) и проверка формата до атаки.
- Метрики находок по статусам.

### Не в скоупе

- Ревью по карточке — раздел S2f.
- Автоматическая резка; вторая модель.
- Атака PRD и плана фаз — резка, вручную.

### Ограничения

- Находка без структуры, правка без статуса по каждой находке, патч, задевший обязательство или
  «Решения человека», — отказ с причиной; тело на форже прежнее.
- Тело карточки меняется только намерением правки дизайна через адаптер форжа; второй раз за
  одну версию — никогда.
- Стадия включается ключом конфига; выключена — поведение прежнее; битое значение — стоп.
- Пороги отключения (экспериментальные, до старта): больше половины находок отклонены или
  дублируются, а принятые не дали в коде карточки ни одного теста-сценария, который краснеет на
  откате правки, две фазы подряд — автоматическая правка тела выключается; расход на принятую карточку вырос больше чем на 30 % без
  снижения поздних дефектов — стадия выключается.
- Правила корня канона.

### Критерии готовности

- [ ] [S2g.1] Тест: карточка без итога атаки для текущего хеша тела → кодер не запускается,
      запускается атака; итог для этого хеша есть → атака не повторяется, в том числе после
      рестарта; тело изменилось → атака заново.
- [ ] [S2g.2] Тест: находка атаки без исходного состояния, последовательности, нарушения или
      источника (ID обязательства либо «отсутствующий инвариант») → отклонена разбором с причиной;
      сессия без итога → повтор по правилу исхода, затем стоп.
- [ ] [S2g.3] Тест: правка дизайна без статуса хотя бы у одной находки, принятая без ссылки на
      обязательство и сценарий проверки или отклонённая без опровергнутого шага → не принята;
      статусы сохраняются в state и в журнале карточки.
- [ ] [S2g.4] Тест: патч удаляет обязательство с ID без отображения на новый, меняет его без
      отображения «старый → новый» или трогает раздел «Решения человека» → стоп с причиной, тело
      на форже прежнее; патч с добавленными или отображёнными обязательствами — принят.
- [ ] [S2g.5] Тест: после принятого патча — ровно одна повторная атака, предмет — изменённые
      разделы, затронутые обязательства и карточки, ссылающиеся на изменённые ID; подтверждённое
      противоречие → карточка `blocked`, стоп с пакетом.
- [ ] [S2g.6] Тест: атака композиции до первой карточки фазы получает тела всех карточек и строит
      таблицу производителей и потребителей состояния (поля state, ветка, PR, исход пуша, ответ
      форжа); её находки получают статус в правке дизайна карточки-владельца; итог привязан к
      хешам всех тел, патч карточки делает недействительными строки с её участием.
- [ ] [S2g.7] Тест: раннер убит после итога атаки, после записи нового тела в state, после записи
      на форж, при потерянном ответе форжа → рестарт продолжает с того же шага; тело не правится
      дважды; кодер получает тело, которое видела повторная атака.
- [ ] [S2g.8] Тест: бюджет атак и правок на карточку и фазу — в state, не убывает рестартом;
      исчерпан → стоп с пакетом.
- [ ] [S2g.9] Тест: карточка без раздела обязательств с ID при включённой стадии → стоп формата до
      атаки; тест скилла `issues`: шаблон слабого исполнителя содержит раздел обязательств.
- [ ] [S2g.10] Тест: ключ стадии — битое значение → стоп на старте; выключена → тесты прежней
      сдачи зелёные без правки ожиданий.
- [ ] [S2g.11] Тест: строка метрик карточки — находки атаки по статусам, правлено ли тело,
      повторная атака, расход сессий атаки и правки.

## S2h. Закрытие дыр ревью от базы перед автомерджами

**Дата**: 2026-11-05
**Статус**: Draft

### Цель

Закрыть две дыры ревью, которые пилот 04.11 нашёл в `main`: коммит чини-сессии гейта уезжает в мердж
мимо ревью, а фаза-продолжение после перечитывания фаз теряет базу и ревьюится целиком. Первая
нарушает главный инвариант мердж-пути, вторая снимает предохранитель Фазы 26.

### Решения человека (05.11)

- Обе дыры чинятся отдельной короткой фазой до Фазы 30: автомерджи возобновляются только с закрытой

### Сценарии

- Чини-сессия запушила коммиты и упала, либо раннер убит между пушем и записью state → рестарт ведёт
  голову в ревью, а не в гейт мерджа.
- HEAD до чини-сессии не прочитался, первая попытка запушила и прервалась → ревью остаётся полным, а
  не сужается следующей попыткой.
- Фаза с `reviewBase` дошла до ревью после перечитывания фаз на границе → ревью идёт от базы.

### В скоупе

- Признак начатой чини-сессии в state, переживающий рестарт; его проверка перед гейтом.
- Перенос `reviewBase` при перечитывании фаз и проверка формы поля.

### Не в скоупе

- Проверка на уровне гейта «голова не равна голове последнего ревью» — после метрик S2f.
- Барьер на любое новое поле строки `phases` без строки в перечитывании — кандидат отдельно.

### Ограничения

- Fail-closed там, где решается мердж: неизвестно, что запушено, — ревью, а не гейт.
- Упавшая чини-сессия без пуша не гонит холостое ревью пустого диффа (#269).
- Правила корня канона: без проектных следов, команды форжа — в адаптерах, чистый клон, храповик
  покрытия.

### Критерии готовности

- [ ] [S2h.1] Тест: чини-сессия запушила и упала → рестарт идёт в ревью от базы, не в гейт мерджа.
- [ ] [S2h.2] Тест: раннер убит после пуша чини-сессии, до записи итога → рестарт идёт в ревью, не в
      гейт мерджа; то же после каждого раннего стопа между сессией и записью итога.
- [ ] [S2h.3] Тест: HEAD до чини-сессии не прочитался, первая попытка запушила и прервалась → ревью
      полное, база не подменена следующей попыткой.
- [ ] [S2h.4] Тест: чини-сессия упала без пуша → рестарт идёт в гейт, холостого ревью нет.
- [ ] [S2h.5] Тест: новое поле state проходит проверку формы; неверная форма — state повреждён;
      переход фазы снимает поле.
- [ ] [S2h.6] Тест: фаза с `reviewBase` доходит до ревью после перечитывания фаз → ревью идёт от
      базы; `reviewBase` не строкой в свежем конфиге → отказ перечитывания с причиной.

## S2i. Модель по ролям на одном рантайме

**Дата**: 2026-11-05
**Статус**: Draft

### Цель

Дать карточкам и сдаче фазы разные модели одного рантайма настройкой конфига. Быстрая модель стоит
вдвое дороже: на всей фазе она упирается в окно лимита и в непрерывной работе делает меньше, а на
короткой сдаче большого PR окупается. Сейчас такое разделение отвергается на старте, хотя рантайм
не меняется.

### Решения человека (05.11)

- Карточки — на обычной модели, сдача фазы — на быстрой: настройкой, без рестарта между этапами.
- Шаг карточки идёт на обычной модели, включая ревью и правки карточки (S2f): они запускаются на
  каждую карточку, и быстрая модель там съела бы выигрыш.
- Ревью и правки всегда на старшей модели: на шаге карточки они не привязаны к модели кодера, дешёвая
  модель на метке пишет код карточки, но не ревьюит и не правит находки.
- Дешёвая модель для замера — K2.8 Preview на `complexity:low` и `complexity:medium`: K3 стоит как K3.1
  Pro. Ревью и атаку не удешевляем. Порядок: S2i → Фаза 27 → Фаза 31.

### Сценарии

- Конфиг задаёт модель рантайма для сдачи, маршрут для карточек и запись для ревью карточки → кодер идёт
  на маршруте, ревью и правки карточки — на своей записи, ревью фазы, планировщик правок, правки фазы,
  арбитр и чини-сессия — на модели рантайма.
- Метка сложности называет свою модель → карточка с этой меткой идёт на ней, остальные на маршруте по
  умолчанию.
- В конфиге алиас, которого CLI не знает → старт отказывает с именем алиаса, а не падает сессия.

### В скоупе

- Маршрут `modelRouting` в статический `kimi-native` как смена модели, а не назначение рантайма.
- Своя запись модели для ревью и правок карточки; без неё поведение прежнее.
- Проверка алиаса модели на старте у рантайма, где список моделей читается локально.

### Не в скоупе

- Смена рантайма маршрутом: другой экспериментальный рантайм по-прежнему отвергается.
- Маршрут в статический OpenCode: его запуск применяет только `opencodeRuntime.model`.
- Отдельные модели для каждой роли сдачи: ревью, планировщик и правки делят модель рантайма.
- Выбор дешёвых моделей и пороги их допуска — по метрикам следующего замера.

### Ограничения

- Fail-closed: непроверенный маршрут и неизвестный алиас — отказ старта, не молчаливая подмена.
- Значения — в конфиге потребителя, не в ядре. Запись без `provider` при статическом рантайме не-claude
  остаётся отказом: имя чужой модели не должно уехать на другой endpoint.
- Правила корня канона: без проектных следов, команды форжа — в адаптерах, чистый клон, храповик
  покрытия.

### Критерии готовности

- [ ] [S2i.1] Тест: статический `kimi-native`, запись `modelRouting` называет его же → старт без
      отказа; запись называет другой экспериментальный рантайм → отказ, как раньше; статический
      OpenCode с маршрутом в себя → отказ, как раньше: его запуск модель маршрута не применяет.
- [ ] [S2i.2] Тест: при заданном маршруте кодер запускается на модели маршрута, ревью и правки карточки —
      на своей записи; записи нет → ревью карточки на модели роли ревью, правки на маршруте, как раньше.
- [ ] [S2i.3] Тест: при том же конфиге ревью фазы, планировщик правок, правки фазы, арбитр и чини-сессия
      запускаются на модели рантайма.
- [ ] [S2i.4] Тест: метка сложности с записью в `labels` ведёт карточку на свою модель; карточка без
      такой метки — на `default`.
- [ ] [S2i.5] Тест: алиас маршрута, рантайма или `default_model`, которого нет в конфиге CLI, → отказ
      старта с именем алиаса; конфиг CLI не прочитался → отказ, а не пропуск проверки.
- [ ] [S2i.6] Лог каждой сессии называет фактическую модель, так что расход этапов сравним по логу.

## Принятые решения

- **Приёмка — от исполняемой спецификации** (решение человека 04.11, после провала Фазы 24
  и разбора двумя независимыми моделями). Качество фазы держат приёмочные тесты и каталог
  опасностей, записанные до кода и закрытые от исполнителя, а не ревью диффа моделью: на
  одной слабой модели во всех ролях ревью не сходится. Раздел S2e.

- **Доставка — внешняя установка** (решение человека 26.10 после второго мнения Codex
  gpt-6-astra и Kimi K3.1 Pro, `delivery-second-opinions.md`; сабмодуль отвергнут — по
  опыту практиков работает плохо, gitlink не ловится маской защиты). Ядро —
  в `~/.local/share/ralph/<sha>/`, в репозитории — `.ralph/core.lock` (SHA, хэш дерева,
  версии) и контракт. Защищает проверка, а не расположение: хэш перед каждым стартом.
  Исполняемая часть хуков едет с ядром, settings сессии собирает launcher из доверенного
  дерева человека, перед сессией — отрицательная проба. Update готовит ревизию без
  остановки петли и правит lock через PR; активация — рестартом на подтверждённой
  границе, с журналом активации. Без сети — только локальный кеш точной ревизии.
  Тесты ядра уходят из гейта потребителя в гейт канона явной миграцией. До launcher —
  стенд CLI (внешний settings и хук в linked worktree у Claude, Codex, Kimi).
- **Харнесс — пакет адаптера, барьер — по нормализованному событию** (27.10, после разбора
  Codex, Kimi Code и OpenCode по бинарям и документации). Перенос регистрации guard
  (Фаза 16b) оставил барьеры на языке Claude Code, и у трёх CLI в разных сочетаниях они
  молча пропускают правку патчем, MCP с другим форматом имени и исполняемые слои конфига
  дерева, а барьер скиллов блокирует навсегда (по строкам — в разборе). Цель — универсальность, включая харнессы, которых ещё нет; поэтому
  чинится не каждый CLI по отдельности, а язык барьеров (Фазы 16c–16f).
- **Лучшее берём у всех** (решение человека 26.10): механизмы открытых проектов берутся
  с указанием источника (раздел «Внешние источники»), код не копируется — идея
  проверяется своими тестами.

- **Независимое ревью = другая сессия** (решение человека 26.10). Ревью засчитывается,
  если его провела отдельная свежая сессия с валидным вердиктом; совпадение модели,
  провайдера или харнесса с автором кода мердж не держит. Разнообразие моделей
  в ревью — настройка маршрута, а не условие мерджа.
- **Порядок: S4 раньше S3** (решение человека 26.10). После S0–S2 — отдельный продукт,
  затем харнессы и роли.
- **Приёмка S4 — на двух живых потребителях** (решение человека 26.10):
  SourceCraft-монорепо с продом и GitHub-полигон с деплоем.
- **На GitHub один аккаунт, lock защищает раннер** (задача 50, решение человека 27.10 по
  canary задачи 106). Порог одобрений ruleset — 0, `lock-guard` и второго аккаунта нет.
  Площадка lock на GitHub не защищает: ruleset не умеет требовать одобрение только для
  части путей, а порог 1 остановил бы каждый доменный PR; второй аккаунт для одобрения
  не завёлся. Защита — в гейте мерджа (задача 139): перед мерджем раннер сверяет файлы PR
  с защищаемыми путями (`core/protected-paths.ts` — тот же список, что у статического
  теста политики) и на пересечении встаёт, мердж за человеком. Оговорка: правку,
  смердженную мимо раннера (руками, другим инструментом), на GitHub не держит никто.
