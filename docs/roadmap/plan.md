## Что изменилось во второй редакции

Ревью двух моделей (полные тексты — вне репозитория, в рабочем каталоге оператора) и решения
человека 26.10:

- **guard раньше автономии.** Петля на каноне стартует только после минимального guard
  с отрицательной пробой. Сейчас канон регистрирует только `SessionStart` и `PostToolUse`,
  без `PreToolUse`. Раньше guard стоял в Фазе 9, теперь — в S0 (Фаза 2).
- **Синхронизация по manifest.** В `.claude/ralph` потребителя лежат его `ralph.config.json`
  и `ralph.project.md`, поэтому сверка всего каталога затёрла бы конфиг живой петли.
- **У каждой миграции свой откат.** Прежняя копия удаляется только после доказанного
  возврата на неё. Сначала GitHub-полигон, потом SourceCraft-прод.
- **Вернулся запрет второго writer** на тот же `repo_id` (PRD «Не в скоупе», R15).
- **R6 полностью:** для `required` CI блокирует и неизвестная свежесть прогона.
- **R2 в каноне уже атомарен** (`writeFileAtomic`): в задаче остались схема, версия
  и различение «повреждён / отсутствует».
- **Крупные карточки разбиты по путям исполнения:** матрица окон падения, журнал этапов,
  launcher.
- **Стенд внешней установки (бывшая Фаза 9) — только эксперименты CLI.** Обрывы
  update/rollback проверяются на готовом launcher.
- **Протокол update:** подготовка ревизии идёт без остановки петли, активация — рестартом
  на подтверждённой границе.
- **Решения человека 26.10:**
    1. S0 — на этой неделе руками;
    2. метрика продукта — в S1;
    3. демо и путь входа — сразу после S1;
    4. «лучшее берём у всех» — у каждого взятого механизма указан источник.

### Фаза 22: Сдача без холостых кругов и без молчаливого пропуска плана (S2c)

**Цель:** вердикт «merge» ревью правок доводит фазу до гейта без холостого разбора
`blocked`, а правки по ревью никогда не начинаются без решения этапа плана. Оба места
найдены на пилоте Фазы 19 (02.11).
**Затрагивает:** core

Решения:

- **Метку `blocked` первого ревью снимает раннер по вердикту «merge» ревью правок.** В
  ветке `'merge'` лестницы ревью правок (`core/orchestrator.ts`, комментарий «'merge':
  держать нечем») при `lastPrBlocked` — вызов `removeBlockedLabelFn(phase.branch, …)` и
  `lastPrBlocked = false`. Снятие — результат ревью раннера, как и в повторном
  ревью разбора `blocked`, а не решение кодер-сессии. Сбой снятия адаптер уже логирует
  строкой `⚠ Снять blocked … не удалось` и не бросает; гейт тогда видит метку и ведёт
  разбор `blocked` как сейчас.
  **Отвергнуто:** гейт сверяет открытые блокеры вместо метки — метка остаётся контрактом
  с человеком (её ставит и снимает и он), и второй источник правды о блоке разошёлся бы с
  ней.
  **Отвергнуто:** снимать метку и при «merge» арбитра — арбитр без истории, его вердикт
  лестница уже ведёт своим путём; в S2c не входит.
- **Нет модели планировщика — стоп `fix-plan` и в первых правках.** Ветка
  `else if (!planDone && !subFinish('plan', 'skip'))` в первых правках уходит: при ревью
  с находками этап плана всегда идёт через `runFixPlanner`, а помощник уже отвечает на
  пустую или `none` модель стопом «ревью-модель не задана». Запись `skip` остаётся только
  у ветки «ревью без находок».
  **Отвергнуто:** взять модель планировщика из `cfg.model`, как разбор `blocked`, —
  молча подменило бы роль ревью моделью кодера; единое правило — стоп с причиной.
- **«План пропущен» пишет только этап плана.** Из `startStage` (`core/submit-journal.ts`)
  уходит ветка, которая при начале `fixes` без записи `plan` сама дописывает `plan: skip`;
  начало `fixes` без завершённого `plan` — отказ с причиной, как у любого этапа не по
  порядку. Совместимость с журналом прежней ревизии остаётся только в `parseSubmitJournal`
  (чтение с диска уже восстанавливает пропуск `plan`), и тест на неё сохраняется.
  **Отвергнуто:** признак ревизии в журнале — журнал прежней ревизии уже узнаётся
  разбором по порядку записей, новое поле state ради этого не нужно.

**Задетые барьеры:** греп литерала `orchestrator.ts` по тестам — 17 файлов на b142d6d,
`submit-journal.ts` — ни одного; плюс `npx vitest related --run` по правимым файлам
(скилл `plan-phase`, «Задетые барьеры»).

**Задачи:**

- [ ] Вердикт «merge» ревью правок снимает метку `blocked` первого ревью
- [ ] Правки только после решения этапа плана: стоп без модели планировщика, без
      самодописанного пропуска плана

**Когда готова:** тесты оркестратора на снятие метки по «merge», на отказ снятия и на
оставшиеся блокеры зелёные; тесты на стоп без модели планировщика, на `skip` при ревью без

### Фаза 23: Порог правок ревью фазы и вердикт стенда без пропуска (S2c, S3a)

**Цель:** ревью фазы, оставившее только косметику ниже порога из конфига, не запускает
планировщика и сессию правок; стенд живых проб не выходит зелёным, если вердикт пробы
пустой или незнакомый. Оба места нашла вахта 03.11 на сдаче Фазы 21: круг правок ради
одного `nit` (8 мин, две сессии) и пустой вердикт упавшего судьи мимо счёта красных проб.
**Затрагивает:** core, provision

Решения:

- **Зелёные вердикты стенда — перечнем, а не красные.** `result()` в
  `provision/install-stand.sh` ставит `RC=1` на всё, что не `PASS`, `FAIL-CLOSED`, `SKIP`
  или `INFO` (полный набор зелёных исходов проб на 03.11), — включая пустую строку и
  незнакомое слово. В `probe_session-context` вывод судьи берётся в переменную, его код
  выхода проверяется: судья упал или вердикт не из `PASS`/`FAIL`/`INCONCLUSIVE` — `result
session-context FAIL "судья не дал вердикта: …"`.
  **Отвергнуто:** дописать пустой вердикт в список красных — следующее незнакомое слово
  прошло бы так же; перечень зелёных закрывает класс.
  **Отвергнуто:** судья без CLI-обёртки, вызов функцией из bash — судья остаётся
  отдельным процессом на хосте, вне досягаемости проверяемого CLI (`provision/CLAUDE.md`).
- **Порог правок — ключ `review.fixSeverityFloor` конфига потребителя.** Тип и проверка —
  как у `review.backlogSeverityFloor`: один из `FIX_SEVERITY_LEVELS`, незнакомый уровень —
  отказ старта с именем ключа (`core/config-profile.ts`). Решение человека 03.11: у канона
  порог `minor` — значение вписывает вахта в локальный конфиг, ядро его не знает.
- **Порог режет только решение «у ревью были находки» перед этапом плана первых правок.**
  В предикате `reviewHadFindings` (`core/orchestrator.ts`, шаг «Авто-правки по ревью»)
  находка с якорем считается, только если `meetsSeverityFloor(severityOf(comment),
fixSeverityFloor)`; `lastPrBlocked` считается всегда. После Фазы 22 ветка «ревью без
  находок» пишет `plan: skip` и правок не запускает — порог входит в неё же, своей ветки не
  заводит. Находки с якорем были, но все ниже порога — строка лога с числом находок и
  порогом. Находка без метки серьёзности порогом не режется (`meetsSeverityFloor` уже так
  делает): потерять находку дороже лишнего круга.
  **Отвергнуто:** порог из `backlogSeverityFloor` — тот режет заведение карточек лестницы, и
  одно значение на два решения связало бы их без причины.
  **Отвергнуто:** заводить карточку на находку ниже порога — у канона `nit` карточек не
  заводит и в лестнице (`backlogSeverityFloor: minor`), находка остаётся комментарием на PR.
  **Отвергнуто:** порог на лестнице ревью правок и в разборе `blocked` — там правки идут
  только по блокирующим, порог ничего бы не менял.

**Задетые барьеры:** греп литерала `orchestrator.ts` по тестам — 18 файлов на d32c299,
`config-profile.ts` — ни одного; тесты, называющие `install-stand.sh`, — 7 файлов; плюс
`npx vitest related --run` по правимым файлам ядра (скилл `plan-phase`, «Задетые барьеры»).

**Задачи:**

- [ ] Вердикт стенда — перечнем зелёных, сбой судьи `session-context` — FAIL
- [ ] Порог серьёзности находок ревью фазы для запуска правок

**Когда готова:** тесты `result()` на каждый зелёный, красный, пустой и незнакомый вердикт
зелёные; тест пробы на сбой судьи зелёный; тесты конфига на порог и тесты оркестратора на
пропуск правок ниже порога, на правки при находке не ниже порога и на прежнее поведение без
порога зелёные; задетые барьеры, типы и формат зелёные; полный гейт — CI PR.

### Фаза 24: Закреплённая версия CLI и ежедневная канарейка (S3b)

**Цель:** сессия петли исполняет свою копию CLI той версии, с которой снято описание пакета, а
не системный бинарь; раз в сутки петля сама проверяет свежую версию каждого CLI в стенде и при
совпавшем инвентаре готовит PR смены версии под ship человека. Обновление CLI на машине петлю
больше не задевает и не останавливает. Поглощает отложенную карточку допуска версии CLI (#211) и
стендовую часть #236 (без маршрута живого ключа: канарейка идёт на фиктивном провайдере).
**Затрагивает:** adapters, core, provision

**Резка — на уровне контракта** (решение человека 03.11). Решения ниже задают входы, выходы,
инварианты и отказы; точек правки и пошагового патча в карточках нет. Это замер: как
исполнитель K3.1 Pro проектирует сам, по сравнению с Фазами 20–22, где тело задавало патч.

**Ship человека.** Фаза правит пакеты харнессов (`adapters/harnesses/**` — защищаемые пути): гейт
мерджа петли на пересечении встанет, мердж — за человеком.

Решения:

- **Поставку CLI объявляет пакет харнесса.** Новое обязательное поле интерфейса пакета —
  `distribution`: реестр `npm`, имя пакета и путь исполняемого файла внутри установки. Все
  четыре CLI — npm-пакеты. Версия — только `cliVersion` описания, второго поля версии нет.
  **Отвергнуто:** таблица «харнесс → пакет» в ядре или адаптере вне пакета — пятый харнесс
  тогда не подключается без правки чужого кода (#212).
- **Копия CLI — каталог `<каталог состояния>/cli/<харнесс>/<версия>/`.** Установка — точной
  версии, без скриптов пакета (`--ignore-scripts`), во временный каталог с атомарным переносом:
  обрыв не оставляет полукопии. После установки рядом пишется манифест — хеш каждого файла
  дерева; перед стартом копия сверяется с манифестом. Расхождение, отсутствие манифеста, сбой
  установки — типизированный отказ (харнесс, версия, причина), а не исключение с текстом.
  **Отвергнуто:** копия рядом с ядром в установке `<sha>` — у одной версии CLI много ревизий
  ядра, каждая ставила бы свою копию; каталог ревизии ядра неизменяем по манифесту установки.
  **Отвергнуто:** скрипты пакета при установке — исполнили бы код пакета на хосте до любой
  проверки; CLI, которому они нужны, канарейка отвергнет красным.
- **Каталог копий — защищаемая поверхность.** Раннер добавляет его в
  `protectedSurfaces.absolute` контекста сессии; guard блокирует запись, перенос и удаление
  своим кодом `config-surface`. Код хуков не меняется: форма `absolute` уже есть.
- **Сессия исполняет копию, а не PATH; версия сверяется у исполняемого.** Перед каждой сессией
  раннер спрашивает версию у того же пути, которым запустит сессию. Не равна `cliVersion` или не
  прочиталась — стоп до сессии с причиной; строка `⚠` дрейфа уходит. Обёртка запуска хоста (ключ
  конфига `cliLauncher`: харнесс → абсолютный путь) получает путь копии первым аргументом, и
  версия спрашивается через неё же.

  попытками меняются; проверка перед сессией дешевле расследования.
- **Канарейка — стадия петли на границе итерации,** когда сессии нет; не чаще раза в 24 ч.
  Время последнего прогона и итоги по ключу «харнесс@версия» живут в state и переживают
  рестарт. Бюджет времени прогона — константа ядра; превышение и любой сбой самой канарейки

  стопа и без карточек.
- **Свежая версия ставится той же установкой, но в каталог канарейки,** и исполняется только

  протокола; ключей провайдеров и секретов в окружении стенда нет.
  **Отвергнуто:** сравнивать новый снимок с фикстурой репозитория — фикстуры сняты в разное

- **Вердикт — перечнем зелёных.** Зелёная канарейка — каждая проба PASS у новой версии;

- **Фикстура стенда находится по версии описания.** Тесты пакетов читают

### Фаза 25: Причина отказа в следующей попытке и фаза не больше лимита итераций (S2d)

**Цель:** вторая кодер-сессия по карточке получает в промпте сохранённый диагноз первого
отказа (поставка B, `reliability-development.md`); петля не берёт фазу, в очереди которой
карточек больше `maxIterations` (#267). Решения человека 03.11 — в PRD S2d.
**Затрагивает:** core
**Статус (04.11):** под `hold` до перерезки по S2e — 17 критериев при пределе 12 (Фаза 26).

Решения снял планировщик (сверено с кодом main 957df78), карточки их не пересматривают:

- **Источник контекста — `state.refusalSeries` и только он** (S2a, `core/refusal-series.ts`).
  Контекст попадает в промпт, когда серия есть, её `milestone` и `issue` совпадают с фазой и
  взятой карточкой, а код не `live-probe-unavailable`. На этот код петля стоит раньше
  (`stopOnRefusalSeries`), фильтр в сборщике — вторая линия. Серию прерывают применённые
  намерения (`refusalOutcomePersister`), и контекст исчезает вместе с ней — своей памяти у
  контекста нет.
  **Отвергнуто:** перечитывать ленту карточки или журнал сессии — это второй источник правды,
  и в нём живёт текст модели, а не диагноз раннера (PRD S2d.9).
- **Ревизия установки — новое поле серии `coreSha: string | null`.** `recordRefusal` берёт его
  из `at.coreSha`, `refusalOutcomePersister` получает его параметром (в `runLoop` это
  переменная `coreSha`, та же, что у `refusalStopText`). Поле необязательное:
  `parseRefusalSeries` принимает серию без него (записана до этой фазы) и отвергает
  не-строку и не-null с именем поля. Версию state не поднимаем: прежний раннер новое поле
  прочитал бы правильно, а не неверно (правило `inspectState`).
  **Отвергнуто:** брать текущую ревизию в момент сборки промпта — после смены установки
  контекст назвал бы не ту ревизию, на которой случился отказ.
- **Текст контекста собирает `buildRefusalContext` в `core/prompts.ts`** (все тексты сессий —
  там). Заголовок вне рамки — «Прошлая попытка по этой карточке отвергнута раннером»; внутри
  `wrapAsData` строки: код, причина, параметры `ключ=значение` по ключам, отсортированным по
  алфавиту, доказательство (`evidence` или «не сохранено»), ревизия дерева попытки (последний
  из `attemptShas` или «неизвестна»), ревизия установки (`coreSha` или «неизвестна»). Граница
  — `REFUSAL_CONTEXT_MAX = 1500` знаков текста внутри рамки. Длиннее — срез и строка
  `[усечено раннером: показано N из M знаков]`. Причина уже прошла `redactSecrets` в
  `refusalOfParseError`, повторной редакции нет.
- **`wrapAsData` обезвреживает свои делимитеры внутри данных** — класс, а не случай: текст
  карточки и комментариев закрыл бы рамку так же. Вхождения `<<<ДАННЫЕ_НАЧАЛО>>>` и
  `<<<ДАННЫЕ_КОНЕЦ>>>` в тексте заменяются на `<<ДАННЫЕ_НАЧАЛО>>` и `<<ДАННЫЕ_КОНЕЦ>>`
  (две угловые скобки). Текст без делимитеров не меняется ни на знак — промпты без отказа
  остаются прежними (S2d.5).
  **Отвергнуто:** экранировать только в новом сборщике — карточка с делимитером в теле
  закрывала бы рамку и дальше.
- **Подключение — одна строка в сборке кодер-промпта** `runLoop` (`const prompt = …`, после
  `issueContext`). Серия читается `parseRefusalSeries(state.refusalSeries)`. Битое поле до
  сюда не доходит: `inspectState` останавливает старт раньше (S2a), а в памяти поле пишет
  только `recordRefusal`.
- **Бюджет фазы считает очередь петли (`listReadyIssues`), а не все открытые.** Очередь уже
  без `human` (фильтр ядра `withHumanFilter`), без `hold` (у SourceCraft это статус `paused`,
  его отсевает площадка), без `blocked` и чужих авторов — ровно то, что петля возьмёт.
  **Отвергнуто:** `listAllOpenIssues` минус метки в ядре — статус `paused` ядру не виден, и
  придержанная карточка попала бы в счёт.
- **Вердикт — чистая функция `phaseEntryBudget({ milestone, openCount, maxIterations })`** в
  `core/new-issue-policy.ts`. Возвращает `{ kind: 'ok' }`, `{ kind: 'warn', line }` (число
  равно лимиту) или `{ kind: 'stop', diagnosis, question }` (больше лимита). Диагноз
  называет веху, число и лимит. Функция роста `phaseBudgetWarning` и её вызов «после роста»
  не меняются (S2d.17).
- **Две точки входа, одна функция.** Старт — `preflight` (блок `#220` после
  `excludeHumanIssues`): очередь читается `openIssuesFn(state.milestone)`, стоп — `failFn`
  текстом `formatStopMessage`. Граница — вершина `while (true)` в `runLoop` (блок
  `budgetChecked`): очередь — `openIssuesFn(phase.milestone)`, стоп — `pushEventFn` с
  `formatStopMessage` и `break`. Причина стопа — новый `TStopReason` `'phase-budget'`,
  заголовок «фаза больше лимита итераций». Чтение очереди бросило — тот же стоп с текстом
  отказа (S2d.16). Режимы `--once` и `--dry-run` вердикт не ослабляют: dry-run и нужен, чтобы
  увидеть отказ старта заранее.
  **Отвергнуто:** оставить строку `⚠` и поднять лимит — решение человека 03.11, размер фазы
  держит барьер.

**Задетые барьеры:** греп литерала по тестам на 957df78 — `orchestrator.ts` 29 файлов,
`stop-message.ts` 5, `prompts.ts` 3, `new-issue-policy.ts` 2, `refusal-series.ts` 1; плюс

### Фаза 26: Предохранители размера и ревью по диффу продолжения (S2e)

**Цель:** мини-срез раннера, без которого пилот (Фаза 27) мерил бы прежнюю болезнь ревью.
План не пропускает фазу больше 12 критериев, раннер не ревьюит ветку больше предела строк, а
после чини-сессии гейта и в фазе-продолжении открытого PR ревью смотрит дифф, а не весь PR.
Решения человека 04.11 — в PRD S2e.
**Затрагивает:** core, tests, docs

Порядок S2e (решение человека 04.11): эта фаза → установка ревизии ядра и рестарт → Фаза 27
(пилот) → Фазы 28–29 только при вердикте «успех» пилота. Фаза 25 — под `hold`.

Решения снял планировщик (сверено с кодом main 741538b), карточки их не пересматривают:

- **Предел критериев считает таблица покрытия, а не проза фазы.** Колонка «Фаза» строк
  `| [S…] |` раздела «Покрытие критериев PRD» — число строк на фазу; больше 12 — красный тест с
  фазой и числом. Разбор — в `tests/plan-coverage.ts` рядом с `coverageIds` (тот же разбор строк,
  второй колонкой), проверка — в `tests/plan-coverage.test.ts`. Долг — `DEBT` точным числом:
  Фаза 24 — 21, Фаза 25 — 17; изменение числа — красное (как `DEBT` в `phase-size.test.ts`).
  **Отвергнуто:** считать критерии по тексту раздела фазы — проза сжимается при резке, номер
  в таблице — единственное место, где критерий привязан к фазе.
- **Предел строк ветки — на заведении PR фазы, до ревью.** Число — изменённые строки
  (`git diff --numstat` вставки + удаления) от базы ревью фазы до HEAD: у обычной фазы база —
  `origin/main`, у фазы-продолжения — её `reviewBase`. Порог — `review.maxPhaseDiffLines` конфига,
  по умолчанию 4000; не положительное целое — отказ валидации конфига. Превышение — стоп с
  причиной «перережь», порогом и числом; ни одной сессии ревью.
  **Отвергнуто:** прогноз диффа при резке — оценка до кода не проверяема кодом.
- **Ревью от базы — один механизм для двух случаев.** Шаг ревью фазы (лог «🔍 Ревью фазы
  моделью»), когда база задана, получает дифф `<база>..origin/<ветка>` (`reviewDiffContextFn` и
  `phaseDiffFilesFn` уже принимают `base`) и доверенные комментарии PR (открытые находки) и
  собирается новым `buildBaseReviewPrompt` (создать в `core/prompts.ts`): предмет — дифф от
  базы и открытые находки, весь PR заново не пересматривается. Дальше — обычная цепочка сдачи.
  База — полный SHA (40 hex) и предок HEAD ветки (`git merge-base --is-ancestor`); иначе стоп
  с причиной до ревью, ни одной сессии.
- **Фаза-продолжение объявляет базу в конфиге, а не угадывает.** У строки `phases` —
  необязательное поле `reviewBase`; задано — первое ревью фазы идёт от него.
  **Отвергнуто:** брать базу из state прошлой фазы — `advancePhase` сбрасывает state фазы, а
  неявная база молча сузила бы ревью чужой работы.
- **После чини-сессии гейта — ревью от HEAD до неё, а не полная сдача.** Перед чини-сессией
  раннер пишет в state `healReviewBase` = HEAD ветки; после неё сдача повторяется, как сейчас
  (`state.submitted = false`, чистый `reviewOfFixes` — дыра #115 закрыта), но ревью фазы идёт от
  `healReviewBase`. Поле снимает `advancePhase` и успешное ревью от него. Правка гейта
  по-прежнему не идёт мимо ревью; решение 19.07 «полная сдача после чини-сессии» снято решением
  человека 04.11.
  **Отвергнуто:** не ревьюить правку гейта — ровно то, от чего защищало решение 19.07;
  отдельный путь через лестницу ревью правок — второй механизм там, где хватает одного.

**Задачи:**

- [ ] Предел критериев на фазу в барьере покрытия плана
- [ ] Предел изменённых строк ветки перед ревью фазы

### Фаза 28: Контракт фазы и каталог опасностей в раннере (S2e)

### Фаза 29: Сходимость ревью и стопы перерезки (S2e)

**Цель:** ревью предъявляет дефект тестом, правку проверяет мутацией, повторные проходы не
пересэмплируют проверенное, а петля останавливается на перерезку вместо очередного круга.
Каждая фаза оставляет строку метрик.
**Затрагивает:** core
**Старт:** только при вердикте «успех» Фазы 27; после Фазы 28. Карточки режутся до шагов после
пилота.

Решения (уровня плана; до шагов — после пилота):

- **Находка blocker/major — с тестом-воспроизведением в намерении** (путь и текст теста). Раннер
  кладёт тест во временный worktree на HEAD фазы: красный — находка блокирует, зелёный или нет
  теста — minor. Ключ находки — путь и имя теста, а не текст (`findingKey` по 120 символам
  уходит).
- **Мутационная проверка правки:** во временном worktree откатываются изменённые правкой строки
  нетестовых файлов; тест находки и проверка класса обязаны покраснеть, иначе правка не принята.
- **Карта покрытия полного ревью:** файл × класс реестра → проверено/нет, SHA; повторное ревью
  получает дифф правок и непроверенные строки.
- **Стопы перерезки** — второй дефект того же класса; новая находка вне диффа правок на проходе
  ≥2; приёмка дольше `review.maxAcceptanceRatio` × реализации. Стоп несёт пакет: открытые
  классы, красные тесты. Бюджет фазы (сессии приёмки, планы) — в state, сбрасывает только
  `advancePhase`.
- **Строка метрик фазы** на закрытии: время реализации и приёмки, сессии и шаги по ролям,
  находки по проходам, повторы классов.

**Задачи:**

- [ ] Находка с тестом-воспроизведением и ключ по тесту
- [ ] Мутационная проверка правки
- [ ] Карта покрытия и предмет повторного ревью
- [ ] Стопы перерезки и бюджет фазы

### Фаза 30: Ревью по карточке с допуском по SHA (S2f)

**Цель:** карточка закрывается только после ревью ровно того кода, который в ней лежит: кодер
просит закрыть — раннер ревьюит дифф карточки, до трёх кругов «ревью → правки», вердикт привязан
к голове ветки. Предел исчерпан — `blocked` и стоп с пакетом. Решения человека 04.11 — в PRD S2f.
**Затрагивает:** core, tests, docs

Порядок (решения человека 04.11 и 05.11): Фаза 26d (S2h) → эта фаза → Фаза 31 (S2g) → Фаза 27
(пилот S2e), затем Ф16e отдельным решением. Ревью фазы остаётся полным. Резку фазы до старта петли атакует слабая модель вручную (промпт атаки из пилота
04.11), находки — в тела карточек.

Решения снял планировщик (сверено с кодом main 99f0ca2, уточнено атакой тел 05.11), карточки их не
пересматривают:

- **Ключи — в блоке `review`:** `cardReview` (boolean, по умолчанию `false`),
  `maxCardReviewRounds` (целое ≥ 1, по умолчанию 3), `maxCardSessions` (целое ≥ 1, по умолчанию
  8 — все сессии карточки: кодер, ревью, правки, включая упавшие). Несовместимо: любой из двух
  пределов задан при `cardReview` не `true` (ключ без стадии — опечатка); `maxCardSessions`
  меньше `2 × maxCardReviewRounds` (бюджет не покрывает путь: кодер, R ревью, R−1 правок). Круг —
  одно ревью с вердиктом; после последнего ревью правок нет: правку без ревью принять некому. Битое или
  несовместимое — отказ на старте с именем ключа (как `resolveMaxPhaseDiffLines`).
  **Отвергнуто:** отдельный блок конфига — пределы ревью уже живут в `review`.
- **Решения стадии — чистый модуль `core/card-review.ts`** (создать): типы, разбор ключей,
  `decideCardStep(progress, cfg, head)` → `review | fix | close | limit` и формат строки метрик.
  Оркестратор — только склейка. **Отвергнуто:** логика в `orchestrator.ts` — модуль на 14 тыс.
  строк, распил заведён отдельно (Ловушки `core/`).
- **State — одна текущая карточка и история фазы:** `cardReview: TCardProgress | null`
  (`issue`, `milestone`, `firstHead` — HEAD до первой сессии карточки, `closeComment` — отложенный
  комментарий закрытия, `rounds`, `sessions`, `failedSessions`, `lastReviewedHead`, `verdict`,
  `findings`, `pending` — сессия запущена и лёг ли её итог, `closing`, `limitHead`, `startedAt`) и `cardHistory: TCardRecord[]` (исход, голова, вердикт, находки, счётчики, время).
  Оба — в перечне формы `inspectState`; `advancePhase` сбрасывает оба; счётчики только растут.
  Одна текущая карточка достаточна: предел ведёт к стопу фазы, параллельной карточки нет.
- **Закрытие откладывает разбор намерений, а не сессия.** `applySessionRequests` получает `cardStage:
{ issue, role, saveBatchFn }` с ролями `coder`, `review`, `fix`, `closing`. Итог батча уходит в
  `saveBatchFn` ДО первого эффекта: применение снимает строки поштучно, и возврат полем терял бы
  `close` и находки при обрыве. На чистом вердикте раннер пишет строку `close` в файл намерений и
  применяет её ролью `closing`: журнал «начато / применено» (#86) и сверка комментария на форже (#94)
  дают закрытию устойчивость к обрыву даром. При включённой стадии `close` без `cardStage` выбывает:
  забытый вызов получает запрет, а не тихое закрытие.
  **Отвергнуто:** правка промпта кодера «не закрывай» — просьба, а не барьер.
- **Итог сессии ложится дважды.** До спавна `pending: { role, head, saved: false }`, итог в state до
  эффектов — `saved: true`, эффекты доведены — `pending = null`. Рестарт на `saved: false` снимает
  батч в карантин: код возврата рестарт не пережил, и сводка упавшей сессии вердиктом не становится.
- **Намерения ревью карточки — свои виды, по образцу PR:** `card-comment` (`issue`, `comment` с
  тегом серьёзности по `severityOf`; с якорем `{path, line}` — находка, без якоря — сводка-вердикт),
  `card-block` (`issue`, `comment`) и `card-fix` (`issue`, `finding` — ID находки, `test` — имя
  теста). Что роль вправе исполнить, держит таблица ролей в `applySessionRequests`; кодер вердикт
  себе выдать не может. Находки раннер хранит в state (ID `F1…`) и дублирует комментарием в карточку.
- **Вердикт — по образцу `reviewVerdict`:** сводка есть → вердикт; `card-block` или находка
  blocker/major → «находки»; ни сводки, ни блока → повтор по правилу исхода, затем стоп
  `review-no-verdict`. Голова, которую видело ревью, — та, что раннер дал сессии после пуша
  (`pushAfterSession` перед ревью), а не та, что назвала сессия.
- **Предмет каждого ревью карточки — весь дифф карточки** `firstHead..origin/<ветка>`
  (`reviewDiffContextFn` с `base`), плюс открытые находки и, со второго круга, пометка «правка —
  от `lastReviewedHead`». **Отвергнуто:** ревью только инкремента — правка, верная локально,
  ломала бы проверенное раньше незаметно (критика 04.11).
- **Сессии ревью и правок карточки не тратят итерации фазы** (`state.count`, `maxIterations`) и
  не входят в `issueStreak` (`maxSameIssue`): их бюджет — `maxCardSessions`. Иначе три круга
  карточки сожгли бы брейкер «одна карточка подряд».
- **Предел — `blockIssue` и стоп с новым кодом `card-review-limit`:** пакет — номер карточки,
  открытые находки blocker/major, `lastReviewedHead`; ветка и коммиты не трогаются. Следующая
  карточка не берётся. Сдача фазы при включённой стадии сверяет `cardHistory`: карточка с исходом
  «закрыта» без чистого вердикта своей головы — стоп `card-unreviewed`.
- **Ревью фазы прежнее, с контекстом:** `buildReviewPrompt` и `buildBaseReviewPrompt` получают
  необязательный `cardReviewsContext` из `cardHistory` (вердикт, SHA, закрытые и открытые находки);
  предмет ревью фазы не меняется.

**Задачи:**

- [ ] Ключи стадии, модуль решений и поля state карточки
- [ ] Намерения ревью карточки и отложенное закрытие
- [ ] Шаг ревью карточки: запуск после запроса закрытия и закрытие по SHA
- [ ] Правки по находкам, тест на находку, предел и стоп с пакетом

**Изменённые ожидания прежней приёмки:** нет — при `cardReview: false` (по умолчанию) прежние
тесты сдачи зелёные без правки ожиданий (S2f.1).

**Задетые барьеры:** греп литерала пути (на 99f0ca2): `orchestrator.ts` — 29 файлов,

### Фаза 30b: Модель по ролям на одном рантайме (S2i)

**Цель:** карточки и сдача фазы идут на разных моделях одного рантайма настройкой конфига, без
рестарта между этапами; маршрут дешёвых моделей по метке открывается той же правкой.
**Затрагивает:** core, adapters, docs
**Старт:** после мерджа Фазы 30; идёт перед Фазой 27 (решение человека 05.11).

Решения сверены с кодом 91f5166, карточки их не пересматривают:

- **Маршрут в статический `kimi-native` — смена модели, а не назначение рантайма.** У записи
  `EXPERIMENTAL_RUNTIMES` новый признак `appliesRouteModel`, он есть только у `kimi-native`:
  `runKimiNativeOnce` применяет модель маршрута. В `checkExperimentalRuntimes` маршрут не считается
  назначением, если он ведёт в `selected` и у рантайма есть этот признак. Запрет на ночной уход на
  хост без песочницы не слабеет: рантайм и так выбран статически.
  **Отвергнуто:** послабление для любого статического рантайма — `runOpencodeOnce` игнорирует модель
  маршрута, и настройка молча шла бы на другой модели (атака карточки); отдельный ключ `kimiNativeRuntime.coderModel` — второй механизм выбора модели рядом
  с `modelRouting`, и метки сложности им не выразить; снятие статуса `experimental` — песочницы нет.
- **Запись без `provider` остаётся отказом** при статическом рантайме не-claude
  (`assertValidModelRouteEntry`, `requireProvider`): имя чужой модели не уезжает на другой endpoint.
- **Ревью и правки карточки — своя запись `modelRouting.cardReview`.** Схема как у `default`: тот же валидатор,
  и запись входит в `reachableRuntimes`, поэтому проверки рантаймов её видят. `reviewCard` берёт модель
  и `modelProvider` из записи; записи нет — как раньше, `reviewModel` роли ревью.
  **Отвергнуто:** ревью карточки на маршруте кодера — дешёвая модель на метке удешевила бы и ревью, а
  у потребителя на Claude метка `low → haiku` ослабила бы его незаметно; `review.default` — это сдача.
- **Правки карточки идут на той же записи** (решение человека 05.11: ревью и правки всегда на старшей
  модели): `fixCard` берёт `cardReview`, записи нет — как раньше, `pickRouteFn(issue)`.
- **Сдача не меняется.** Ревью фазы, планировщик, правки фазы и арбитр не ставят `modelProvider`, и
  `runKimiNativeOnce` берёт `kimiNativeRuntime.model`; чини-сессия — то же без `healEscalation`. Тест
  держит это на конфиге с маршрутами.
- **Алиас проверяется по `config.toml` дома CLI** в `kimiNativeAuthProblems`: новый параметр
  `requiredModels` (без дублей) и `default_model`, когда `model` не задан, обязаны иметь таблицу
  `[models."<алиас>"]`: заголовок на своей строке, алиас сравнивается буквально, комментарий не
  считается; нет — проблема с именем алиаса. **Отвергнуто:** живой запрос списка моделей — сеть на старте и новый отказ без
  пользы; новый алиас, которого CLI ещё не записал, остановит старт, и это честный стоп.

**Задачи:**

- [ ] Маршрут в статический рантайм, запись `cardReview` и проверка алиаса на старте
- [ ] Ревью карточки на своей записи и тесты разделения ролей

**Когда готова:** на конфиге с Highspeed в рантайме и обычной моделью в маршруте лог показывает `-m`
каждой сессии по ролям из S2i; маршрут в другой экспериментальный рантайм отвергается; неизвестный
алиас останавливает старт; полный гейт зелёный.

### Фаза 31: Атака дизайна до кода (S2g)

**Цель:** дыры дизайна ловятся до кода: петля атакует композицию фазы и каждую карточку до первой
кодер-сессии, находки со статусами разбирает правка дизайна, тело меняется патчем с защищёнными
обязательствами. Решения человека 04.11 — в PRD S2g.
**Затрагивает:** core, adapters, .claude/skills, docs
**Старт:** после мерджа Фазы 30 и её метрик; карточки режутся до шагов после неё — решения ниже
она может пересмотреть.

Решения (уровня плана; до шагов — после Фазы 30):

- **Обязательства с ID — раздел тела карточки** (`## Обязательства`, строки `- [O1] …`): шаблон
  слабого исполнителя (скилл `issues`) и формат карточки (`issueFormat`) — до атаки. Уточнение —
  строкой отображения `[O1] → [O1a]`; удаление без отображения и правка «Решений человека» —
  отказ патча.
- **Атака карточки и композиции — сессии роли ревью** (`review.default`) с промптами в
  `core/prompts.ts`; промпт карточки — шаги × исходы и обязательный проход по домену значений
  (нет, `undefined`, `null`, верное, устаревшее, нечитаемое × первая/повторная попытка × оператор
  записи), «не доказано» вместо «безопасно». Находка — намерение со структурой (исходное
  состояние, последовательность, нарушение, источник: ID или «отсутствующий инвариант»).
- **Итог атаки — по хешу тела и базе** в state; композиция — по хешам всех тел. Новое тело — в
  state ДО `setIssueBody` (метка до эффекта, #87); потерянный ответ форжа — сверка тела чтением.
- **Правка дизайна — роль кодера**, выдаёт статусы по каждой находке и патч разделов; повторная
  атака — изменённые разделы и карточки, ссылающиеся на изменённые ID; подтверждённое
  противоречие — `blocked`, стоп с пакетом (механизм Фазы 30).

**Задачи:**

- [ ] Раздел обязательств с ID: шаблон карточки и проверка формата до атаки
- [ ] Атака карточки: промпт, структура находки, итог по хешу тела
- [ ] Правка дизайна: статусы находок, патч с защитой обязательств, повторная атака
- [ ] Атака композиции фазы и недействительность её строк после патча
- [ ] Окна обрыва атаки и патча, бюджет, ключ стадии и метрики

**Когда готова:** атака до кодера по хешу тела, повтор только при смене тела; находка без
структуры и правка без статуса отвергнуты; патч, задевший обязательство без отображения или
«Решения человека», — стоп, тело прежнее; одна повторная атака с замыканием связей; композиция по
хешам всех тел; рестарт после каждого перехода без двойной правки тела; бюджет — стоп с пакетом;
выключенная стадия — прежнее поведение; полный гейт — CI PR.
