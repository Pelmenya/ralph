# Сведение трёх копий ядра

Карта для Фазы 1 дорожной карты: что берётся из какой копии при сведении ядра в одно дерево,
и manifest для синхронизации Фазы 2 — какие пути каталога ядра у потребителя являются кодом
канона, а какие его данными. Документ — результат сверки, а не план работ: сливает человек
с вахтой, по шагам, с прогоном обоих наборов тестов.

## Три копии

| Копия   | Ревизия            | Что это                                                          |
| ------- | ------------------ | ---------------------------------------------------------------- |
| База    | `5e1a192` (27.08)  | копия ядра в проекте-источнике; с неё снята копия потребителя    |
| Канон   | `9f4c1fb` (25.08)  | этот репозиторий; вынесен из проекта-источника 19.08 (`58e6b42`) |
| Ветвь Б | `306e93a1` (20.10) | копия ядра у потребителя: база плюс 72 коммита                   |

**База не является общим предком в строгом смысле.** Канон вынесен 19.08, а база снята 27.08:
между ними проект-источник получил ещё около тридцати коммитов в ядре. Поэтому направление
правки здесь определено **по истории, а не по сравнению с базой**:

- правка канона — файл менялся в каноне после выноса (`58e6b42..9f4c1fb`);
- правка ветви Б — файл менялся в проекте-источнике после 19.08 12:39 UTC или у потребителя
  после переноса (база → `306e93a1`);
- менялся в обеих — слияние; ни в одной, но файлы различаются — разница выноса (форматирование
  канона и вычищенные пути машин).

Точку выноса по совпадению деревьев найти нельзя: при выносе канон вычищали от следов проекта,
и у любого кандидата расходятся 24–30 файлов. Сверка по истории это обходит.

**Многое сделано дважды.** Срок годности карточек лестницы, адрес накопительной вехи,
«петля не встаёт там, где отказа нет», мердж-статус через шов, конфликт меток на старте,
тихие дефолты форжа — эти правки внесены в обе ветви параллельно, одним смыслом и разным кодом.
Задача «ветку фазы держит раннер» реализована дважды независимо — из двух реализаций остаётся одна.

ядра, остаётся у потребителя.

## Найдено при сверке

- **В `main` канона уже есть утечка**: имя проекта, где ядро обкатывалось, в комментарии
  `core/session-requests.ts` и его теста. Барьер `tests/project-traces.test.ts` на этом дереве
  зелёный, то есть такое имя он не ловит. Сведение закрывает утечку вердиктом «Б», а дыра барьера —
  отдельная задача.
- Карта прошла независимое ревью второй моделью по исходным деревьям: исправлены вердикты
  `core/session-requests.*` и `README.md`, разведено владение `RUNBOOK.md`, дополнен runtime-список.

## Порядок слияния

1. Механика без суждения: «канон», «Б», «пересобрать», «данные» — переносятся как есть.
2. Слияния без конфликта смысла: доки папок, тесты-наборы, где обе ветви добавляли кейсы.
3. Тяжёлые слияния — каждое отдельным коммитом с прогоном обоих наборов тестов:
   `core/config-profile.ts` (схема конфига — ни одного ключа Б не терять), `core/gate.ts`,
   `core/phase-branch.ts` (выбор одной реализации), `core/orchestrator.ts` (по темам).
4. Гейт канона на сведённом дереве зелёный; число тестов не меньше суммы уникальных кейсов обеих ветвей.

В каноне эти файлы живут в `runtimeDir`. Пока потребитель на старой раскладке, они лежат в каталоге
ядра и синхронизация обязана их обходить. После миграции state (протокол канона) живых файлов в каталоге
ядра нет, но остаются маркер `MIGRATED-TO` и копии `*.migrated` — материал отката; их синхронизация
тоже не трогает, удаляются они только после доказанного отказа от отката.

| Путь                          | Что                                                                              |
| ----------------------------- | -------------------------------------------------------------------------------- |
| `ralph.state.json`            | состояние петли                                                                  |
| `ralph.lock`                  | файл-лок процесса                                                                |
| `ralph.log`                   | журнал петли                                                                     |
| `ralph.dry.log`               | журнал сухого прогона                                                            |
| `monitor.out`                 | вывод монитора                                                                   |
| `monitor.pid`                 | pid монитора                                                                     |
| `.deps-lock.sha`              | отпечаток установленных зависимостей                                             |
| `review-findings.jsonl`       | журнал находок ревью                                                             |
| `ralph.requests.jsonl`        | канал намерений сессии                                                           |
| `security-baseline-push.json` | базовая линия аудита                                                             |
| `sessions/`                   | журналы сессий                                                                   |
| `MIGRATED-TO`                 | маркер миграции state: куда уехало состояние; читается барьером старой раскладки |
| `*.migrated`                  | прежние копии runtime-файлов после миграции — материал отката                    |

`node_modules/` не синхронизируется: зависимости ставятся у потребителя.
