# Перевод на внешнюю установку и возврат на встроенную копию

**Задача 107**, Фаза 15 плана (`docs/roadmap/plan.md`). Встроенную копию ядра у потребителя не
удаляют, пока возврат на неё не доказан на нём же. Протокол ниже отрепетирован 27.10.2026 на
GitHub-полигоне с раскладкой продового потребителя: ядро вложено в `.claude/ralph/` дерева, дерево
раннера отдельное. Ход репетиции и номера PR — в задаче 107, а не здесь: у полигона своё имя, а
этот репозиторий публичный.

## Что где лежит

Старая раскладка («всё в каталоге ядра») держит состояние в ДВУХ местах, и это главное, что
надо знать перед переездом:

- `.claude/ralph/` **дерева раннера** (`runnerWorktreeDirname`) — `ralph.state.json`, ход
  живого прогона, монитор. Сюда раннер пишет после перехода в дерево раннера;
- `.claude/ralph/` **места запуска** (дерево человека) — лок, лог и журнал событий первых секунд
  старта.

Новая раскладка — один каталог `runtimeDir` из секции `roots` конфига.

## Что сохранить до переезда

- встроенную копию ядра в дереве — она и есть точка возврата, удаляется только последним шагом;
- копию локального конфига с секцией `roots` и без неё: старая раскладка стартует только без
  `roots`, ядро из установки — только с ней;
- хуки дерева (`.claude/hooks/`, `.claude/settings.json`) — встроенная копия идёт на них, ядро из
  установки собирает settings сессии само (`core/session-settings.ts`).

## Переезд: встроенная копия → внешняя установка

1. Остановить петлю на границе итерации (после закрытия карточки, не посреди сессии).
2. Положить `.ralph/core.lock` и launcher `./ralph`, поставить ревизию (`./ralph install` или
   `./ralph update`) — PR с правкой lock проходит обычным порядком.
3. Вписать секцию `roots` в конфиг.
4. `./ralph start --migrate-runtime` — переезд делает ядро ИЗ УСТАНОВКИ: встроенная копия при
   `roots` и lock в дереве старт отвергает (productRoot из lock ≠ исполняемое ядро), и это
   правильно. Опись берёт файлы из обоих мест старой раскладки (задача 146), журнал
   `.migration.json` в `runtimeDir` называет каждый файл и его каталог (`origins`), оригиналы
   паркуются как `*.migrated`, в обоих деревьях встаёт маркер `MIGRATED-TO`.
5. `./ralph start`.

**Признаки успеха:** журнал `status: done` и среди файлов есть `ralph.state.json`; первая строка
итерации на новой раскладке продолжает номер (`итерация N/…` с тем же N, что был бы следующим на
встроенной копии); `./ralph doctor` зелёный, журнал активации называет ревизию.

## Возврат: внешняя установка → встроенная копия

1. Остановить петлю на границе итерации.
2. `./ralph start --migrate-rollback` (секция `roots` ещё в конфиге). Откат возвращает ТЕКУЩЕЕ
   состояние `runtimeDir` на места из `origins`, а снимок на момент переезда откладывает как
   `*.pre-rollback` (задача 152) — работа на внешней установке не теряется.
3. Убрать секцию `roots` из конфига.
4. Стартовать встроенную копию прежней командой.

**Признаки успеха:** журнал `status: rolled-back`; маркеров `MIGRATED-TO` нет; первая итерация
на встроенной копии продолжает номер с внешней установки; если фаза, начатая до переезда, уже
смерджена, раннер сам переходит к следующей.

**Известное ограничение (задача 153).** Процесс отката сам пишет лог, журнал событий и heartbeat
в старую раскладку раньше переноса и затем встаёт на «`ralph.log` есть в двух местах»; к этому
моменту `ralph.state.json` уже возвращён, а журнал и маркеры ещё говорят «переезд в силе». Пока
задача открыта, откат доводится руками по журналу: файлы, созданные самим откатом, — в сторону
(не удалять), остальные файлы `runtimeDir` — на места из `origins`, `*.migrated` →
`*.pre-rollback`, маркеры `MIGRATED-TO` переименовать, журналу — `rolled-back`. Так и прошла
репетиция; state при этом продолжился.

## Удаление встроенной копии

Только после того, как на этом же потребителе прошли оба направления и по итерации на каждой
стороне. Удаление — обычный PR, откатывающий вложение ядра; после мерджа `./ralph doctor`
зелёный, и `./ralph start` стартует ядро из установки, сверенное с lock.

## Чего протокол не покрывает

Деплой и проверку здоровья после перевода — их доказывает продовый потребитель (у полигона деплоя
нет). Возврат на встроенную копию ПОСЛЕ её удаления — это уже не откат, а повторная установка.
