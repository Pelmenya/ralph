# Как работать в этом репозитории

Здесь лежит **ядро** автономного раннера разработки — то, что подключают к проекту, а не
сам проект. Отсюда почти все правила ниже: код, который нельзя занести проектной
спецификой, история, которую нельзя очистить, и барьеры вместо просьб к модели.

Правила по папкам — рядом с кодом: [`core/`](core/AGENTS.md),
[`adapters/`](adapters/AGENTS.md), [`runtime/`](runtime/AGENTS.md),
[`shared/`](shared/AGENTS.md), [`tests/`](tests/AGENTS.md),
[`provision/`](provision/AGENTS.md), [`.claude/`](.claude/AGENTS.md) — хуки и барьер
сессий в этом репозитории. Что такое раннер по существу — в [README](README.md).

## Гейт

```
npm ci        # один раз
npm run gate  # формат → типы → сьют, fail-fast
```

Гейт обязан быть зелёным на **чистом клоне**: `npm ci && npm run gate` и больше ничего.
Всё, что для этого нужно, лежит в репозитории — свой `vitest.config.ts`, свои
devDependencies, свой `tsconfig.json`. Тест, которому нужен файл потребителя, — красный
здесь по определению; такому тесту место на стороне потребителя.

**Одна проверка знает про среду, и это сказано вслух.** Барьер чистоты продукта на живом
цикле (`tests/live-cycle-purity.test.ts`) гоняет НАСТОЯЩИЙ прогон раннера в песочнице. Сам
барьер идёт везде; две пробы внутри него — про уборку за ненормально убитым прогоном —
требуют своего пространства имён процессов (`unshare --pid`) и без него пропускаются, называя
пропуск в отчёте. Ничего ставить не нужно: `setpriv` и `unshare` есть в базовом образе, а
закрыты пространства имён бывают в ужатых контейнерах со своим seccomp-профилем.

Сторожит это `tests/outside-deps.test.ts`: он ищет в коде якоря НАРУЖУ репозитория —
`process.cwd()`, домашний каталог машины, `resolve(X, '..', '..')`. Такая зависимость не
краснеет там, где нужный файл рядом лежит, поэтому находится позже всех: на машине автора
зелено, на чистом клоне красно. Остатки названы поимённо храповиком `DEBT` — у каждого
есть причина, но каждый остаётся обещанием, которого канон пока не держит.

Отдельные шаги: `npm test`, `npm run typecheck`, `npm run format:check` (починить —
`npm run format`).

**`RALPH_TRACE_DENY`** — список через запятую: имена репозиториев, организаций, доменов
потребителей, а также их меток и фаз. Структурной формы у этих имён нет вовсе (`area:acme`
неотличим от любого двоеточия в тексте), поэтому словарь — единственный способ их
распознать. Без него скан следов идёт только по структурным классам, и гейт об этом
говорит вслух. Там, где имена известны, задавай их: половина барьера иначе не идёт.

## Четыре правила, которые ломаются чаще всего

**1. Никаких проектных следов.** Ни имени проекта-потребителя, ни пути конкретной машины,
ни адреса хоста — ни в коде, ни в комментарии, ни в **сообщении коммита**. Репозиторий
публичный: след в истории правкой файла уже не убирается. Пример писать можно, но только
абстрактной формой — `/path/to/app`, `your-project`, `example.com`. Сторожит
`tests/project-traces.test.ts` (дерево + история), словарь имён приходит снаружи.

**2. Проектные ЗНАЧЕНИЯ живут в конфиге, проектные КОМАНДЫ — в адаптерах.** Ядро знает
контракт, а не команды: состав чеков гейта, имена меток и milestone'ов приезжают из
`ralph.config.json` потребителя, команды форжа — из `adapters/`. Сторожит
`tests/core-purity.test.ts`. У него есть **храповик долга** `DEBT`: модули, где команды
форжа ещё лежат в ядре, названы поимённо с числом строк, и число сверяется равенством.
Вынес вызов в адаптер — опусти число там же.

**3. Барьер вместо абзаца в промпте.** Всё, что обязано соблюдаться, проверяется кодом.
Просьба к модели — не барьер: модель ошибается и «убеждает себя». Если правило нельзя
проверить чеком, скорее всего оно сформулировано не тем языком.

**4. Остановка дороже ошибки, но дешевле молчания.** Транзиент переживают повтором; отказ
по существу останавливает петлю и **называет причину**. Fail-closed везде, где решается
мердж: битый конфиг — стоп, а не «дефолт как у нас»; пустой результат скана — красный, а
не «нечего проверять».

## Как здесь пишут код

- **TypeScript без билд-шага**: исполняется нативным type stripping Node 24. Значит только
  erasable-синтаксис — аннотации типов и ничего больше: ни `enum`, ни `namespace`, ни
  parameter properties. Это включено в `tsconfig.json` (`erasableSyntaxOnly`), но узнать
  об этом лучше отсюда, чем из красного гейта.
- **Пути — от каталога модуля** (`import.meta.dirname`), никогда от `process.cwd()`. Ядро
  запускается и своим клоном, и каталогом внутри проекта-потребителя; CWD в этих раскладках
  разный. Исключение — то, что и должно зависеть от места запуска (лог живого прогона).
- **Комментарий объясняет ПОЧЕМУ**, а не что. В дереве это норма: докблок модуля называет
  инцидент, из которого модуль вырос, и решение, которое иначе выглядит произвольным.
  Правишь такой код — правь и объяснение, иначе оно превращается в ложь о нём.
- **Формат — prettier**, конфиг в `.prettierrc`. Не спорь с ним руками, гони
  `npm run format`.

## Как здесь пишут тесты

- **Побочки в тестах запрещены структурно.** `RALPH_NO_SIDE_EFFECTS=1` (из
  `vitest.config.ts`) переводит боевые `sh`/`shArgv`/`spawnClaude`/запись state в отказ с
  записью в общий журнал, а `tests/test-setup.ts` сверяет журнал после каждого теста.
  Забытый мок не «просто пройдёт» — он покраснеет. **Чтение боевого файла — тоже
  побочка**, если оно связывает прогон с живым деревом: чтение файла намерений стояло без
  предохранителя, и тесты подхватывали намерения отработавшей сессии. Краснели при этом
  сьюты, к каналу намерений отношения не имеющие, — то есть фаза не сдавалась при
  исправном коде.
- **Зависимости подменяются параметром**, а не моком модуля: каждая функция ядра принимает
  своих коллабораторов (`shFn`, `logFn`, `loadStateFn`, …). Тест, которому нечего подменить,
  обычно указывает на то, что зависимость зашита не там.
- **Барьер проверяют «от противного».** Скан, который никогда не краснел, может не работать
  вовсе. Рядом с каждым сканом — юнит-тесты на подсунутом следе.

## Доки

Правила лежат под двумя именами: `CLAUDE.md` читает Claude Code, `AGENTS.md` — остальные
площадки. **Источник один — `CLAUDE.md`**, `AGENTS.md` рядом с ним сгенерирован и правку
руками теряет. Правишь источник — пересобери копию:

```
npm run docs:sync
```

На памяти это тоже не держится. После правки `CLAUDE.md` копию пересобирает PostToolUse-хук
(`.claude/hooks/sync-docs.cjs`), а расхождение ловит сьют (`tests/docs-coverage.test.ts`):
хук срабатывает только там, где правку делает агент этой сессии, и барьером быть не может —
руками, другим инструментом и из CI правка приезжает мимо него.

Ссылку между доками подписывают БЕЗ имени файла в подписи: «в корне канона», а не
«CLAUDE.md». В копии цель ссылки переписывается на `AGENTS.md` — подпись, названная именем,
разъехалась бы с целью и врала бы читателю о том, куда он идёт.

## Git

- **В `main` не пушат — только PR.** Барьер стоит в `.sourcecraft/branches.yaml` и
  действует ИЗ основной ветки, поэтому PR не может ослабить его, пока сам не смержен.
  Обычный PR мёржится без человека — иначе автономная работа невозможна; ship руками
  требуют правки самих барьеров, их список в `.sourcecraft/review.yaml`.
- Сообщение коммита сканируется барьером следов — пиши его так, будто его прочитает
  посторонний, потому что так и будет.
- `ralph.config.json` и `ralph.project.md` в этот репозиторий не коммитятся вовсе: они
  принадлежат потребителю, здесь живёт только шаблон `ralph.project.md.example`.
- **Карточку закрывает описание PR, а не связь с ним.** Площадка связывает PR с задачей
  по номеру, но связь ничего не закрывает, и она бывает ложной: номер матчится в любом
  тексте, включая сообщения коммитов. Поэтому после мерджа в `main` CI гоняет
  `close-merged-issues.mts`, и он закрывает ровно те карточки, которые описание PR назвало
  строкой, НАЧИНАЮЩЕЙСЯ со слова «Закрывает» («Закрывает #10 и #12» — обе). Номер,
  упомянутый посреди фразы, командой не считается.
- **Токен автозакрытию даёт сама площадка.** `SOURCECRAFT_TOKEN` — её предопределённая
  переменная CI, секрет репозитория для неё не нужен. Пока значение тянулось из
  `secrets`, его отсутствие валило весь прогон вместе с гейтом ещё на разборе конфига —
  три красных пуша в `main` это показали. Если механизм всё же упрётся в 403 на закрытии,
  дело не в секрете, а в правах: право МЕНЯТЬ СТАТУС карточек отдельно от чтения
  и комментирования.

## Состояние сессии

`.claude/local/HANDOFF.md` — что сделано и что дальше; его подгружает хук старта сессии.
Файл локальный и под `.gitignore`: передача между сессиями честна только с путями машины
и именами потребителей, а им в публичном репозитории не место. Прежний обезличенный
`.claude/state/HANDOFF.md` из git удалён — обезличенный handoff следующей сессии не
говорил ничего.

## Петля на каноне

Канон — сам себе потребитель: петля работает над этим репозиторием, как над любым
другим. Ядро при этом исполняется из ОТДЕЛЬНОЙ установки на зафиксированной ревизии, а
не из дерева, которое петля правит, — `productRoot` и `consumerRoot` совпадать не могут
(`core/roots.ts`). Проектная половина промпта — `.claude/ralph/ralph.project.md`,
единственное исключение из запрета на файлы потребителя здесь; конфиг остаётся
локальным. Запуск, смена ревизии и переключение очереди между репозиториями — в
[RUNBOOK петли на каноне](docs/runbook-canon-loop.md).
