# `runtime/` — наблюдение за петлёй

Оболочка вокруг петли: панель прогресса, сторож тишины, уведомления. Ничего из этого не
принимает решений о фазе — они только показывают и будят человека. Общие правила
репозитория — в [корне канона](../AGENTS.md).

## Что где

| Модуль                 | Что это                                                               |
| ---------------------- | --------------------------------------------------------------------- |
| `monitor.js`           | ТОНКИЙ entry панели: проверка версии Node и запуск логики             |
| `monitor-panel.mts`    | логика панели: чтение лога, сводка, очередь и PR фазы через шов, пуш  |
| `deadman.ts`           | пороги тишины по последнему событию лога                              |
| `disk-watch.ts`        | сторож свободного места под каталогом состояния: пуш раньше отказа    |
| `telegram-notifier.ts` | односторонний канал «бот → человек»                                   |
| `product-metric.ts`    | метрика продукта: исход задач, доля мерджа в бюджет, счётчик барьеров |
| `metric.mts`           | команда сводки за период: конфиг, лог и state экземпляра → строка     |

## Местные правила

**Признак жизни петли — свежее из `ralph.log` и его heartbeat** (задача 95). Смена HEAD
признаком не годится — легитимные шаги ревью и гейта подолгу его не двигают, — а одного
лога мало: `log()` глотал отказ записи, и полный диск при живом раннере выглядел тишиной.
Теперь строка уходит в три независимых приёмника (`core/event-journal.ts`): лог, журнал
событий и heartbeat фиксированной длины, который перезаписывается на месте и потому
переживает полный диск. Heartbeat несёт последнюю строку, и панель дописывает её в хвост,
если в лог она не легла (`withHeartbeat`): иначе режим считался бы по прошлому шагу, и
сессия жила бы под пятиминутным порогом. Отсюда два следствия, оба неочевидные:

- монитор печатает свой вывод в **свой** stdout, а не через `log()` раннера. Иначе пуш о
  тишине обновил бы mtime лога и замаскировал ровно ту тишину, о которой сообщает;
- чужой прогон (dry-run, не-prod профиль) в боевой лог не пишет — его штатные маркеры
  остановки перевели бы deadman в режим «остановлено» и ослепили сторож боевой петли.

**Трекер панель спрашивает через шов, а не командой форжа** (#58). Панель звала CLI GitHub
напрямую и на площадке без него показывала пустыми ровно две строки, ради которых её
смотрят: сколько задач фазы осталось и есть ли PR. Теперь вопросы идут к `taskSource`,
выбранному тем же `config.adapters`, что у петли (`observerTaskSource` раннера), и у каждого
три различимых исхода: ответ, «шов ответил — ничего» и «шов не ответил» с причиной. Методов
у панели два (`PanelTaskSource`), оба читающие: инвариант «монитор только смотрит» держит
тип, а не вежливость. `observerTaskSource` отвязывает лог раннера от файла — адаптеры пишут
предупреждения через его `log()`, и в процессе монитора они легли бы в `ralph.log`.
Команд форжа в `runtime/` нет, и долга там барьер чистоты ядра не допускает.

**Сторож диска — у панели, раз на эпизод** (`disk-watch.ts`). Сигнал о месте ниже
`observability.diskMinFreeMb` (умолчание 1024 МБ) обязан прийти, пока запись state и лога
ещё проходит: отказ записи тих, и узнают о нём по потерянной фазе. Шлёт его монитор, а не
раннер — раннер на часы уходит в синхронную сессию, а панель тикает. Эпизод кончается
возвратом выше порога; сбой доставки на prod эпизод не защёлкивает, как у DEADMAN.

**Entry остаётся тонким.** `monitor.js` — обычный JS, запускаемый напрямую, потому что
проверка версии Node обязана отработать ДО первого импорта `.mts`. На старом Node импорт
упал бы синтаксической ошибкой вместо внятного «нужен Node 24».

**Секреты — строго из окружения.** Токен и адресат Telegram приходят из env, не из
`ralph.config.json`: конфиг коммитится, история публичная и необратимая.

**Формат сообщений — контракт между модулями.** Строку ожидания деплоя собирает
`core/deploy-check.ts`, а разбирает регуляркой `deadman.ts`. Правишь текст — правь обе
стороны; это ровно тот случай, когда «просто поправил формулировку» ломает сторож.

**Метрика считает успехом только мердж.** Задача, чей исход по логу не распознан, идёт
строкой «исход неизвестен», а не в успехи и не «в работе» (`product-metric.ts`); закрытая
задача несмердженной фазы — своей строкой «закрыта, фаза не смерджена». Разбор
держится на тексте строк раннера — взятие, закрытие, `blocked`, мердж фазы, стоп с кодом
причины, — и тест сверяет эти шаблоны с исходником оркестратора: поправленная
формулировка краснеет там, а не обнуляет сводку молча. Бюджет задачи — только из
конфига (`metrics.taskBudgetMin`) или явным флагом на один запуск; умолчания нет.

**Счётчик барьеров полон по построению, а не по памяти.** Сводка печатает, сколько раз
сработал каждый барьер: строки `⛔ Гейт:` из `core/gate.ts`, узнаваемые по началу строки, и
те стопы, у которых своей строки гейта нет. Тест полноты читает исходник гейта — строки в любых кавычках — и требует,
чтобы каждая строка `⛔ Гейт:` была либо барьером из `GATE_BARRIERS`, либо названа
не-барьером с причиной. Новый отказ гейта без строки в счётчике краснеет там; новая причина
стопа без роли в `STOP_ROLES` не компилируется. Ноль срабатываний печатается: «барьеры
молчали» — тоже утверждение.

**Барьер и стоп петли — разные числа.** Сдаваясь после красного гейта, оркестратор пушит
стоп с кодом причины по тому же событию, которое гейт уже записал строкой. Сложив обе, счётчик
считал бы каждый терминальный отказ дважды. Поэтому стоп, парный строке гейта, в сумму
барьеров не идёт, а стоп петли (`breaker`, `tree-dirty`, `main-conflict`,
`main-sync-failed`, `head-diverged`, `session-unpushed`, `forge-unreadable`, `deadman`,
`unknown`) барьером не
является вовсе: это «чем кончилось», а не «что поймали». Все стопы с
кодом печатаются отдельным разделом. ⛔-пуш без кода причины (инфраструктура, арбитр,
«старт заблокирован») — не стоп: петля по многим из них идёт дальше.

**Суточная строка метрики — у панели, fail-open.** Её шлёт `maybePushDailyMetric` на первом
тике после полуночи UTC — за прошедшие календарные сутки, окно кончается полуночью, а не
моментом тика, иначе окна соседних дней перекрывались бы на дрейф тика; на старте панели
ключ встаёт на сегодня без пуша, иначе каждый рестарт петли слал бы строку. Расчёт идёт тем
же `summarizeRuntime`, что и команда, — два чтения лога разошлись бы в цифрах; проводку
(каталог, конфиг, окно) держит фабрика `dailyMetricLine` под тестом на фикстуре. Ни сбой
расчёта, ни сбой доставки не роняют тик: исключение в `setInterval` убило бы монитор вместе
с deadman. Формат строки (`formatMetricDayLine`) — контракт, тест сверяет её целиком.
